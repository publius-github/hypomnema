# Architecture Reference

Maintained map of the current codebase, kept accurate so a new session can build context from this file instead of re-reading the sources. Update the affected section in the same commit whenever a change touches vault layout, config schemas, engine invariants, module responsibilities, or the build/release flow. Verified against the code at v0.41.0.

## Layers

- Rust core (`src-tauri/src/`) owns all data and business logic: SQLite, YAML parsing, the generation engine, watchers, filesystem access for Journal/Notes. Exposed as ~60 `#[tauri::command]`s in `lib.rs` plus the `vault-updated` event.
- React frontend (`src/`) is presentation only: one Zustand store (`src/store.ts`) wrapping `invoke` calls, ts-rs generated types in `src/bindings/` (regenerated by `cargo test`), Tailwind tokens, CodeMirror 6 editor.
- Two windows: `main` (the app) and `capture`, a small hidden always-on-top window pre-created in `.setup()` that `src/main.tsx` routes to `CaptureWindow.tsx` via the `#/capture` hash - one input calling `capture_task` (task into the `capture_list` list, created manual+favorite on first use via `tasks::ensure_inbox`; the command emits `vault-updated` so the main window refreshes). Shown by the OS-global shortcut `capture_shortcut` and the tray menu; hidden on Esc, focus loss or close, never destroyed. The tray icon (`tray_icon`, menu Show / Quick capture / Quit, left click shows main) and `close_to_tray` (main window close hides instead of quitting; forced off without the tray) are synced from the config in setup, on vault open, on `config_set` and on the watcher reload; a shortcut that fails to parse/register surfaces in the error banner and never blocks saving.

## Vault layout (`vault.rs`)

All working files live under `<vault>/.hypomnema/` (like a repo's `.git`). Never join layout paths by hand - use the helpers in `vault.rs` (`work_dir`, `config_dir`, `settings_file`, `db_path`, `tasks_dir`).

```
<vault>/
  journal/<YYYY>/<YYYY-MM-DD>.md   # journal entries
  .trash/                          # Notes deletes, pruned after 30 days
  .hypomnemaignore                 # gitignore-like filter for the Notes tree
  <user notes>                     # KB root = vault root unless config.kb_path set
  .hypomnema/
    app.db (+wal/shm)              # WAL mode, migrations in db.rs (15 entries)
    settings/app.yml               # AppConfig, source of truth; SQLite `settings` is a mirror
    settings/profiles/*.yml        # saved settings profiles (profiles.rs): visual-subset snapshots
    config/                        # user YAML configs, seeded with commented samples
      recurring.yml scheduled.yml birthdays.yml
      weekly-focus.yml day-reminders.yml day-schedule.yml
      templates/journal.md
      <subfolder>/*.yml            # "packs": merged into recurring/scheduled/birthdays by top-level key
    tasks/                         # two-way Markdown task mirror + agenda.md + read-only today.md (tasks_mirror.rs)
    state/                         # app-written text state (state_export.rs): *.jsonl DB snapshot
      mirror-base/                 # last-exported mirror copies: the import's merge base
    backups/db/ backups/config/    # daily VACUUM INTO + pre-rewrite config copies (backup.rs)
```

The only state outside the vault is `vault-path.txt` in the OS app-config dir. `migrate_layout` moves pre-0.32 flat vaults into `.hypomnema/` (resumable, step-by-step). All file writes go through `write_atomic` (tmp + rename).

## UI sections

Order configurable via `config.section_order`; Settings always last. Besides the combined Dashboard there are two focused variants: **Lists** (every list in a wrapping grid, `lists_page_columns`, rows optionally height-aligned via `lists_page_align_rows`, and a sticky right rail like the dashboard list zone's: the New list button over the All-lists index, which scrolls a column into view and flashes it with an accent ring) and **Days** (the day grid at full height, no list zone; its own `days_today_only` toggle and `days_page_columns` count). All three views end their header with the same + Task quick-add button at the far right, and share the store snapshot - whose window spans the widest of the day grids, so widening one page never leaves it empty - and the drag-and-drop wiring (`components/taskDnd.ts`). The Dashboard and Days headers carry a date picker that jumps the grid to any date. Rail also has Search (Ctrl/Cmd+K), Sync (runs engine), theme toggle, About.

- **Dashboard** - day grid (`grid_columns`, paged) over list-zone backlog columns (paged, split draggable); the list dialog (⋯ on a column, or double-click on the column's free space) manages name/color/description and the backlog itself (add, check off, star, delete, open a task with its subtasks); dnd-kit drag between days/lists; a dated manual list task stays in its list column always (any date, with a date chip - `tasks_snapshot` includes manual list tasks unconditionally), shows on its day column under Exact date wearing the scheduled-style date label and the exact-date color (isListExact in src/lib/tasks.ts; inside the list the stripe stays list-colored unless `list_exact_stripe` and the chip color follows `list_date_chip_color`), and is listed read-only in Upcoming > Scheduled - one row everywhere; weekly focus + day reminders from `dashboard_context`.
- **Upcoming** - sub-tabs Scheduled / Birthdays / Recurring; CRUD writes back into the YAML files (comment-preserving splice in `config_files.rs`). A materialized scheduled event stays listed until its task is done or deleted.
- **Reminders** - the three ambient config files that feed the day columns, in sub-tabs Weekly focus / Day reminders / Day schedule, over a "Right now" summary (this week's phrase, today's reminders, the current and next block). Same index-based splice CRUD as Upcoming (`reminders_overview` + `focus_phrase_*`, `day_reminder_*`, `schedule_block_*`); these files have no packs, so file order is a stable key.
- **Calendar** - month grid: real tasks + read-only projections from `views::calendar_outlook`, per-cadence horizons. The day list groups a day's tasks by category ({X} title prefix, else the list name) and wears the same chips as the cards. Real tasks are interactive: a day-list row drags onto any month cell to reschedule (its own local DndContext, ids `caltask:`/`calday:`; selection follows the drop), a row click opens the task dialog, and the QuickAdd under the list adds a task on the selected day. Projections stay read-only.
- **History** - month completion stats, per-rule daily streaks, completed tasks by day; bounded by retention pruning.
- **Review** (section id `review`) - weekly review over an ISO week (offset navigation, 0 = current): the week's focus phrase, stat tiles (done/past with rate, per-origin, still-open), Completed grouped by day next to Still open (rows open the task dialog; Still-open rows carry a hover action strip - manual tasks: Next wk (`nextWeekTarget` in `src/lib/tasks.ts`: Monday of the following week, clamped to tomorrow for past weeks), Backlog (clear date, keep list, Inbox via `inbox_list` when listless), Done, Delete with Undo; generated tasks get only Done/Delete since their date and list are rule-owned), and a Next week panel (next week's focus, real tasks + `calendar_outlook` projections by day). Composes existing commands only (`tasks_snapshot`, `calendar_outlook`, `dashboard_context` - which pins the asked week's focus phrase, deterministic cycle so harmless); "Weekly note" jumps to the Journal on the week's last day.
- **Journal** - one Markdown entry per date, template-seeded (`{{date}}`), file created on first save.
- **Notes** (section id `kb`) - file tree over the KB root (multi-select with Ctrl/Shift, F2 rename, Delete, Ctrl+C/X/V copy-cut-paste via `kb_copy`/`kb_rename`, drag-and-drop onto a folder row or the root area, right-click menu with the same actions plus new note/folder, "Show in file manager" (`kb_reveal`) and "Copy absolute path" (`kb_abs_path`); folders are created with `kb_mkdir` from the header button, a folder row's button, or the menu), editor (YAML colored per the VS Code Dark+/Light+ spec via --yaml-* vars, markdown/YAML linting with a lint gutter), content search, wiki `[[links]]` and web/mail URLs (both on Ctrl/Cmd+click; URLs go to the system browser via `open_external`, which only accepts http/https/mailto and never touches a shell), `.trash`, plus a Config group editing the six YAMLs + journal template with save-time validation. A collapsible Backlinks strip under the editor lists notes whose `[[wiki links]]` point at the open note plus unlinked plain-text mentions, journal entries (links and mentions via `journal::backlinks`, newest first, the note's own-date entry skipped) and tasks (`tasks::backlinks`, `[[links]]` in title/description only - mentions in short titles are noise); `kb_backlinks` returns the aggregate `BacklinksResult`, and with the KB rooted at the vault the note scan drops `journal/` hits so the journal scan stays authoritative. Link beats mention per file, mention floor 3 chars, same caps as `kb_search`. A note/journal hit navigates there; a task hit opens the task dialog in place. The section's frontend is split across `src/sections/kb/` (NoteRow tree row, EditorPane, TreeMenu, CreateNoteModal, util) with state staying in `KnowledgeBase.tsx`. New-note dialog completes the .md extension explicitly (Tab); the + on a folder row pre-fills that folder's path.
- **Settings** - tabs Profiles (named snapshots of the visual settings: built-in Default resets the visual surface, Save/Apply/Delete with confirms, app.yml backed up before an apply) / Appearance (theme, fonts, text/task/chip/plate colors, dated-list-task look, editor palette + line numbers) / Layout (the three task views, day columns incl. done_display, spacing & density incl. title line clamps, section order) / Tasks & Lists (card and list behavior, quick capture & tray) / Engine / Calendar / Notifications / Files (vault paths, snapshots & mirror, backups) / Maintenance (actions only) (`src/sections/settings/`). Every group is a `SettingsGroup`: a group whose fields all sit at their factory defaults (compared against `config_default` via `src/lib/settingsGroups.ts`) renders collapsed behind a "Customize" affordance; manual expand state is ephemeral.

## Config files (`config_files.rs`, `config.rs`)

| File | Schema |
| --- | --- |
| `recurring.yml` | `tasks: [{schedule: cron, description, items: ["{List} text"]}]` |
| `scheduled.yml` | `events: [{date: YYYY-MM-DD, title, time?}]` |
| `birthdays.yml` | `birthdays: [{name, date: MM-DD, year?}]` |
| `weekly-focus.yml` | `rotation: cycle`, `phrases: [..]` (no packs) |
| `day-reminders.yml` | `reminders: [{day_type: workday\|weekend\|mon..sun, text}]` (no packs) |
| `day-schedule.yml` | `blocks: [{from, to, label}]` (no packs) |

Packs: subfolders of `config/` are walked recursively; a `*.yml` file contributes to whichever of the three task sections its top-level keys name. Errors carry the path relative to `config/`. Broken files never wipe state - last valid config stays active, error shows as a banner.

`AppConfig` (~80 fields): theme + `theme_preset` chrome palettes (default/black/vscode/nord/gruvbox/solarized, per-theme variants in `src/lib/themePresets.ts`) with individual accent/surface/panel/border overrides, typography, dashboard layout, task display (cadence colors, done display/hold, `undo_toast_seconds` for the delete/archive Undo toast, `list_task_lines`/`list_dialog_task_lines` title clamps), vertical rhythm (`task_gap`, `section_gap`, `category_block_gap` for day columns and `list_category_block_gap` for the list columns plus the list dialog, the four Postponed/Done gaps), engine (`retention_days`, `catchup_days`, `cron_ignore_time`), calendar outlook horizons, quick capture (`capture_list`, `capture_shortcut`, `tray_icon`, `close_to_tray`), chip look (`chip_font_scale` sizes every category/list/date chip against the text beside it, `category_color_mode` picks how a category chip is colored via `categoryChipColor`: `single` = one shared `category_color`, `varied` = the list's own color else a `CATEGORY_PALETTE` hue hashed from the name, `alternate` = `category_color_a`/`category_color_b` taking turns by the card's `categoryBlockIndex` - a counter the column runs over its cards in render order, so the turn carries straight through the cadence sections and on into Postponed/Done instead of restarting), `section_order`, files (`kb_path`, `tasks_mirror` + `tasks_mirror_ids`, `backup_keep`), `notify_system`, markdown editor color presets. Adding a setting = field + default + `sanitized()` clamp + `settings_pairs()` in `config.rs`, deciding whether it joins `PROFILE_KEYS` (visual customization) or stays out (behavior, paths, timings), ts-rs regen via `cargo test`, control in the matching Settings tab and group.

Settings profiles (`profiles.rs`): flat YAML mappings of the `PROFILE_KEYS` subset (63 visual fields, pinned by `profile_keys_are_real_fields`) under `settings/profiles/<name>.yml`. Apply = reset every scope key to its default, overlay the file's whitelisted keys, `sanitized()`, `vault.save_config`; missing keys mean defaults, unknown/out-of-scope keys (a smuggled `kb_path`) are ignored, "Default" is the reserved empty overlay. Commands: `config_default` (the frontend's defaults source), `profiles_list`, `profile_save`, `profile_apply` (backs up app.yml via `backup_config_file` first), `profile_delete`.

## Engine (`engine.rs`)

Three generators per pass: recurring (cron), scheduled events, birthdays. No separate dailies/priority generator: "daily" is a cadence bucket derived from firing frequency (`cadence_of`); priority is instance-local user state on ANY task (generated included) and survives engine passes.

- **Dedup**: `rule_runs(rule_key, period_key)` ledger, keys via stable FNV-1a 64. Period keys: recurring `YYYY-MM-DDTHH:MM`, scheduled `YYYY-MM-DD`, birthday `<year>`. Card deletes are hard (`task_delete` drops the row and its `rule_runs` entry), so a deleted instance of a live rule regenerates on the next pass; only the delete-done sweep leaves archived tombstones, and `repair_orphaned_period` unblocks today/future periods whose task vanished without one.
- **Catch-up**: window `[now - catchup_days, today + config.horizon_days() - 1]`, where the horizon is the widest day grid any view shows (`max(grid_columns, days_page_columns)`) - the calendar projection starts right after it; missed firings collapse into the single latest one (one overdue copy, not N); `MAX_FIRINGS = 2000` runaway guard; fresh rules start from today (`rule_seen`).
- **Reconcile**: removing a rule/item removes ALL its instances - future, today's open, and pre-today done history (nothing lingers in the Calendar); only a copy already completed today survives, so editing a rule (key change) never hides a just-finished task. Missing/comment-only `recurring.yml` is treated as transient (generation may run, reconcile must not).
- **Carry-over**: open pre-today tasks move to today with the overdue mark (priority included unless `priority_overdue` is off); dailies are exempt and get rehomed to their firing day; at most one open overdue copy per rule.
- **Done ahead of time**: a task checked off on a future day column keeps that day. Both the list sweep (`clear_done_list_tasks`) and retention pruning skip a done task whose `scheduled_date` is today or later, so it disappears only on the rollover after its own day.
- **Pass phases** (one IMMEDIATE transaction): generate x3 -> carry-over -> retention prune -> clear done list-backlog tasks (`clear_done_list_tasks`) -> purge archived rows (>24h, except pending delete-done tombstones) -> trim old `rule_runs` -> dedupe errors. Returns `EngineOutcome{generated, carried_over, removed, pruned, errors}`.

## Core modules

- `tasks.rs` - lists/tasks CRUD; `ensure_inbox` returns the quick-capture list (case-insensitive match over active lists, promotes an auto namesake, else creates manual+favorite); list names are unique among **active** lists only (partial index `idx_lists_active_name`, migration 015): an archived namesake never blocks a create/rename, an auto list of that name is absorbed into the user list instead (its tasks move over, the auto row goes), a live manual namesake reports "a list named X already exists", and `list_unarchive` refuses a restore whose name is taken. `list_ensure` prefers the active list over an archived namesake. `task_delete` is a hard delete (cascades to subtasks, drops the `rule_runs` row) and returns a `DeletedTasks` snapshot (rows + ledger entry) that `task_restore` puts back - the Undo toast round-trips it through the frontend; original ids are kept while free, and a restore is skipped when the engine already regenerated the same (rule, period) instance. `archived_at` remains only for the delete-done sweep tombstones; lists carry a `favorite` flag (sorts ahead in the list zone). The `overdue` flag survives the status cycle (done does not clear it; the UI just hides it on done cards).
- `tasks_mirror.rs` - Markdown mirror of tasks: one file per list + `scheduled.md` (manual tasks, full authority) + `agenda.md` (generated instances from today onward, gated by `config.tasks_mirror_agenda`: status/priority/time sync back, title/date edits do not, absence never deletes, an id-less line creates a manual task on that day - the phone-over-file-sync surface) + `today.md` (gated by `config.tasks_mirror_today`, covering `tasks_mirror_today_days` days: a read-only phone-readable day sheet - focus phrase, reminders, schedule blocks, Overdue, tasks grouped by category with no `^id` keys; its marker makes the import a no-op, the sweep removes it when the flag turns off, and it gets no mirror-base copy). The optional files ride `ExportOptions`; `export` takes the config dir for `dashboard_context`. Per-line `^<id>` sync keys (omitted with `config.tasks_mirror_ids` off, and a line is then matched to its task by title; in the agenda the date joins the match key); `[x]` done, `[z]` postponed (`[>]` from older versions still parses); marker first line; gated by `config.tasks_mirror`; folder watcher imports outside edits. Every export also snapshots the files into `state/mirror-base/`; the import is a three-way merge against that base: a field applies only when the file changed it, absence deletes only tasks the base knew, a stale line of an app-side-deleted task is not resurrected, and a scheduled/agenda marker under a wrong file name (a sync "conflicted copy") is rejected instead of double-imported. Without a base the file wins wholesale, as before.
- `journal.rs` - entry open/save/list/search, template at `config/templates/journal.md`.
- `kb.rs` - Notes FS layer; `resolve()` blocks path traversal; `.hypomnemaignore` glob filter; trash + 30-day prune.
- `reminders.rs` - `dashboard_context` (weekly focus, ISO-week pinned via `weekly_focus_state`; day-type reminders; schedule blocks) and `overview` behind the Reminders section.
- `views.rs` - read-only projections: upcoming, birthdays, recurring list, calendar outlook, daily streaks, cron weekday labels.
- `state_export.rs` - makes app.db a disposable cache: every mirror-export trigger also writes a full JSONL snapshot of the database's authoritative state under `state/` (tasks with ids/provenance/tombstones, lists, `rule_runs`, `rule_seen`, `weekly_focus_state`; gated by `config.state_snapshot`, on by default), and `Vault::open` on a vault without app.db restores from it before anything can export the empty database over it (a broken snapshot aborts the open for the same reason). Deleting app.db is the supported way to force a rebuild; ids are preserved so the mirror's `^id` keys stay valid.
- `backup.rs` - daily DB snapshot (`VACUUM INTO`) + pre-rewrite config backups, rotation by `backup_keep`, best effort.
- `db.rs` - migrations (15), refuses a newer-than-known `user_version`; `mirror_settings`.
- `lib.rs` - commands, `AppState`, three debounced watchers: `config/`+settings (reload + engine + `vault-updated`), `tasks/` (mirror import), KB root.

## Frontend notes

- Store invalidation: `vaultVersion` counter bumped by engine runs and `vault-updated`; sections re-fetch on it.
- `store.defaults` caches `config_default` once per session (settings disclosure and the Profiles tab); `store.profiles` + load/save/delete/applyProfile wrap the profile commands, applyProfile re-running the engine when a `WINDOW_KEYS` field changed, same contract as `updateConfig`.
- `src/lib/`: date helpers, wiki-link codec, markdown lint/table, md color presets, updater flow (silent on failure, runs once on mount).
- Global keys: Ctrl/Cmd+K search, Ctrl/Cmd+1..9 sections. 60s rollover engine re-run, 30s due-task notification timer; the due toast's Snooze button hides it and forgets the notified id after `notify_snooze_minutes`, so the 30s check raises it again while the task stays open.
- Undo toast (bottom center, `App.tsx`): deleting a task or archiving a list offers Undo for `undo_toast_seconds`; one pending entry at a time (`store.undoEntry`), task undo calls `task_restore` with the snapshot, list undo calls `list_unarchive`.

## Build, release, tests

- `VERSION` is the single version source; `scripts/bump.sh` syncs `package.json`/`tauri.conf.json`/`Cargo.toml`; `scripts/release.sh` = bump + commit + tag `v*` + push. PowerShell twins: `build.ps1`, `release.ps1`. `scripts/build.sh` = local `npm ci && tauri build` (signs updater artifacts only if `~/.tauri/app-pkb.key` present).
- CI (`ci.yml`, push to main + PRs): frontend lint/typecheck/test/build; rust fmt/clippy(-D warnings)/test.
- Release (`release.yml`, tag `v*`): Windows-only NSIS build via `tauri-action`, draft release; first step fails on tag/VERSION mismatch. Updater endpoint = `releases/latest/download/latest.json`; secrets `TAURI_SIGNING_PRIVATE_KEY(_PASSWORD)`.
- Tests: 171 Rust `#[test]`s inline per module (engine.rs is the biggest); frontend Vitest: pure-logic tests (`src/lib/*.test.ts`, `dateFields.test.ts`) plus component smoke tests with a mocked Tauri IPC (`src/App.smoke.test.tsx`, `QuickAddModal.test.tsx`, `Review.smoke.test.tsx`; per-file `@vitest-environment jsdom`, fixtures in `src/test/fixtures.ts` - `defaultConfig` there mirrors `AppConfig::default()` and the typecheck forces it to track new fields, dispatch in `src/test/tauriMocks.ts`). No e2e (tauri-driver has no macOS support and dev happens here).
