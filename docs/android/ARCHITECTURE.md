# Android Notes

Supplement to `docs/general/ARCHITECTURE.md` (the shared Rust core + React frontend map, including the phone UI under `src/mobile/` in its Frontend notes). This file covers only what is specific to the Android build. Android is a second build target of the same Tauri project, cross-compiled for `aarch64-linux-android`; iOS is not planned.

## Prerequisites

The script is run from Linux or WSL - the setups it is built and tested on. What a build needs, with the versions the project builds with:

- Node, npm and Rust as for the desktop (CONTRIBUTING, *Build from source*); the script adds the missing `rustup` targets itself.
- JDK 17 (`java` on `PATH` or `JAVA_HOME`) - the generated project uses Android Gradle Plugin 8.11, which requires it.
- Android SDK with `ANDROID_HOME` exported: `platforms;android-37.0` (compileSdk/targetSdk 37 in the template of the pinned Tauri CLI, minSdk 24), `build-tools;35.0.0`, `platform-tools`, and the NDK `ndk;27.0.12077973` (found under `$ANDROID_HOME/ndk` unless `ANDROID_NDK_HOME` is set). `sdkmanager --licenses` accepted once.
- `python3` - the script patches the generated manifest and Gradle files with it.

Google sign-in on a self-built APK does not work out of the box: the project's Android OAuth client is registered for the SHA-1 of the release key (see Release below). A build of your own needs its own Android OAuth client in Google Cloud for your key's SHA-1 (`keytool -list -v` on the keystore); without one the app works fully, with sync unavailable.

## Build (`scripts/android/build.sh`)

- `src-tauri/gen/android` is generated (`tauri android init`) and **not tracked**: the CLI recreates it from `tauri.conf.json` and rewrites parts of it during a build (a new plugin's Gradle module, for one). Nothing in it is hand-edited; everything a build needs there is written by the script on every run:
  - `ensure_android_project` generates the project when it is missing;
  - `sync_launcher_icons` copies the committed mipmaps from `src-tauri/icons/android/` (see Icons in the general map);
  - `configure_storage_permission` declares `MANAGE_EXTERNAL_STORAGE`, so the in-app vault folder browser can leave the app's own folders;
  - `configure_backup` sets `android:allowBackup="false"`: Auto Backup would otherwise copy the default vault (`getExternalFilesDir()`) and the `device-id` to the user's Google backup, and a restore would hand a new phone the old one's sync identity;
  - `configure_signing` signs a release with the keystore named by `ANDROID_KEYSTORE` (+ `ANDROID_KEYSTORE_PASS`, `ANDROID_KEY_ALIAS`, `ANDROID_KEY_PASS`), writing `keystore.properties` and a `signingConfigs` block. Without the variable a release is signed with the debug key - installable for testing, not publishable - and the script says so. Either way `set_release_signing_config` names the config in the release build type on every run: the template of Tauri CLI 2.12 names none there, and a release built from it as is comes out unsigned;
  - `check_android_notices` (after the build: a fresh `gen/android` has no `tauri.settings.gradle` until `tauri android build` writes it) resolves `universalReleaseRuntimeClasspath` through Gradle and stops the build when it differs from `scripts/general/notices/android-libraries.txt`, printing what to add or remove - the Android half of `THIRD_PARTY_LICENSES.txt` has no CI job, so this is where it is checked.
- APKs are named `Hypomnema-<version>-b<build>-<variant>-<abi>.apk`; the build number lives in `releases/android/.build-number` and increments per run, so a test device can tell two builds of one version apart. `collect_artifacts` copies them into `releases/android/` and, when `APK_COPY_DIR` is set, into that folder too (say a synced folder a test phone installs from). The script header lists the remaining environment overrides (`ANDROID_ABIS`, default `aarch64`; SDK/NDK/JDK roots; `CARGO_TARGET_DIR`; the release keystore).
- `prune_target` runs `scripts/general/prune-target.mjs` first, the same stale-output prune the Windows build script does (see the Build section of `docs/windows/ARCHITECTURE.md`); it covers `target/aarch64-linux-android/` and honors `CARGO_TARGET_DIR` and `PRUNE_DAYS`.

## Release

`release.yml` builds the APK on a `v*` tag next to the Windows installer (`build-android`), behind the same CI gates and the same `release` environment approval. The build step runs `scripts/android/build.sh release` with `ANDROID_ABIS=aarch64` and no keystore, so no secret is in reach while Gradle, the Tauri CLI and the npm and Cargo build scripts run; the release variant comes out signed with the runner's debug key. The next step re-signs it with `apksigner` from `build-tools;35.0.0` using the `ANDROID_KEYSTORE_BASE64` and `ANDROID_KEYSTORE_PASS` secrets (alias `hypomnema`, key password = store password), checks the signer's SHA-256 against `ANDROID_CERT_SHA256` in the workflow, and names the file `Hypomnema_<version>_arm64.apk`. A provenance attestation is recorded for it, and `attach-android` uploads it to the draft release that `build-windows` creates.

The release key (`hypomnema-android.jks`, PKCS12, RSA 4096, `CN=Hypomnema`) stays with the owner, outside the repository. It cannot be replaced: Android installs an update only over an APK with the same signature, and Google Play App Signing can take the same key as the app signing key if the app moves there. SHA-1 `85:69:3D:6E:6A:71:A0:F1:AB:6F:94:DB:71:09:D8:92:92:D5:95:9B` is the one Google's Android OAuth client needs; SHA-256 is in the README.

The app does not update itself on Android: the Tauri updater is desktop-only (`#[cfg(desktop)]`, below). A user installs the next APK over the installed one.

## Native code

- Plain Android API calls need no Kotlin: `PlatformWebview::jni_handle().exec()` hands the JNI environment to tracked Rust - `android_storage.rs` checks `Environment.isExternalStorageManager()` and opens the all-files-access settings screen that way (`MANAGE_EXTERNAL_STORAGE` has no runtime dialog), and writes the vault export into `Download/Hypomnema/` through `MediaStore.Downloads` (Android 10+, no permission; the copy of a vault kept in the app-specific folder, which an uninstall deletes).
- Anything the OS instantiates itself (a service, a worker, an intent filter) or that needs an activity *result* lives in a Tauri plugin with its own tracked `android/` module, which Tauri's build wires into `gen/android` on every build and whose `AndroidManifest.xml` merges into the app's. Today that is `src-tauri/plugins/google-auth/` (Google sign-in through `AuthorizationClient` and `SyncKeepAliveService`, the `dataSync` foreground service that keeps a sync pass alive while the app is put away - details in the general map's Sync entry) and `src-tauri/plugins/widget/` (the home-screen widgets, below).
- **Home-screen widgets** (`src-tauri/plugins/widget/android/`, package `com.hypomnema.widget`): plain `RemoteViews`, no Glance or Compose, so they add no library to `android-libraries.txt`. Two widgets of one shape, a name over a scrolling list, neither with a configure screen, neither editing anything: every tap opens the app. "Hypomnema lists" (`ListWidgetProvider`) shows the user's own lists in alphabetical order (the engine's auto lists stay out), each a card: a head with its colour dot, "group / name" and open count, then its open tasks as rows on the card's surface laid out as the list screen lays them out - under `category_headers` a block's `{Category}` named once over its rows in its chip colour (the alternating palette counted down the list), else a chip on each row - a hairline under every row but the last, the open tasks first, then the postponed and waiting ones and (on a checklist) the ticked ones, each with the app's status box before it and its text in the status colour (a ticked item struck through and muted), "Nothing open" for an empty list, and a foot closing the card's corners; a tap anywhere on the card opens the app on that list (one mutable activity `PendingIntent` template per widget, every piece's fill-in carrying the list id), the name opens the app as is, and it has no +. "Hypomnema today" (`DayWidgetProvider`: it marks its widget ids as the day's on their first draw) shows today's tasks as the Day screen lays them out: the section plates - Exact date, General, Daily... in the configured order, each in its cadence colour on a wash of it, with the count, shown only when there is more than one section - then under `category_headers` (one rule for both widgets) the block's category named once over its rows in its chip colour (else as a chip on each row), then the rows: a priority task's star in the warn tone at the start of its text, the `[MON,SAT]` weekday marker in the app's marker tone, the text clamped to two lines with an ellipsis, a hairline under each row. Postponed and waiting tasks are in: under `done_display` "separate" in their own plates after the cadences - Postponed, Done, waiting, in the plate colours, read by category then title under `closed_sections_sort_alpha` - else in place in their cadence section, and either way with the app's status box before the text (the drawable is a white rounded square with the mark cut out of it, `fillType evenOdd`, so the one colour filter RemoteViews allows paints the box and the mark shows the surface through); done and dropped tasks stay out of the widget. A row tap opens the app on the Day (the template carries the day flag, the rows fill in nothing), the name does the same and + opens it with the day's add field focused. Both share `TaskWidgetProvider` (drawing), `ListWidgetService` (the rows' `RemoteViewsFactory`, five view types: plate, category header, task, list head and list foot - a card is a run of rows, since a collection row cannot hold a variable number of children; the task and category rows carry a background image shown only inside a card, `inCard`), `WidgetStore` (the shared state: `viewFor` resolves a widget id to what it draws) and `WidgetPlugin`, the core's door. The today widget's day is the core's at publish time: after midnight it shows yesterday's tasks until the next export - the engine pass on the app's next resume. The widget never runs the core: it draws from `filesDir/widget/data.json`, which the core publishes through the plugin after every export (`widget.rs` in the general map). The widget wears the app's chrome, not the launcher's: the payload's `theme` is the device's theme palette under the colors.yml overrides, and every colour is applied at draw time - text through `setTextColor` and spans, the rounded backgrounds (widget, card, plate) through an `ImageView` under the content tinted with `setColorFilter` (the one background setter RemoteViews allows paints a flat colour and loses the corners), a plate's wash through `setImageAlpha` on top of it; `values`/`values-night` only cover the first draw before the core has published. RemoteViews inflates only the view classes it allows and calls only `@RemotableViewMethod` setters, and a row that breaks either fails as a whole (the launcher draws "Couldn't add widget" in its place): no plain `View` in a row layout (the hairline is an `ImageView`), and all text styling - the priority star, the marker tone, a ticked item's strikethrough - goes through spans in the text, not through setters. A JSON `null` read through `optString` comes back as the string "null": `WidgetStore.str` is the one way a nullable field is read. A launch intent carries the target (the day flag or the list id) and the add flag as extras, which `WidgetPlugin` takes from the activity's intent (`load`) or a later one (`onNewIntent`) and hands to the core once.
- Desktop-only chrome (tray, global shortcut, updater, the capture window) is `#[cfg(desktop)]` in `lib.rs`, with `#[cfg(mobile)]` no-op stubs of the same signatures - see `docs/windows/ARCHITECTURE.md`.

## Open items

- **OS-scheduled background sync** is not built. Sync runs on resume, on leaving the app, on reconnect, on a heartbeat while open and after an edit; a WorkManager worker would go into a plugin as above.
- **Share-sheet capture** is not built; its intent filter would go into a plugin manifest the same way.
- **The widget's checks** run only on a device: no CI job runs it on every push, and the Kotlin half compiles only in `scripts/android/build.sh` (locally, or in `release.yml` on a tag). The core half (`widget.rs`) has desktop unit tests. Two points to confirm on the first build: that the generated `TauriActivity` forwards `onNewIntent` to the plugins (Tauri's `PluginManager.onNewIntent` exists for it), and that the launcher honours `FLAG_ACTIVITY_SINGLE_TOP` on the launch intent so a widget tap resumes the running activity rather than recreating it.
- **History** is not ported: Review answers "how did the week go?" on a phone. Revisit if phone use shows the need.
- **Update notice**: nothing tells an Android user that a newer APK is out. The desktop's `latest.json` check could drive a banner linking to the release.
