# Architecture Reference (shared core)

Maintained map of the codebase shared across every build target (Windows desktop, Android), kept accurate so a new session can build context from this file instead of re-reading the sources. Update the affected section in the same commit whenever a change touches vault layout, config schemas, engine invariants, or module responsibilities. Platform-only concerns live in `docs/windows/ARCHITECTURE.md` and `docs/android/`; product-level decisions live in `docs/general/DECISIONS.md`. Verified against the code at v0.41.0.

## Layers

- Rust core (`src-tauri/src/`) owns all data and business logic: SQLite, YAML parsing, the generation engine, watchers, filesystem access for Journal/Notes. Exposed as ~60 `#[tauri::command]`s in `lib.rs` plus the `vault-updated` event. This layer is shared as-is across build targets (`#[cfg(desktop)]`/`#[cfg(mobile)]` gate only the small integration bits in `lib.rs` that differ - see `docs/windows/ARCHITECTURE.md`).
- React frontend (`src/`) is presentation only: one Zustand store (`src/store.ts`) wrapping `invoke` calls, ts-rs generated types in `src/bindings/` (regenerated by `cargo test`), Tailwind tokens, CodeMirror 6 editor. Same frontend codebase for every target; platform-specific UI (touch layout, no tray) is planned per `docs/android/`.
- Desktop-only chrome - a second always-on-top `capture` window, the system tray, and the global capture shortcut - lives outside this shared core; see `docs/windows/ARCHITECTURE.md` for how it's wired.

## Vault layout (`vault.rs`)

All working files live under `<vault>/.hypomnema/` (like a repo's `.git`). Never join layout paths by hand - use the helpers in `vault.rs` (`work_dir`, `config_dir`, `settings_file`, `db_path`, `tasks_dir`).

```
<vault>/
  journal/<YYYY>/<YYYY-MM-DD>.md   # journal entries
  .trash/                          # Notes deletes, pruned after 30 days
  .hypomnemaignore                 # gitignore-like filter for the Notes tree
  <user notes>                     # KB root = vault root unless config.kb_path names a folder that exists here
  .hypomnema/
    app.db (+wal/shm)              # WAL mode, migrations in db.rs (19 entries)
    settings/app.yml               # AppConfig, source of truth; SQLite `settings` is a mirror
    settings/profiles/*.yml        # saved settings profiles (profiles.rs): visual-subset snapshots
    config/                        # user YAML configs, seeded with commented samples
      recurring.yml scheduled.yml birthdays.yml
      weekly-focus.yml day-reminders.yml day-schedule.yml
      templates/journal.md
      <subfolder>/*.yml            # "packs": merged into recurring/scheduled/birthdays by top-level key
    tasks/                         # two-way Markdown task mirror + agenda.md + read-only today.md (tasks_mirror.rs)
    state/                         # app-written text state (state_export.rs): *.jsonl DB snapshot
      mirror-base/                 # last-exported mirror copies: the import's merge base
    backups/db/ backups/config/    # daily VACUUM INTO + pre-rewrite config copies (backup.rs)
```

The only state outside the vault is `vault-path.txt` in the OS app-config dir. `migrate_layout` moves pre-0.32 flat vaults into `.hypomnema/` (resumable, step-by-step). All file writes go through `write_atomic` (tmp + rename).

## UI sections

Order configurable via `config.section_order`; Settings always last. The list panels (dashboard list zone and the Lists page) render `orderPanel` items, in one of two shapes chosen by `config.lists_group_display`: **folded** (the default) puts ungrouped lists on the panel as columns plus one tile per group (`GroupColumn`), and **flat** gives every list its own column whatever group it is in, with the group's name as a clickable chip on the column header (the chip drills into the group view) and no group tiles at all. A group tile is a member-list index with open counts over its own + List / + Existing pair (create a list straight into the group, or move an existing one in); ⋯ - and a double-click on the tile's free space - opens `GroupModal` (rename, color, membership checkboxes sorted by name, delete-with-release), and the tile is a drop target. Groups are created via the rail's + New group; the All-lists index lists groups with a ▸ marker (`indexRows` in `src/lib/tasks.ts` builds it): the index keeps the folded shape whatever the panel does, so under **flat** a group still gets its row with its member lists indented beneath it - the panel has spread them out, and the index is then the only place left that says who belongs together. A group row jumps to its tile when there is one, and drills into the group view when there is not (flat). Clicking a group tile (header or any row) switches the whole panel into that group's view - its lists as full columns under a `GroupBackBar` (per-view ephemeral state; the bar carries the group's own ⋯ and doubles as the "take this list out" drop target); a click on a member row also pages/scrolls to that list and flashes it with the same accent ring the index jump uses, and the mouse's back button (button 3) leaves the view. Inside the view the rail's index shows the group's lists ("Group lists"), + New list creates the list directly in the group, + Existing list moves one in, and + New group hides - groups do not nest. Membership is also a drag: a list column's header grip drags `listmove:<id>`, and `components/taskDnd.ts` turns a drop on a group tile (`group:<id>`) or on the back bar (`group:none`) into a `list_set_group` call - the same DndContext as the task cards, told apart by the id prefix. Besides the combined Dashboard there are two focused variants: **Lists** (every list in a wrapping grid, `lists_page_columns`, rows optionally height-aligned via `lists_page_align_rows`, a Groups folded/flat switch in the header beside the column count - the same `lists_group_display` the Layout tab holds, put where the panel it reshapes is; it hides inside a group view, where the shape does not apply, and a sticky right rail like the dashboard list zone's: the New list button over the All-lists index, which scrolls a column into view and flashes it with an accent ring) and **Days** (the day grid at full height, no list zone; its own `days_today_only` toggle and `days_page_columns` count). All three views end their header with the same + Task quick-add button at the far right, and share the store snapshot - whose window spans the widest of the day grids, so widening one page never leaves it empty - and the drag-and-drop wiring (`components/taskDnd.ts`). The Dashboard and Days headers carry a date picker that jumps the grid to any date. Rail also has Search (Ctrl/Cmd+K), Sync (runs engine), theme toggle, About. `config.section_hidden` takes sections off the rail entirely (Settings > Layout, next to the order arrows): Settings itself never hides, Ctrl/Cmd+1..9 follow what the rail actually shows, and standing in a section that is being hidden steps the window to the first one still shown.

- **Dashboard** - day grid (`grid_columns`, paged) over list-zone backlog columns (paged, split draggable); the list dialog (⋯ on a column, or double-click on the column's free space) manages name/color/description/type (todo queue vs persistent checklist, with Check all / Uncheck all for checklists; the phone's inline list settings carry the same controls) plus the list's group, and the backlog itself (add, check off, star, delete, open a task with its subtasks); dnd-kit drag between days/lists; a dated manual list task stays in its list column always (any date, with a date chip - `tasks_snapshot` includes manual list tasks unconditionally), shows on its day column under Exact date wearing the scheduled-style date label and the exact-date color (isListExact in src/lib/tasks.ts; inside the list the stripe stays list-colored unless `list_exact_stripe` and the chip color follows `list_date_chip_color`), and is listed read-only in Upcoming > Scheduled - one row everywhere; weekly focus + day reminders from `dashboard_context`.
- **Upcoming** - sub-tabs Scheduled / Birthdays / Recurring; CRUD writes back into the YAML files (comment-preserving splice in `config_files.rs`). A materialized scheduled event stays listed until its task is done or deleted.
- **Reminders** - the three ambient config files that feed the day columns, in sub-tabs Weekly focus / Day reminders / Day schedule, over a "Right now" summary (this week's phrase, today's reminders, the current and next block). Same index-based splice CRUD as Upcoming (`reminders_overview` + `focus_phrase_*`, `day_reminder_*`, `schedule_block_*`); these files have no packs, so file order is a stable key.
- **Calendar** - month grid: real tasks + read-only projections from `views::calendar_outlook`, per-cadence horizons. The day list groups a day's tasks by category ({X} title prefix, else the list name) and wears the same chips as the cards. Real tasks are interactive: a day-list row drags onto any month cell to reschedule (its own local DndContext, ids `caltask:`/`calday:`; selection follows the drop), a row click opens the task dialog, and the QuickAdd under the list adds a task on the selected day. Projections stay read-only.
- **History** - month completion stats, per-rule daily streaks, completed tasks by day; bounded by retention pruning.
- **Review** (section id `review`) - weekly review over an ISO week (offset navigation, 0 = current): the week's focus phrase, stat tiles (done/past with rate, per-origin, still-open, dropped), Completed grouped by day with a Dropped, not done group under it next to Still open (rows open the task dialog; Still-open rows carry a hover action strip - manual tasks: Next wk (`nextWeekTarget` in `src/lib/tasks.ts`: Monday of the following week, clamped to tomorrow for past weeks), Backlog (clear date, keep list, Inbox via `inbox_list` when listless), Done, Drop, Delete with Undo; generated tasks get only Done/Drop/Delete since their date and list are rule-owned), and a Next week panel (next week's focus, real tasks + `calendar_outlook` projections by day). Composes existing commands only (`tasks_snapshot`, `calendar_outlook`, `dashboard_context` - which pins the asked week's focus phrase, deterministic cycle so harmless); "Weekly note" jumps to the Journal on the week's last day.
- **Journal** - one Markdown entry per date, template-seeded (`{{date}}`), file created on first save.
- **Notes** (section id `kb`) - file tree over the KB root (multi-select with Ctrl/Shift, F2 rename, Delete, Ctrl+C/X/V copy-cut-paste via `kb_copy`/`kb_rename`, drag-and-drop onto a folder row or the root area, right-click menu with the same actions plus new note/folder, "Show in file manager" (`kb_reveal`) and "Copy absolute path" (`kb_abs_path`); folders are created with `kb_mkdir` from the header button, a folder row's button, or the menu), editor (YAML colored per the VS Code Dark+/Light+ spec via --yaml-* vars, markdown/YAML linting with a lint gutter), content search, wiki `[[links]]` and web/mail URLs (both on Ctrl/Cmd+click; URLs go to the system browser via `open_external`, which only accepts http/https/mailto and never touches a shell), `.trash`, plus a Config group editing the six YAMLs + journal template with save-time validation. A collapsible Backlinks strip under the editor lists notes whose `[[wiki links]]` point at the open note plus unlinked plain-text mentions, journal entries (links and mentions via `journal::backlinks`, newest first, the note's own-date entry skipped) and tasks (`tasks::backlinks`, `[[links]]` in title/description only - mentions in short titles are noise); `kb_backlinks` returns the aggregate `BacklinksResult`, and with the KB rooted at the vault the note scan drops `journal/` hits so the journal scan stays authoritative. Link beats mention per file, mention floor 3 chars, same caps as `kb_search`. A note/journal hit navigates there; a task hit opens the task dialog in place. The section's frontend is split across `src/sections/kb/` (NoteRow tree row, EditorPane, TreeMenu, CreateNoteModal, util) with state staying in `KnowledgeBase.tsx`. New-note dialog completes the .md extension explicitly (Tab); the + on a folder row pre-fills that folder's path. Markdown notes carry a `Created:` / `Last edited:` header the app keeps (`config.notes_timestamps`, `kb.rs`): `kb_write` returns the stamped text, and the editor adopts it through `rebaseStamp` (`kb/util.ts`) - only the head that changed is carried onto whatever was typed while the save ran - while `MarkdownEditor` applies an outside value as a minimal diff kept out of the undo history and not echoed back as an edit; a note opens with the cursor under the header (`noteBodyOffset`).
- **Settings** - tabs Profiles (named snapshots of the visual settings: built-in Default resets the visual surface, Save/Apply/Delete with confirms, app.yml backed up before an apply) / Appearance (theme, fonts, text/task/chip/plate colors, dated-list-task look, editor palette + line numbers) / Layout (the three task views, day columns incl. done_display, spacing & density incl. title line clamps, section order) / Tasks & Lists (card and list behavior, quick capture & tray) / Engine / Calendar / Notifications / Files (vault paths, snapshots & mirror, backups) / Maintenance (delete-done, archived-list restore, and a restore list for both backup kinds - `backups_list`/`backup_restore_db`/`backup_restore_config`) (`src/sections/settings/`). The page's own content width is `config.settings_width` (px, 0 = the whole window): the tab strip wraps inside it, so a column too narrow for nine tabs pushes half of them onto a second line. Every group is a `SettingsGroup`: a group whose fields all sit at their factory defaults (compared against `config_default` via `src/lib/settingsGroups.ts`) renders collapsed behind a "Customize" affordance; manual expand state is ephemeral.

## Config files (`config_files.rs`, `config.rs`)

| File | Schema |
| --- | --- |
| `recurring.yml` | `tasks: [{schedule: cron, description, items: ["{List} text"], threshold?: 0-100}]` (`threshold` = the rule's own rate-chip alert, not part of the rule key) |
| `scheduled.yml` | `events: [{date: YYYY-MM-DD, title, time?}]` |
| `birthdays.yml` | `birthdays: [{name, date: MM-DD, year?}]` |
| `weekly-focus.yml` | `rotation: cycle`, `phrases: [..]` (no packs) |
| `day-reminders.yml` | `reminders: [{day_type: workday\|weekend\|mon..sun, text}]` (no packs) |
| `day-schedule.yml` | `blocks: [{from, to, label}]` (no packs) |

Packs: subfolders of `config/` are walked recursively; a `*.yml` file contributes to whichever of the three task sections its top-level keys name. Errors carry the path relative to `config/`. Broken files never wipe state - last valid config stays active, error shows as a banner.

`AppConfig` (~80 fields): theme + `theme_preset` chrome palettes (default/black/vscode/nord/gruvbox/solarized, per-theme variants in `src/lib/themePresets.ts`) with individual accent/surface/panel/border overrides, typography, dashboard layout, task display (cadence colors, done display/hold, `undo_toast_seconds` for the delete/archive Undo toast, `list_task_lines`/`list_dialog_task_lines` title clamps), vertical rhythm (`task_gap`, `section_gap`, `category_block_gap` for day columns and `list_category_block_gap` for the list columns plus the list dialog, the six Postponed/Waiting/Done gaps), engine (`retention_days`, `catchup_days`, `cron_ignore_time`), calendar outlook horizons, quick capture (`capture_list` is used on every target; `capture_shortcut`, `tray_icon`, `close_to_tray` are desktop-only - see `docs/windows/ARCHITECTURE.md`), chip look (`chip_font_scale` sizes every category/list/date chip against the text beside it, `category_color_mode` picks how a category chip is colored via `categoryChipColor`: `single` = one shared `category_color`, `varied` = the list's own color else a `CATEGORY_PALETTE` hue hashed from the name, `alternate` = `category_color_a`/`category_color_b` taking turns by the card's `categoryBlockIndex` - a counter the column runs over its cards in render order, so the turn carries straight through the cadence sections and on into Postponed/Done instead of restarting), `section_order` + `section_hidden`, `lists_group_display` (folded/flat list panels) and `settings_width`, files (`kb_path`, `notes_timestamps`, `tasks_mirror` + `tasks_mirror_ids`, `backup_keep`), `notify_system`, sync (`sync_auto`, `sync_interval_minutes`, `sync_on_leave` - mobile only; the desktop reaches its vault through the filesystem), markdown editor color presets. Adding a setting = field + default + `sanitized()` clamp + `settings_pairs()` in `config.rs`, deciding whether it joins `PROFILE_KEYS` (visual customization) or stays out (behavior, paths, timings), ts-rs regen via `cargo test`, control in the matching Settings tab and group.

Settings profiles (`profiles.rs`): flat YAML mappings of the `PROFILE_KEYS` subset (65 visual fields, pinned by `profile_keys_are_real_fields`) under `settings/profiles/<name>.yml`. Apply = reset every scope key to its default, overlay the file's whitelisted keys, `sanitized()`, `vault.save_config`; missing keys mean defaults, unknown/out-of-scope keys (a smuggled `kb_path`) are ignored, "Default" is the reserved empty overlay. Commands: `config_default` (the frontend's defaults source), `profiles_list`, `profile_save`, `profile_apply` (backs up app.yml via `backup_config_file` first), `profile_delete`.

## Engine (`engine.rs`)

Three generators per pass: recurring (cron), scheduled events, birthdays. No separate dailies/priority generator: "daily" is a cadence bucket derived from firing frequency (`cadence_of`); priority is instance-local user state on ANY task (generated included) and survives engine passes.

- **Dedup**: `rule_runs(rule_key, period_key)` ledger, keys via stable FNV-1a 64. Period keys: recurring `YYYY-MM-DDTHH:MM`, scheduled `YYYY-MM-DD`, birthday `<year>`. Card deletes are hard (`task_delete` drops the row and its `rule_runs` entry), so a deleted instance of a live rule regenerates on the next pass; only the delete-done sweep leaves archived tombstones, and `repair_orphaned_period` unblocks today/future periods whose task vanished without one.
- **Catch-up**: window `[now - catchup_days, today + config.horizon_days() - 1]`, where the horizon is the widest day grid any view shows (`max(grid_columns, days_page_columns)`) - the calendar projection starts right after it; missed firings collapse into the single latest one (one overdue copy, not N); `MAX_FIRINGS = 2000` runaway guard; fresh rules start from today (`rule_seen`).
- **Reconcile**: removing a rule/item removes ALL its instances - future, today's open, and pre-today done history (nothing lingers in the Calendar); only a copy already acted on today (done, dropped or waiting) survives, so editing a rule (key change) never hides a just-finished task. Missing/comment-only `recurring.yml` is treated as transient (generation may run, reconcile must not).
- **Statuses**: `todo`, `postponed`, `waiting` (done on the user's side, waiting on someone else) are open; `done` and `dropped` (not done, taken off the plan) are closed - SQL spells that as `status IN ('done', 'dropped')` (`tasks::STATUSES`/`is_closed`). Closed tasks are what the list sweep, retention and delete-done remove and what carry-over skips; only `done` is a completion (History, Review rate, streaks), so a recurring instance dropped at review time reads as not done. The checkbox cycles todo -> done -> postponed -> waiting -> todo; dropped is only ever chosen on purpose (the card's ⊘, the task dialog, Review's Drop) and a click brings it back to todo. In the separate done display waiting gets its own "Done, waiting" section between Postponed and Done, and dropped shares Done. The waiting mark takes `config.waiting_color` (a muted blue, `#3b80c0`, by default) through the `--color-waiting` var, exposed to Tailwind as the `waiting` color.
- **Carry-over**: open pre-today tasks (postponed and waiting included) move to today with the overdue mark (priority included unless `priority_overdue` is off); dailies are exempt and get rehomed to their firing day; at most one open overdue copy per rule - a waiting copy is never the one collapsed away.
- **Done ahead of time**: a task checked off on a future day column keeps that day. Both the list sweep (`clear_done_list_tasks`) and retention pruning skip a done task whose `scheduled_date` is today or later, so it disappears only on the rollover after its own day.
- **Pass phases** (one IMMEDIATE transaction): generate x3 -> carry-over -> retention prune -> clear done list-backlog tasks (`clear_done_list_tasks`; checklist-kind lists are exempt from both this sweep and retention - their checked items are kept state) -> purge archived rows (>24h, except pending delete-done tombstones) -> trim old `rule_runs` -> dedupe errors. Returns `EngineOutcome{generated, carried_over, removed, pruned, errors}`.

## Core modules

- `tasks.rs` - lists/tasks CRUD; `ensure_inbox` returns the quick-capture list (case-insensitive match over active lists, promotes an auto namesake, else creates manual+favorite); list names are unique among **active** lists only (partial index `idx_lists_active_name`, migration 015): an archived namesake never blocks a create/rename, an auto list of that name is absorbed into the user list instead (its tasks move over, the auto row goes), a live manual namesake reports "a list named X already exists", and `list_unarchive` refuses a restore whose name is taken. `list_ensure` prefers the active list over an archived namesake. `task_delete` is a hard delete (cascades to subtasks, drops the `rule_runs` row) and returns a `DeletedTasks` snapshot (rows + ledger entry) that `task_restore` puts back - the Undo toast round-trips it through the frontend; original ids are kept while free, and a restore is skipped when the engine already regenerated the same (rule, period) instance. `archived_at` remains only for the delete-done sweep tombstones; lists carry a `favorite` flag (sorts ahead in the list zone) and a `kind` (`todo` | `checklist`, set in the list dialog via `list_set_meta`): a checklist keeps its checked items - the overnight list sweep, retention pruning and the delete-done maintenance sweep all skip its tasks (subtasks included) - its tasks have no postponed state in the UI (the checkbox is a plain todo <-> done toggle; a leftover postponed row still renders and can be reset), and `list_set_all_statuses` checks/unchecks the whole list at once (top-level tasks plus their subtasks - the Check all / Uncheck all bulk actions). The `overdue` flag survives the status cycle (done does not clear it; the UI just hides it on done cards). List groups (`list_groups` table, `groups_all`/`group_create`/`group_set_meta`/`group_delete`/`list_set_group`): a group is a named folder in the list panel - the panel shows the group tile (member lists with open counts, drill-in per column), a grouped list (`lists.group_id`) never renders as its own panel column; deleting a group releases its members (ON DELETE SET NULL, which also restamps them for sync); group names are unique among groups; the snapshot carries them in `list_groups.jsonl` (stamped merge like lists.jsonl; a restore drops a membership whose group is gone from a merged snapshot rather than failing the open).
- `tasks_mirror.rs` - Markdown mirror of tasks: a list's file header carries its group as an editable `<!-- group: Name -->` line (a group is otherwise invisible from the vault; editing the line moves the list and creates the group when the name is new, an empty name releases it, and a file with no such line at all - an older export, a hand-made file - leaves the membership alone; it merges against the base like any other field). One file per list + `scheduled.md` (manual tasks, full authority) + `agenda.md` (generated instances from today onward, gated by `config.tasks_mirror_agenda`: status/priority/time sync back, title/date edits do not, absence never deletes, an id-less line creates a manual task on that day - the phone-over-file-sync surface) + `today.md` (gated by `config.tasks_mirror_today`, covering `tasks_mirror_today_days` days: a read-only phone-readable day sheet - focus phrase, reminders, schedule blocks, Overdue, tasks grouped by category with no `^id` keys; its marker makes the import a no-op, the sweep removes it when the flag turns off, and it gets no mirror-base copy). The optional files ride `ExportOptions`; `export` takes the config dir for `dashboard_context`. Per-line `^<id>` sync keys (omitted with `config.tasks_mirror_ids` off, and a line is then matched to its task by title; in the agenda the date joins the match key); `[x]` done, `[z]` postponed, `[xz]` done but waiting, `[zz]` dropped (`[>]` from older versions still parses); marker first line; gated by `config.tasks_mirror`; folder watcher imports outside edits. Every export also snapshots the files into `state/mirror-base/`; the import is a three-way merge against that base: a field applies only when the file changed it, absence deletes only tasks the base knew, a stale line of an app-side-deleted task is not resurrected, and a scheduled/agenda marker under a wrong file name (a sync "conflicted copy") is rejected instead of double-imported. Without a base the file wins wholesale, as before.
- `journal.rs` - entry open/save/list/search, template at `config/templates/journal.md`.
- `kb.rs` - Notes FS layer. The root is the vault itself unless `config.kb_path` names a directory that exists **on this device**: an unset path used to be an error (leaving a phone's Notes tab permanently empty) and a path from another machine still is one on paper - `settings/` never syncs, but a vault copied wholesale from a desktop carries its app.yml along, and `D:\Projects\...` means nothing on a phone. The phone's fallback banner carries a "Use the vault" button that clears `kb_path` locally - settings never sync, so adopting the vault on the phone leaves the desktop's path alone. `kb_status` reports the effective root and whether it is a fallback, so a desktop whose external notes drive is unplugged is told rather than quietly writing into the vault. `write` stamps Markdown notes with the `Created:` / `Last edited:` header when `kb_write` asks it to (setting on, `.md`, not a `journal/` entry of a vault-rooted tree): `stamp_note` keeps the header at the top (inside a frontmatter block when there is one), finds it within the first lines so text typed above it never duplicates it, takes Created from the incoming text, then the disk copy, then the file's birth time, and moves Last edited only when the text under the header changed - a no-op save is not rewritten. `resolve()` blocks path traversal; `.hypomnemaignore` glob filter; trash + 30-day prune. `kb_reveal` (Show in file manager) writes its Windows command line with `raw_arg`: explorer.exe does not parse arguments the way `CommandLineToArgvW` does, so Rust's own quoting made it open a default folder instead of the note whenever the path held a space.
- `reminders.rs` - `dashboard_context` (weekly focus, ISO-week pinned via `weekly_focus_state`; day-type reminders; schedule blocks) and `overview` behind the Reminders section.
- `views.rs` - read-only projections: upcoming, birthdays, recurring list, calendar outlook, daily streaks, cron weekday labels, habit rates. `habit_rates` (command of the same name) gives each recurring rule item (`rule_key`) its completion rate over the newest `habit_rate_window` settled instances: done and waiting count as done, dropped as not done, a daily instance still open after its day as not done (dailies never carry over); an open instance of any other cadence is live overdue work and waits. Items under `habit_rate_min_instances` get no rate. The threshold is the rule's own `threshold:` else `habit_rate_threshold`, and `alert` = rate below it (the percent is rounded down, so a shown 80% never alerts at 80). The store keeps them in `habitRates` (reloaded by `refresh`, by a status change on a recurring task in `updateTask`, and by a change of the three computing settings); `TaskCard` shows `Rate: N%` after the overdue mark behind `habit_rate_chip`, tinted with `habit_rate_alert_color` when alerting; the Recurring section's add/edit forms set the per-rule threshold (empty = default).
- `state_export.rs` - makes app.db a disposable cache: every mirror-export trigger also writes a full JSONL snapshot of the database's authoritative state under `state/` (tasks with ids/provenance/tombstones, lists, list groups, `rule_runs`, `rule_seen`, `weekly_focus_state`; gated by `config.state_snapshot`, on by default), and `Vault::open` on a vault without app.db restores from it before anything can export the empty database over it (a broken snapshot aborts the open for the same reason). Deleting app.db is the supported way to force a rebuild; ids are preserved so the mirror's `^id` keys stay valid.
- `backup.rs` - daily DB snapshot (`VACUUM INTO`) + pre-rewrite config backups, rotation by `backup_keep`, best effort; `overview`/`list_db_backups`/`list_config_backups` back the Maintenance tab's restore list. `restore_db_backup` swaps app.db from a snapshot (caller must close the live connection first; the file being replaced is itself copied aside, and its stale `-wal`/`-shm` siblings are dropped) and `restore_config_backup` puts one config/settings file back in place (also backing up the file it overwrites) - every restore backs up what it's about to replace first, so a restore is itself undoable.
- `db.rs` - migrations (19), refuses a newer-than-known `user_version`; `mirror_settings`. Migration 019 rebuilds `tasks` to widen the status CHECK with `waiting`/`dropped` (self-reference named `tasks_new` during the copy so the DROP cascades into nothing; indexes and stamp triggers recreated, stamps preserved). Migration 017 adds `lists.kind` (`todo` | `checklist`); 018 adds `list_groups` (stamped by the same trigger pattern as migration 016) and `lists.group_id` (FK, ON DELETE SET NULL). Migration 016 adds `updated_at`/`updated_by` to `tasks` and `lists` and stamps them from **triggers**, not from the ~70 call sites that write those tables: a missed site would not fail a build, it would make a changed row look untouched and hand the next cross-device merge to the wrong side. Both triggers stand aside when a statement supplies its own values, which is what lets `state_export::restore` put a snapshot back with the stamps it was taken with instead of relabelling the vault as "changed here, now". `set_device_id` records the writing device per connection (`sync_device`), so the same vault opened on another machine stamps with that machine's id.
- `crypto.rs` / `secret_store.rs` - Argon2id + AES-256-GCM (pure Rust, so the Android cross-compile stays free of native deps) behind an optional device passphrase. One secret is protected today: the Dropbox refresh token, a standing grant to the whole app folder that outlives every access token. Off by default; enabling seals what is already on disk, disabling requires the passphrase, and the unlocked passphrase lives in memory for the session and nowhere else. **Not** vault encryption - the vault is plain files a desktop reads directly and Dropbox syncs as-is (`docs/android/ROADMAP.md` Phase 4 says why, and the UI says the same in the same words).
- `device.rs` - this install's opaque device id (the `updated_by` half), kept in the app's private config dir and never in the vault: a vault synced to a second machine must not carry the first machine's identity, or two devices' edits become indistinguishable.
- Dropbox sync (Android only so far, `docs/android/ROADMAP.md` Phase 1/3; the desktop reaches its vault through the filesystem and never calls these): `sync_provider.rs` is the backend-agnostic trait (list changes since a cursor, read/write/delete a file guarded by an opaque change marker, `Error::SyncConflict` on a stale write or a guarded delete of a file that moved on); `sync_merge.rs` is the per-field last-writer-wins merge with a conflicts list plus the `rule_runs` set union; `sync_state.rs` applies that merge to the JSONL snapshot record by record, giving each file the merge its content deserves (`tasks`/`lists` by their `updated_at`/`updated_by` stamps, `rule_runs` as a set union, `rule_seen` keeping the earliest first-seen so catch-up never re-runs a rule's history, `weekly_focus` keeping this device's pin and logging the other); `sync_cycle.rs` is the full pass - the manifest's revision says whether the remote moved, its hash says whether this device did, and only when both moved does a merge happen (record-wise for the snapshot, a Dropbox-style `(conflicted copy <device> <date>)` file beside the original for prose, because merging two people's prose invents a version neither wrote); `sync_conflicts.rs` keeps what those merges had to choose between in a device-local log; `sync_bootstrap.rs`/`sync_push.rs` remain the one-way first pull and forced upload; `sync_dropbox.rs` implements the trait over Dropbox's HTTP API (`files/list_folder[/continue]`, `files/upload` with `mode: add`/`update(rev)` for real optimistic concurrency, `files/download`, `files/delete_v2` with `parent_rev`) behind a `DropboxTransport` seam so the shaping is unit-tested without a network; `sync_dropbox_oauth.rs` is OAuth2 PKCE (verifier/S256 challenge, authorize URL, code and refresh exchanges) with the app key as a public constant - no client secret exists under PKCE; `dropbox_link.rs` stores the tokens in the app's private config dir (never the vault, never a synced folder) and refreshes the access token ahead of expiry. `dropbox_sync` is the everyday command; when a pass changes the snapshot it drops app.db and reopens the vault so the merged JSONL rebuilds the cache through the existing restore path rather than a second write path into SQLite. Deletions propagate both ways, distinguished from "never pulled" by the manifest and guarded by the revision this device last saw - an edit on the other end outranks a deletion here, and vice versa.
- `lib.rs` - commands, `AppState`, three debounced watchers: `config/`+settings (reload + engine + `vault-updated`), `tasks/` (mirror import), KB root.

## Frontend notes

Written against the desktop's keyboard/mouse interaction model. The phone gets its own UI under `src/mobile/` rather than a responsive squeeze of it (`docs/android/`). Five tabs: Day (`MobileDay`, one day at a time: it drives the store's `gridOffset` - the desktop date-jump mechanism - so the snapshot window follows wherever the day goes, past days included; a date-input picker in the header, the desktop column's ambient context (weekly focus, the day's reminders, today's Now/Next schedule blocks from `dashboard_context`), and the same `splitDone`/`statusHold` Postponed/Done sections the desktop column renders under `done_display` - the phone exposes that switch in its Settings Advanced group, since app.yml is per-device; a persistent input row at the bottom adds a task to the shown day), Lists (`MobileLists`, one list at a time with inline list settings incl. a Group selector; the index shows groups over the ungrouped lists and its bottom field creates either a list or a group - without that a phone could only ever see groups a desktop had made - and a tapped group gets a member-list screen of its own with its own inline settings (rename, colour, delete-with-release) and its own two ways to fill it: a new list straight into the group, or an existing one moved in. Both screens apply the desktop panel's `orderLists` rule - favorites first, auto lists only while something unscheduled or priority lives in them), Journal (`MobileJournal`, a textarea - the system keyboard is the editor on a phone; header date picker plus a `journal_list` entries screen, and it consumes `journalOpenDate` so search hits and the Review's Weekly note land here), Notes (`MobileNotes`, folder-at-a-time browse plus edit, search, tappable `[[wiki links]]`, backlinks, trash, creation and rename/move via inline forms (the WebView's prompt is unreliable on Android), the desktop's Config group - the six YAMLs + journal template through `config_file_get`/`config_file_set` with save-time validation shown inline - and it consumes `kbOpenNote` for search hits), and More (`MobileMore`) holding the sections a five-slot bar cannot seat: Upcoming (`MobileUpcoming`, the three rule files through the desktop's own comment-preserving splice commands, add/edit/delete for root-file rows), Reminders (`MobileReminders`), Calendar (`MobileCalendar`, month browse over its own month-wide `tasks_snapshot` - the store's window follows the day view - plus a QuickAdd on the selected day), Review (`MobileReview`, the desktop Review stacked for one column: done-rate over past days, per-origin tiles, Completed grouped by day, a Next week panel from `tasks_snapshot` + `calendar_outlook`, Weekly note jump, and leftover actions - Next week / Backlog - carried by each row's own "..." via TaskRow's `reviewWeekStart` prop) and Settings (`MobileSettings`: an index of panels rather than one scroll, each row carrying its live state - Sync (when unlinked the panel *is* the Dropbox linking flow, `DropboxLink` embedded; linked it holds sync-now, the automatic-sync switches, the folded one-way actions incl. Unlink, and the conflict log), Passphrase, Appearance (theme, palette, text size, cadence colours, screen edges), Tasks & engine (engine run, notifications, done-display, snooze, capture list, retention, catch-up, cron time), Maintenance mirroring the desktop tab - delete-done sweep, archived-list restore, DB/config backup restore - and Vault (path, move to another folder); boolean settings are switches and number settings commit on blur, both from `mobile/controls.tsx`). `MobileSearch` is the phone's Ctrl+K: a whole-screen palette over `tasks_search`/`kb_search`/`journal_search`, reached from the Day header; a task hit opens the editor (moving the day window there first when the task sits outside it), note and journal hits jump tabs through the same store fields the desktop palette uses (`MobileNavContext` in `mobile/nav.ts` carries the tab switch). The shell renders the store's Undo toast above the tab bar (delete/archive on a phone is one tap with no confirm) and the shared `DueToasts` component (`src/components/DueToasts.tsx`) - the 30s due-check, in-app toast stack and Snooze, extracted from the desktop layout so both targets run the same code. The document itself never scrolls (`html, body { overflow: hidden; overscroll-behavior: none }`): every view owns an inner scroll container, because the Android WebView scrolls the *page* to lift a focused input above the soft keyboard, which slides the whole layout up under the status bar and behind the navigation buttons. For the same reason a scroll container must never be the element carrying the inset - padding on a scrollport scrolls away with the content, and `position: sticky; top: 0` inside one sticks to the padding box, i.e. under the status bar; `MobileTaskEditor` keeps a still wrapper and scrolls its body. Every screen that owns the whole viewport wears `.safe-area` (`src/styles.css`): Android has drawn apps under the status and navigation bars since API 35 and this build targets 36, so each edge takes the larger of `env(safe-area-inset-*)` and a floor the user can raise (`mobile_safe_area_top`/`_bottom`) for the devices where the WebView reports no inset. `MobileVaultFolder` is the phone's answer to "pick a folder" - Android has no directory picker to call (Tauri's dialog plugin picks files; SAF returns a `content://` tree the Rust core cannot open), so the app browses the filesystem itself: `vault_browse` lists a directory with shortcuts, `vault_browse_mkdir` makes one, `vault_use_path` takes the result. Each listing reports two things a plain `read_dir` does not, because on Android both are invisible from the path and both change what the button should say: whether the app can *write* there (probed by writing a file and deleting it) and whether a vault is already there. The default vault location on Android is the app's folder on shared storage rather than its private one - both need no permission, only that one is reachable from a computer over USB. The chooser is a full screen, not a panel. `build-android.sh` declares `MANAGE_EXTERNAL_STORAGE` so the browser can leave those folders, and `android_storage.rs` asks for it from Rust - `PlatformWebview::jni_handle().exec()` hands over the JNI environment, so `Environment.isExternalStorageManager()` and the settings `Intent` need no Kotlin and no edit to the regenerated `gen/android`. Anything needing an activity *result* (a SAF picker) still would. Until the grant happens a directory reports itself unreadable instead of looking empty. `TaskRow` wears the desktop's own signals - colour stripe (hand-picked colour, else the list's, else the cadence palette), `{Category}` chip, list chip, date chip, weekday marker - built from the same `src/lib/tasks.ts` helpers the cards use, and the day view groups into the configured cadence sections via `groupByCadence`: a phone shows fewer tasks at once than a desktop, not less distinguishable ones. `MobileTaskEditor` is a whole screen rather than a dialog, reached from any task row through the `EditingTaskContext` in `mobile/editing.ts`; reordering is Up/Down rather than drag. Automatic sync lives in the shell and fires on resume, on leaving the app, on reconnect, and on a `sync_interval_minutes` heartbeat. Android's hardware back button undoes one UI step instead of minimizing: wry's activity walks the WebView history when it can, so `mobile/back.ts` keeps a sentinel history entry armed while any screen has a step to undo (re-armed from a fresh task after each press - a pushState inside the traversal's own popstate can be dropped natively) - `useBackStep(active, onBack)` handlers stack in activation order (the task editor and search overlay register on mount, screens register their inner steps: list settings / open list / open group, the More screen, the journal browser, the Notes note / search hits / folder trail one level per press, the vault chooser, and finally the non-Day tab back to Day); with nothing registered the press minimizes as usual.

- Store invalidation: `vaultVersion` counter bumped by engine runs and `vault-updated`; sections re-fetch on it.
- `store.defaults` caches `config_default` once per session (settings disclosure and the Profiles tab); `store.profiles` + load/save/delete/applyProfile wrap the profile commands, applyProfile re-running the engine when a `WINDOW_KEYS` field changed, same contract as `updateConfig`.
- `src/lib/`: date helpers, wiki-link codec, markdown lint/table, md color presets, updater flow (silent on failure, runs once on mount).
- Global keys: Ctrl/Cmd+K search, Ctrl/Cmd+1..9 sections. 60s rollover engine re-run; the 30s due-task notification timer lives in `src/components/DueToasts.tsx` (rendered by both the desktop layout and the phone shell) - Snooze hides the toast and forgets the notified id after `notify_snooze_minutes`, so the 30s check raises it again while the task stays open.
- Undo toast (bottom center on the desktop in `App.tsx`, above the tab bar on the phone in `MobileApp.tsx`): deleting a task or archiving a list offers Undo for `undo_toast_seconds`; one pending entry at a time (`store.undoEntry`), task undo calls `task_restore` with the snapshot, list undo calls `list_unarchive`.

## Icons

One mark on every platform: a slate tile with an H traced as nested contour lines ("The Meander Habit"). `src-tauri/icons/icon.svg` is the tile; `android-bg.svg`/`android-fg.svg` are the Android adaptive layers (the H alone, shrunk into the launcher's safe zone). `npx tauri icon src-tauri/icons/icon-manifest.json` regenerates everything: the desktop/iOS PNGs, `.ico` and `.icns` land in `src-tauri/icons/`, but the Android mipmaps are written straight into the uncommitted `src-tauri/gen/android` - copy its `res/mipmap-*` folders into `src-tauri/icons/android/`, which `scripts/android/build-android.sh` (`sync_launcher_icons`) copies back into the generated project on every build.

## Versioning

`VERSION` at the repo root is the single version source, synced into `package.json`/`src-tauri/tauri.conf.json`/`src-tauri/Cargo.toml` by `scripts/general/bump.sh` (never edit those manifests by hand). Bumping and cutting an actual release are separate concerns per build target - see `docs/windows/ARCHITECTURE.md` for the Windows release flow (`scripts/windows/release.sh`/`release.ps1`, `release.yml`) and `docs/android/` for the Android build.

CI (`ci.yml`, push to main + PRs): frontend lint/typecheck/test/build; rust fmt/clippy(-D warnings)/test - this gate runs regardless of target, since it's exercising the shared frontend and Rust core.

## Tests

367 Rust `#[test]`s inline per module (engine.rs is the biggest); frontend Vitest: pure-logic tests (`src/lib/*.test.ts`, `dateFields.test.ts`) plus component smoke tests with a mocked Tauri IPC (`src/App.smoke.test.tsx`, `QuickAddModal.test.tsx`, `Review.smoke.test.tsx`; per-file `@vitest-environment jsdom`, fixtures in `src/test/fixtures.ts` - `defaultConfig` there mirrors `AppConfig::default()` and the typecheck forces it to track new fields, dispatch in `src/test/tauriMocks.ts`).
