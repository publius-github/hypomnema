# Architecture Reference (shared core)

Maintained map of the codebase shared across every build target (Windows desktop, Android), kept accurate so a new session can build context from this file instead of re-reading the sources. Update the affected section in the same commit whenever a change touches vault layout, config schemas, engine invariants, or module responsibilities. Platform-only concerns live in `docs/windows/ARCHITECTURE.md` and `docs/android/`; product-level decisions live in `docs/general/DECISIONS.md`. Kept in step with the code commit by commit (the version in `VERSION` is the one this file describes).

## Layers

- Rust core (`src-tauri/src/`) owns all data and business logic: SQLite, YAML parsing, the generation engine, watchers, filesystem access for Journal/Notes. Exposed as ~100 `#[tauri::command]`s plus the `vault-updated` event. `lib.rs` is the Tauri builder only (plugins, windows, the handler list); the commands live in `cmd_vault.rs` (vault selection, settings, backups), `cmd_tasks.rs` (lists, groups, tasks, `engine_run`), `cmd_views.rs` (read-only projections), `cmd_rules.rs` (the rule/reminder YAML splice commands and the editable config files), `cmd_journal.rs`, `cmd_kb.rs` (Notes and `open_external`), `cmd_sync.rs` (Google sign-in and sync, passphrase lock, conflict log); `state.rs` holds `AppState`, `with_conn`/`with_vault_root` and the `LockOrRecover` trait (every mutex is taken through `lock_or_recover`, which hands back a poisoned guard instead of panicking - with `panic = "abort"` in release a second panic would be a dead process); `watchers.rs` holds `open_vault`, the three watchers and the export worker; `desktop.rs` the windows/tray/shortcut code with its mobile stubs; `nav_guard.rs` a navigation hook on every window that refuses to leave the app's own origin (`tauri://localhost` / `http(s)://tauri.localhost`, the dev server in a debug build) and hands an `http(s)`/`mailto` link to the browser instead - so a link the frontend fails to intercept cannot replace the app with a web page. This layer is shared as-is across build targets (`#[cfg(desktop)]`/`#[cfg(mobile)]` gate only the small integration bits in `lib.rs` that differ - see `docs/windows/ARCHITECTURE.md`).
- React frontend (`src/`) is presentation only: one Zustand store (`src/store.ts`, `useAppStore`) assembled from slices by concern - `store/vault.ts` (vault, config, defaults, engine runs, the error banner), `store/tasks.ts` (the task/list snapshot, its in-place mutations, habit rates, the status hold), `store/undo.ts` (the Undo toast), `store/navigation.ts` (section, page offsets, the jumps into Notes and Journal), with `store/theme.ts` applying a config to the document - each slice typed against the whole `AppState`, wrapping `invoke` calls; shared view logic sits in hooks and small components both platforms use (`hooks/useEditingTask.ts` - the open task that may leave the snapshot window; `components/DayAmbient.tsx` - a day's reminders and Now/Next schedule lines), ts-rs generated types in `src/bindings/` (regenerated by `cargo test`), Tailwind 4 tokens (all in `src/styles.css`, no JS config: `@theme inline` maps the palette colors - `surface`, `content`, `accent`, `line`... - onto the runtime RGB triplets `--rgb-*` that the `.dark` class and Settings > Appearance set, and `waiting`/`dropped` onto the hex `--hex-*` marks; a second `@theme` and a few base rules keep Tailwind 3's rem line heights, border and placeholder colors, button cursor and date-field height, so the 3 -> 4 move changed no pixel in `npm run e2e:visual`; `input`/`btn-*` are `@utility` classes), CodeMirror 6 editor. Every IPC call goes through `src/lib/ipc.ts`: its `Commands` interface names each `#[tauri::command]` with its camelCased argument object and its result type, and the typed `invoke` there is the only import of `@tauri-apps/api/core`'s invoke outside the tests, so a wrong command name or argument shape fails `tsc`. Adding a command = the Rust fn + `generate_handler!` + a `Commands` entry; `src/lib/ipc.test.ts` fails when the two lists drift. A rejected command carries `error.rs`'s `Error` serialized as `{kind, message, path?}` (`kind` in io/db/config/state/no_vault/sync_conflict; an io failure on a known file is `Error::IoAt`, still `kind: "io"`, whose message names the file - `IoContext::at(path)` on an `io::Result`, used by the atomic write and the Notes/Journal file operations; `NoVault` is its own variant so "nothing selected yet" is distinguishable from a failure), and the frontend turns rejections into banner text only through `errorMessage` in `ipc.ts` (`String(e)` on the object would read "[object Object]"), branching on `errorKind` where it matters. Rejections the UI deliberately keeps out of the banner (cosmetic theme calls, the offline update check, an automatic sync pass, a missing habit rate) still go through `warn` in `src/lib/log.ts`, so a swallowed failure leaves a trace in the WebView console. Same frontend codebase for every target; the phone has its own UI under `src/mobile/` (Frontend notes below).
- Desktop-only chrome - a second always-on-top `capture` window, the system tray, and the global capture shortcut - lives outside this shared core; see `docs/windows/ARCHITECTURE.md` for how it's wired.

## Vault layout (`vault.rs`)

All working files live under `<vault>/.hypomnema/` (like a repo's `.git`). Never join layout paths by hand - use the helpers in `vault.rs` (`work_dir`, `config_dir`, `settings_file`, `synced_file`, `db_path`, `tasks_dir`).

```
<vault>/
  journal/<YYYY>/<YYYY-MM-DD>.md   # journal entries
  .trash/                          # Notes deletes, pruned after 30 days; never synced
  .hypomnemaignore                 # gitignore-like filter for the Notes tree
  .hypomnemasyncignore             # same syntax: paths sync leaves on this device (itself synced)
  <user notes>                     # KB root = vault root unless config.kb_path names a folder that exists here
  .hypomnema/
    app.db (+wal/shm)              # WAL mode, migrations in db.rs (20 entries)
    settings/app.yml               # AppConfig minus the synced parts, per device; SQLite `settings` is a mirror
    config/                        # user YAML configs; a fresh vault gets the starter rules (`CONFIG_STARTERS`), a vault in use a commented sample for a file it lacks (`CONFIG_SAMPLES`)
      recurring.yml scheduled.yml birthdays.yml
      weekly-focus.yml day-reminders.yml day-schedule.yml
      colors.yml                   # the color scheme (config::COLOR_KEYS), synced so every device matches; absent = defaults
      shared.yml                   # rules every device must agree on (config::SHARED_KEYS): retention, catch-up, cadence thresholds, cleanup, capture list, rate inputs
      templates/journal.md
      <subfolder>/*.yml            # "packs": merged into recurring/scheduled/birthdays by top-level key
    tasks/                         # two-way Markdown task mirror + agenda.md + read-only today.md (tasks_mirror.rs)
    state/                         # app-written text state (state_export.rs): *.jsonl DB snapshot
      mirror-base/                 # last-exported mirror copies: the import's merge base
    backups/db/ backups/config/    # daily VACUUM INTO + pre-rewrite config copies (backup.rs)
```

The only state outside the vault is `vault-path.txt` in the OS app-config dir. `migrate_layout` moves pre-0.32 flat vaults into `.hypomnema/` (resumable, step-by-step). All file writes go through `write_atomic` / `write_atomic_bytes` (tmp, `sync_all`, rename) - sync's downloads and merges included; a crash leaves at most a `.<name>.<pid>-<seq>.tmp` staging file (`vault::is_staging_file`), which the Notes tree hides and sync never ships.

## UI sections

Order configurable via `config.section_order`; Settings always last. The list panels (dashboard list zone and the Lists page) render `orderPanel` items, in one of two shapes chosen by `config.lists_group_display`: **folded** (the default) puts ungrouped lists on the panel as columns plus one tile per group (`GroupColumn`), and **flat** gives every list its own column whatever group it is in, with the group's name as a clickable chip on the column header (the chip drills into the group view) and no group tiles at all. A group tile is a member-list index with open counts over its own + List / + Existing pair (create a list straight into the group, or move an existing one in); ⋯ - and a double-click on the tile's free space - opens `GroupModal` (rename, color, membership checkboxes sorted by name, delete-with-release), and the tile is a drop target. Groups are created via the rail's + New group; the All-lists index lists groups with a ▸ marker (`indexRows` in `src/lib/tasks.ts` builds it, `components/IndexRowLabel.tsx` draws a row on both panels: a top-level list starts at the left edge where a group's ▸ stands, members hang one step past the group's name): the index keeps the folded shape whatever the panel does, so under **flat** a group still gets its row with its member lists indented beneath it - the panel has spread them out, and the index is then the only place left that says who belongs together. A group row jumps to its tile when there is one, and to its first member (listed right under it) when there is not (flat) - the index only ever scrolls or pages, it never opens a group view; that is the group chip's and the tile's job. Clicking a group tile (header or any row) switches the whole panel into that group's view - its lists as full columns under a `GroupBackBar` (per-view ephemeral state; the bar carries the group's own ⋯ and doubles as the "take this list out" drop target); a click on a member row also pages/scrolls to that list and flashes it with the same accent ring the index jump uses, and the mouse's back button (button 3) leaves the view. Inside the view the rail's index shows the group's lists ("Group lists"), + New list creates the list directly in the group, + Existing list moves one in, and + New group hides - groups do not nest. Membership is also a drag: a list column's header grip drags `listmove:<id>`, and `components/taskDnd.ts` turns a drop on a group tile (`group:<id>`) or on the back bar (`group:none`) into a `list_set_group` call - the same DndContext as the task cards, told apart by the id prefix. Besides the combined Dashboard there are two focused variants: **Lists** (every list in a wrapping grid, `lists_page_columns`, rows optionally height-aligned via `lists_page_align_rows`, a Lists column count and the Groups folded/flat switch in the header, in the dashboard's order - the same `lists_group_display` the dashboard header also carries, put where the panel it reshapes is; it hides inside a group view, where the shape does not apply, and a sticky right rail like the dashboard list zone's: the New list button over the All-lists index, which scrolls a column into view - `scroll-mt-4` keeps it a page-padding below the top edge so the ring is not cut off - and flashes it with an accent ring) and **Days** (the day grid at full height, no list zone; its own `days_today_only` toggle and `days_page_columns` count). Every day and list column, on all three pages, renders its tasks as one look - flush rows split by hairlines: a `TaskCard` row is transparent - no frame, fill, rounding or shadow; only the drag overlay keeps a framed card - and the column itself takes the card fill `bg-surface-alt`, so rows and gaps share one work surface the theme contrasts against the page; the section plates grow to `list_view_plate_scale` % of their size (default 100, the plain plate) - label font and padding together (`listViewPlateStyle` in `src/lib/tasks.ts`), so the text stays in proportion to the plate - and the first row of every block also takes the hairline above it (`lineAbove`) so a block opened by a gap is framed on both sides. Every break is whole separator stripes (`components/GapFill.tsx`, also used between {Category} blocks in the list dialog): one stripe is `list_gap_stripe` % of a single-line row's height (`listGapStripe`, follows `ui_font_size`), 1 stripe between category blocks, 2 between sections (cadence groups; the priority block and the backlog), 3 into the closed blocks (Postponed / Done, waiting / Done / Dropped - before the first one shown) and 2 between those blocks (`LIST_GAP_STRIPES`; `layout` in `hooks/useColumnSections.ts` turns a closed block that follows another one into a section break). A break is plain space - there is no band in it. On top of the stripes sit a few toggles in the same group, all on by default (`components/ColumnSection.tsx`, shared by `DayColumn`, `ListColumn` and the phone's `Sections`) - this flat look is the only one, there is no framed-panel mode: `row_hairlines` draws the line under every row; `category_headers` names a category block once over its first row in bold at the task text size (`ColumnRow.header`, in the block's chip hue) and the rows drop that chip - the {Category} one, else the list one (`labelInHeader`); `section_plate_count` adds `· N` to the plate (`done/total` when closed tasks stay inline); `section_plate_sticky` pins the plate to the top of its scrolling column; any plate is a fold toggle, by section key so a fold applies to every column, and the fold is remembered in `config.folded_sections` (default: Done and Dropped folded) - there is no fold setting; `closed_row_opacity` fades a closed row's text, chips and badges - not its status box (`.closed-dim` in `src/styles.css`). The plate label is bold, in its own capitalization, at the task text size (14px) at 100% scale; list and group names show as typed, never uppercased. All three views end their header with the same + Task quick-add button at the far right, and share the store snapshot - whose window spans the widest of the day grids, so widening one page never leaves it empty - and the drag-and-drop wiring (`components/taskDnd.ts`). The Dashboard and Days headers carry a date picker that jumps the grid to any date; the Dashboard header also holds the list zone's Lists count (`list_columns`), the Groups Folded/Flat switch and its Days count - Days last, so it stands where the Days page has it. Every page header's view controls go through `components/HeaderControls.tsx` (`HeaderControls` + `HeaderSelect`): one gap between controls and before + Task, one label-to-dropdown gap, and the same names on every page (the Lists page's column count is "Lists", like the dashboard's). Every ‹ / › that steps a view by a period (day grid, Journal day, Calendar and History month, Review week) is `components/NavArrow.tsx`, one look for one function. The app's `<main>` scroller reserves its scrollbar lane (`scrollbar-gutter: stable`), so a page that grows a scrollbar keeps its header controls where a page without one has them. Rail also has Search (Ctrl/Cmd+K), Sync (runs the engine and, while a Google account is signed in, a Drive pass right after; under it the last pass's day and time from `sync_standing` - refreshed on every `sync-status` end, so scheduler passes move it too - red with the error in the tooltip when that pass failed), About. The theme lives in Settings > Appearance only. `config.section_hidden` takes sections off the rail entirely (Settings > Pages > Left bar, next to the order arrows): Settings itself never hides, Ctrl/Cmd+1..9 follow what the rail actually shows, and standing in a section that is being hidden steps the window to the first one still shown.

- **Dashboard** - day grid (`grid_columns`, paged; the count is set by the header's Days dropdown, like the Days page, and has no Settings control) over list-zone backlog columns (paged, split draggable); the list dialog (⋯ on a column, or double-click on the column's free space) manages name/color/description/type (todo queue vs persistent checklist, with Check all / Uncheck all for checklists; the phone's inline list settings carry the same controls) plus the list's group, and the backlog itself (add, check off, star, delete, open a task with its subtasks); dnd-kit drag between days/lists; a dated manual list task stays in its list column always (any date, with a date chip - `tasks_snapshot` includes manual list tasks unconditionally), shows on its day column under Exact date wearing the scheduled-style date label and the exact-date color (isListExact in src/lib/tasks.ts; inside the list the stripe stays list-colored unless `list_exact_stripe` and the chip color follows `list_date_chip_color`), and is listed read-only in Upcoming > Scheduled - one row everywhere; weekly focus + day reminders from `dashboard_context`.
- **Upcoming** - sub-tabs Scheduled / Birthdays / Recurring (`views::recurring_list` adds each rule's `next_occurrence` after now, which only the phone orders by); CRUD writes back into the YAML files (comment-preserving splice in `config_files.rs`; only a missing file starts empty - one that cannot be read, a lock or bytes that are not UTF-8, refuses the write instead of being replaced by the new item). Scheduled events and birthdays are edited by value (`original`); recurring rules by index plus the `original` rule the editor opened on, refused when the file changed under the editor (a sync pass, an edit in Notes) so the index would hit another rule. A materialized scheduled event stays listed until its task is done or deleted.
- **Reminders** - the three ambient config files that feed the day columns, in sub-tabs Weekly focus / Day reminders / Day schedule, over a "Right now" summary (this week's phrase, today's reminders, the current and next block). Same index-plus-`original` splice CRUD as Upcoming (`reminders_overview` + `focus_phrase_*`, `day_reminder_*`, `schedule_block_*`); these files have no packs, so file order is a stable key.
- **Calendar** - month grid: real tasks + read-only projections from `views::calendar_outlook`, per-cadence horizons. The day list groups a day's tasks by category ({X} title prefix, else the list name) and wears the same chips as the cards. Real tasks are interactive: a day-list row drags onto any month cell to reschedule (its own local DndContext, ids `caltask:`/`calday:`; selection follows the drop), a row click opens the task dialog, and the QuickAdd under the list adds a task on the selected day. Projections stay read-only.
- **History** - month completion stats, per-rule daily streaks (each with a strip of its newest `streak_strip_days` instances as done / waiting / not-done marks, `DailyStreak::recent`), completed tasks by day; bounded by retention pruning.
- **Review** (section id `review`) - weekly review over an ISO week (offset navigation, 0 = current): the week's focus phrase, stat tiles (done/past with rate, per-origin, still-open, dropped), Completed grouped by day with a Dropped, not done group under it next to Still open (rows open the task dialog; Still-open rows carry a hover action strip - manual tasks: Next wk (`nextWeekTarget` in `src/lib/tasks.ts`: Monday of the following week, clamped to tomorrow for past weeks), Backlog (clear date, keep list, Inbox via `inbox_list` when listless), Done, Drop, Delete with Undo; generated tasks get only Done/Drop/Delete since their date and list are rule-owned), and a Next week panel (next week's focus, real tasks + `calendar_outlook` projections by day). Composes existing commands only (`tasks_snapshot`, `calendar_outlook`, `dashboard_context` - which pins the asked week's focus phrase, deterministic cycle so harmless); "Weekly note" jumps to the Journal on the week's last day.
- **Journal** - one Markdown entry per date, template-seeded (`{{date}}`), file created on first save. The default template (`DEFAULT_TEMPLATE` in `journal.rs`) is a short evening review - a Mood/Energy line, Went well, Could be better, Learned, Grateful for, Tomorrow's one thing; a vault still holding the previous default word for word is moved to the current one, an edited template is never touched. The header carries the same day stepper as the Dashboard and Days headers - ‹ › (`NavArrow`, also Alt+←/→), the date picker (`DatePick` from `components/DateJump.tsx`) and Back to today when away from it - then names the weekday; the sidebar has no Today button or date field of its own; under it `journal/DayTasks.tsx` lists the day's tasks from `tasks_snapshot` (gated by `journal_day_tasks`, rows open the task dialog); the sidebar index (`journal/EntryList.tsx`) folds by year with month headings and lists the entries written on this calendar day in earlier years ("On this day").
- **Notes** (section id `kb`) - file tree over the KB root - the vault itself until `kb_path` is set, on the desktop as on the phone (the sidebar footer's "Use another folder" / "Change folder" sets it) - (multi-select with Ctrl/Shift, F2 rename, Delete, Ctrl+C/X/V copy-cut-paste via `kb_copy`/`kb_rename`, drag-and-drop onto a folder row or the root area, right-click menu with the same actions plus new note/folder, "Show in file manager" (`kb_reveal`) and "Copy absolute path" (`kb_abs_path`); folders are created with `kb_mkdir` from the header button, a folder row's button, or the menu), editor (YAML colored per the VS Code Dark+/Light+ spec via --yaml-* vars, Markdown headings bold and colored but at the text size so no line jumps in height, markdown/YAML linting - squiggles only for Markdown, plus a lint gutter for YAML, Alt+Z toggling word wrap for the session across documents - off, a wide table keeps its Tab-aligned rows and scrolls sideways), content search, wiki `[[links]]` and web/mail URLs (both on Ctrl/Cmd+click; URLs go to the system browser via `open_external`, which only accepts http/https/mailto and never touches a shell), `.trash`, plus a Config group editing the six YAMLs, colors.yml (opens on the scheme in use while the file does not exist yet; only color keys pass validation) + journal template with save-time validation. A collapsible Backlinks strip under the editor lists notes whose `[[wiki links]]` point at the open note plus unlinked plain-text mentions, journal entries (links and mentions via `journal::backlinks`, newest first, the note's own-date entry skipped) and tasks (`tasks::backlinks`, `[[links]]` in title/description only - mentions in short titles are noise); `kb_backlinks` returns the aggregate `BacklinksResult` (walking the files without the vault lock - `state::vault_root`, as `journal_list`/`journal_search` do - so a scan never holds up the database commands), and with the KB rooted at the vault the note scan drops `journal/` hits so the journal scan stays authoritative. Link beats mention per file, mention floor 3 chars, same caps as `kb_search`. A note/journal hit navigates there; a task hit opens the task dialog in place. The section's frontend is split across `src/sections/kb/` (NoteRow tree row, EditorPane, TreeMenu, CreateNoteModal, util) with state staying in `KnowledgeBase.tsx`. New-note dialog completes the .md extension explicitly (Tab); the + on a folder row pre-fills that folder's path. Markdown notes carry a `Created:` / `Last edited:` header the app keeps (`config.notes_timestamps`, `kb.rs`): `kb_write` returns the stamped text, and the editor adopts it through `rebaseStamp` (`kb/util.ts`) - only the head that changed is carried onto whatever was typed while the save ran - while `MarkdownEditor` applies an outside value as a minimal diff kept out of the undo history and not echoed back as an edit; a note opens with the cursor under the header (`noteBodyOffset`).
- **Settings** - deliberately short: what a person sets up once to make the app theirs. Six tabs (`src/sections/settings/`): General (`GeneralTab.tsx`: theme, fonts and sizes, Left bar = `section_order` + `section_hidden`) / Tasks (`TasksTab.tsx`: Task cards = category block headers, weekday markers, the completion-rate chip (`habit_rate_display` off / alert / always) and its threshold, subtask order, priority overdue and General overdue (`general_overdue`); Day and list columns = `done_display` with `closed_sections_sort_alpha` under Separate (ordered by category then title via `sortClosedAlpha`, in day columns, list columns and the phone's day alike), the day column section order, daily-today-only, `lists_sort_alpha` (list columns and the tasks inside them), list title lines) / Recurring & calendar (cadence buckets, generation, projection horizons) / Capture & alerts (quick capture with the single "Keep running in the tray" switch, system notifications and the lead time) / Data (vault paths; Journal & notes = editor line numbers, note stamps, the Journal's day tasks, the journal template; the Markdown mirror and today.md; backup retention *with* the restore lists; Done tasks cleanup = `retention_days`, `clear_done_list_tasks`, delete-done and archived-list restore - `backups_list`/`backup_restore_db`/`backup_restore_config`) / Sync (`SyncTab.tsx`: Google sign-in and sign-out, standing + Sync now + the mass-deletion guard's "Upload this vault again", the conflict log, a warning when the vault path sits inside a Dropbox / OneDrive / Google Drive client folder, and the one Sync automatically switch). Everything else is in the files, and the page ends with a line linking both into Notes > Config: the color scheme in the synced `config/colors.yml`, fine-tuning (column spacing and plates, opacities, chip size, done-hold and undo timings, snooze and toast lengths, sync cadence and guard, mirror ids/agenda/today days, the streak strip) in this device's `settings/app.yml` - both editable there with validation. Column counts, the Folded/Flat group shape, the two `*_today_only` view modes and the dashboard split are switched on the pages that own them; section folds are remembered from the plates. The map itself is `src/lib/settingsCatalog.ts`: tabs, groups (title, tab, always-open, no-reset, knobs-only) and one entry per `AppConfig` field with its search label; `SettingsGroup` reads title and field list from it by group id, so a tab never repeats a key list, and `settingsCatalog.test.ts` pins the catalog against `AppConfig` - a new field must land in a group or be named in `EXCLUDED_KEYS` with a reason (page-header controls, mobile insets, `IN_COLORS_YML`, `IN_APP_YML`), and no field with "color" in its name may reach the page. A search box over the whole catalog (label, config key, group title, extra terms; every term must match) jumps to the tab and rings the group. The page's column is as wide as Upcoming's (`max-w-4xl`), capped at the window - there is no width setting. A group flagged `advanced` in the catalog (Cadence buckets, Generation, Calendar projections, Markdown mirror) is left off the page until the header's "Show advanced settings" switch (`settings_advanced`, device-local, off by default) is on - unless something in it already differs from its default or a search has landed in it; a tab with nothing else (Recurring & calendar) hides with it under the same three exceptions (`tabShowsWithoutAdvanced`). Every group is a `SettingsGroup`: a group whose fields all sit at their factory defaults (compared against `config_default` via `src/lib/settingsGroups.ts`) renders collapsed behind a "Customize" affordance (manual expand state is ephemeral), a changed one offers "reset" back to those defaults. A group that is *nothing but* knobs is flagged `knobs` in the catalog (Cadence buckets, Calendar projections) and wears a customization checkbox on its own header instead of the collapse link: it is ticked exactly while one of its fields differs from its default, so unticking it is the reset - a checkbox left unticked over changed values would be a lie. Ticking only reveals the fields; it writes nothing. Search still reaches a hidden field: the focus context (`{group}`) opens the group a hit landed in.

## Config files (`config_files.rs`, `config.rs`)

| File | Schema |
| --- | --- |
| `recurring.yml` | `tasks: [{schedule: cron, description, items: ["{List} text"], threshold?: 0-100}]` (`threshold` = the rule's own rate-chip alert, not part of the rule key) |
| `scheduled.yml` | `events: [{date: YYYY-MM-DD, title, time?}]` |
| `birthdays.yml` | `birthdays: [{name, date: MM-DD, year?}]` |
| `weekly-focus.yml` | `rotation: cycle`, `phrases: [..]` (no packs) |
| `day-reminders.yml` | `reminders: [{day_type: workday\|weekend\|mon..sun, text}]` (no packs) |
| `day-schedule.yml` | `blocks: [{from, to, label}]` (no packs); `from`/`to` are zero-padded `HH:MM` on both the read and the write path (`reminders::normalized_blocks`, `config_files::validate_block`) - the whole block model compares clock strings lexicographically, so a hand-written `9:00` would sort after `23:00` and never read as the current block |

Packs: subfolders of `config/` are walked recursively; a `*.yml` file contributes to whichever of the three task sections its top-level keys name. Errors carry the path relative to `config/`. Broken files never wipe state - last valid config stays active, error shows as a banner.

`AppConfig` (117 fields, every one of them filed in `src/lib/settingsCatalog.ts` or excluded there with a reason): dark/light `theme` over a single chrome palette - VS Code Dark+/Light+, baked into the `:root`/`.dark` tokens of `src/styles.css` - with individual accent/surface/panel/border overrides, typography, dashboard layout, task display (cadence colors, closed-section plate colors, done display/hold, `undo_toast_seconds` for the delete/archive Undo toast, `list_task_lines`/`list_dialog_task_lines` title clamps), engine (`retention_days`, `catchup_days`, `cron_ignore_time`), calendar outlook horizons, quick capture (`capture_list` is used on every target; `capture_shortcut`, `tray_icon` and `update_check` are desktop-only - see `docs/windows/ARCHITECTURE.md`), chip look (`chip_font_scale` sizes every category/list/date chip against the text beside it, `category_color_mode` (default `single`) picks how a category chip is colored via `categoryChipColor`: `single` = one shared `category_color`, `varied` = the list's own color else a `CATEGORY_PALETTE` hue hashed from the name - with `category_avoid_cadence_colors` (default on) the palette first drops every hue within 20 degrees of a saturated cadence color, so a chip never wears the color of the Weekly/Monthly plate above it, `alternate` = `category_color_a`/`category_color_b` taking turns by the card's `categoryBlockIndex` - a counter the column runs over its cards in render order, so the turn carries straight through the cadence sections and on into Postponed/Done instead of restarting), `section_order` + `section_hidden`, `lists_group_display` (folded/flat list panels), files (`kb_path`, `notes_timestamps`, `tasks_mirror` + `tasks_mirror_ids`, `backup_keep`), `notify_system` + `notify_lead_minutes` + `notify_toast_seconds`, `journal_day_tasks`, `streak_strip_days`, sync (`sync_auto`, `sync_interval_minutes`, `sync_on_leave` - leave on the phone, quit on the desktop - plus desktop-only `sync_debounce_seconds` and `sync_on_focus`, and `sync_mass_delete_guard_percent`), markdown editor: no color presets - Markdown and YAML always follow the VS Code Dark+/Light+ `--md-*`/`--yaml-*` tokens in `src/styles.css`. Adding a setting = field + default + `sanitized()` clamp + `settings_pairs()` in `config.rs`, deciding whether it is a color (`COLOR_KEYS`, colors.yml) or a per-device field (app.yml), ts-rs regen via `cargo test`, then either a control in the matching Settings group with its entry in `src/lib/settingsCatalog.ts` (the test fails until the field is filed or excluded).

Object colors (cadence stripes and plates, closed-section plates, status marks, chips, list/group dots, the day header, reminder, weekly focus and weekday marker tones) are one hex for both themes and adapt per theme at render (`src/lib/color.ts`): `readable(hex, kind)` keeps the hue and moves only the OKLCH lightness - lighter on dark surfaces, darker on light ones, judged by the actual surface colors so chrome overrides count - just far enough to reach `color_min_contrast` (tenths of a ratio, default 45 = 4.5:1, 0 = off) against both surfaces. `tint` measures text on its own 15% tint (`tintStyle`: plates and chips), `text` plain text, `mark` non-text and stops at 3:1; a color that already reads comes back untouched. `applyTheme` in the store refreshes the context (`setColorContext`) before the render that follows a config change. The default hexes (`AppConfig::default()`, `CATEGORY_PALETTE`) sit at the OKLCH lightness that balances contrast on the dark and light panels, so the adaptation rarely has to move them; neighbouring plates get distinct hues. The text-tone and chrome overrides default to empty, following the theme (the Dark+ secondary text token is lightened to #bfbfbf). None of these colors has a Settings control, on the desktop or the phone. app.yml is per device (sync leaves `settings/` alone), so whatever must match across devices lives in synced files under `config/` instead - `config::SyncedPart`: **Colors** (`COLOR_KEYS`, `colors.yml` - the scheme is the user's, not the screen's) and **Shared** (`SHARED_KEYS`, `shared.yml` - retention, catch-up, `cron_ignore_time`, `clear_done_list_tasks`, `priority_overdue`, `general_overdue`, the cadence bucket thresholds, `capture_list` and the completion-rate inputs: the engine runs on every device, and two devices with different rules would clean up and generate differently; these keep their Settings controls, only the storage moved). `AppConfig::read(settings, config_dir)` lays each synced file over app.yml (synced keys still in an old app.yml are ignored, a missing file means its defaults, a broken one costs only its own fields and is reported per file); `save` writes app.yml without them, and `Vault::save_config` writes a synced file only when one of its values actually changed (backing it up first) - rewriting it on every setting would push this device's copy over a newer synced one. Migration: colors were not seeded (the defaults are the owner's scheme), but `seed_shared` writes shared.yml from an old app.yml once when its rules differ from the defaults, so a tuned retention or catch-up is not lost; a device at the defaults waits for the file to sync in. `load_or_default` then rewrites an app.yml that still carries synced or retired keys. The config watcher reloads the synced files like any config file; a broken one mid-session keeps its previous values. Both are editable in Notes > Config (`config_file_get` serves the values in use while the file does not exist yet; validation rejects keys that belong elsewhere, and app.yml rejects synced keys).

Commands: `config_default` (the frontend's defaults source). There are no settings profiles: the color scheme is one synced file and the rest has defaults worth keeping.

## Engine (`engine.rs`)

Three generators per pass: recurring (cron), scheduled events, birthdays. No separate dailies/priority generator: "daily" is a cadence bucket derived from firing frequency (`cadence_of`); priority is instance-local user state on ANY task (generated included) and survives engine passes.

- **Dedup**: `rule_runs(rule_key, period_key)` ledger, keys via stable FNV-1a 64. Period keys: recurring `YYYY-MM-DDTHH:MM`, scheduled `YYYY-MM-DD`, birthday `<year>`. Card deletes are hard (`task_delete` drops the row and its `rule_runs` entry), so a deleted instance of a live rule regenerates on the next pass; only the delete-done sweep leaves archived tombstones, and `repair_orphaned_period` unblocks today/future periods whose task vanished without one. A generated task's row id is derived from its `(rule_key, period_key)` (`ids.rs`), so two devices generating the same instance mint the same row and the snapshot merge folds them; it is inserted with the untouched stamp (`ids::UNTOUCHED_AT`/`UNTOUCHED_BY`, the epoch and `engine`), so a real edit on the other device - checking it off - always outranks a copy generated later. Carry-over's `dedupe_instances` collapses any remaining twins of one `(rule, period)` (older builds, rows merged in under counted-up ids): the copy someone acted on is kept (done/dropped, then waiting, then postponed, then untouched), then the smallest id - deterministic, so both devices keep the same one - and the loser's subtasks move to it.
- **Catch-up**: window `[now - catchup_days, today + config.horizon_days() - 1]`, where the horizon is the widest day grid any view shows (`max(grid_columns, days_page_columns)`) - the calendar projection starts right after it; missed firings collapse into the single latest one (one overdue copy, not N); `MAX_FIRINGS = 2000` runaway guard (`firings_until`; a daily-cadence rule enumerates from today only, since it discards every pre-today firing anyway; a cron enumeration error keeps the firings found before it, an overflow skips the rule); fresh rules start from today (`rule_seen`, `first_seen`). Where a day starts is `engine::day_start`: midnight, the earlier one when clocks fall back over it, and the first minute after the gap where a DST jump skips midnight. Birthdays are checked for every year the window touches (`window_start.year()..=horizon.year()`), so a birthday missed over New Year still catches up. Scheduled events store their `date`/`time` zero-padded whatever the YAML says (chrono accepts `2026-9-8`; the model compares strings), and a changed `time:` reaches the already-generated instance the way a changed birthday year reaches its title.
- **Reconcile**: removing a rule/item removes ALL its instances - future, today's open, and pre-today done history (nothing lingers in the Calendar); only a copy already acted on today (done, dropped or waiting) survives, so editing a rule (key change) never hides a just-finished task. Missing/comment-only `recurring.yml` is treated as transient (generation may run, reconcile must not).
- **Statuses**: `todo`, `postponed`, `waiting` (done on the user's side, waiting on someone else) are open; `done` and `dropped` (not done, taken off the plan) are closed - SQL spells that as `status IN ('done', 'dropped')` (`tasks::STATUSES`/`is_closed`). Closed tasks are what the list sweep, retention and delete-done remove and what carry-over skips; only `done` is a completion (History, Review rate, streaks), so a recurring instance dropped at review time reads as not done. The checkbox cycles todo -> done -> postponed -> waiting -> todo; dropped is only ever chosen on purpose (the card's ⊘, the task dialog, Review's Drop) and a click brings it back to todo. In the separate done display waiting gets its own "Done, waiting" section between Postponed and Done, and dropped gets "Not done, dropped" after Done (`dropped_plate_color`, neutral gray by default: dropped is a quiet outcome, not an error). The waiting mark takes `config.waiting_color` through the `--hex-waiting` var, exposed to Tailwind as the `waiting` color; the dropped mark likewise takes `config.dropped_color` through `--hex-dropped` / `dropped`. `done_display` defaults to `separate`.
- **Carry-over**: open pre-today tasks (postponed and waiting included) move to today with the overdue mark (priority included unless `priority_overdue` is off; a General task - no rule cadence, not a scheduled event, birthday or dated list task, matching `cadenceKeyOf` - unless `general_overdue` is off; the `OVERDUE_EXEMPT` SQL in `engine.rs` decides both, and the same pass clears a mark already given once a switch goes off); dailies are exempt and get rehomed to their firing day; at most one open overdue copy per rule - a waiting copy is never the one collapsed away.
- **Done ahead of time**: a task checked off on a future day column keeps that day. Both the list sweep (`clear_done_list_tasks`) and retention pruning skip a done task whose `scheduled_date` is today or later, so it disappears only on the rollover after its own day.
- **Pass phases** (one IMMEDIATE transaction): generate x3 -> carry-over -> retention prune -> clear done list-backlog tasks (`clear_done_list_tasks`; checklist-kind lists are exempt from both this sweep and retention - their checked items are kept state) -> purge archived rows (>24h, except pending delete-done tombstones) -> trim old `rule_runs` -> dedupe errors. Returns `EngineOutcome{generated, carried_over, removed, pruned, errors}`.

## Core modules

- `applog.rs` - the per-device diagnostic log `<app-config-dir>/hypomnema.log` (outside the vault: never synced, survives a broken vault). `init` in setup points it at the file and installs the panic hook (which falls back to a plain append when the panic happened inside a log write, rather than deadlocking). Writers: panics, background failures with no banner (state snapshot export, the daily backup, automatic sync passes, tray/shortcut/device-id setup, navigations `nav_guard.rs` refused), and the frontend through `log_write` (every rejected command but `no_vault` from `lib/ipc.ts` `invoke`, `lib/log.ts` `warn`, window errors and unhandled rejections, the render error boundary). Rotates to `hypomnema.log.1` past `log_max_kb` (app.yml-only, applied by `applog::set_max_kb` wherever the tray is resynced from a config). `diagnostics` returns version, OS and the last 16 KiB of the log as text for the user to copy; `log_reveal` shows the file in the file manager (desktop).
- `ids.rs` - row ids for `tasks`, `lists` and `list_groups` that two devices mint without colliding (the snapshot merge is keyed by `id`, and SQLite's `MAX(id) + 1` hands the same next id to different rows on each device). Every production insert names its id: an engine-generated task gets one derived from `(rule_key, period_key)`, a list or group one derived from its name (two devices creating "Work" get one list), anything else - or a name whose derived id is taken - a random one. Random ids live in `[2^40, 2^51)`, derived in `[2^51, 2^52)`: above any counted-up id of an older vault, below JS's 2^53. Ids carry no order, so "newest" queries sort by `created_at`.
- `tasks.rs` - lists/tasks CRUD; `ensure_inbox` returns the quick-capture list (case-insensitive match over active lists, promotes an auto namesake, else creates manual+favorite); `home_listless` sends a top-level manual task left with neither a day nor a list - which no view, list column or mirror file would show - to that list: `task_create`, `task_update` and `task_restore` (an Undo whose list is gone) all run it, and the store fetches the lists when the answer names one it does not know yet; list names are unique among **active** lists only (partial index `idx_lists_active_name`, migration 015): an archived namesake never blocks a create/rename, an auto list of that name is absorbed into the user list instead (its tasks move over, the auto row goes), a live manual namesake reports "a list named X already exists", and `list_unarchive` refuses a restore whose name is taken. `list_ensure` prefers the active list over an archived namesake. `task_delete` is a hard delete (cascades to subtasks, drops the `rule_runs` row) and returns a `DeletedTasks` snapshot (rows + ledger entry) that `task_restore` puts back - the Undo toast round-trips it through the frontend; original ids are kept while free, and a restore is skipped when the engine already regenerated the same (rule, period) instance. `archived_at` remains only for the delete-done sweep tombstones; lists carry a `favorite` flag (sorts ahead in the list zone) and a `kind` (`todo` | `checklist`, set in the list dialog via `list_set_meta`): a checklist keeps its checked items - the overnight list sweep, retention pruning and the delete-done maintenance sweep all skip its tasks (subtasks included) - its tasks have no postponed state in the UI (the checkbox is a plain todo <-> done toggle; a leftover postponed row still renders and can be reset), and `list_set_all_statuses` checks/unchecks the whole list at once (top-level tasks plus their subtasks - the Check all / Uncheck all bulk actions). The `overdue` flag survives the status cycle (done does not clear it; the UI just hides it on done cards). List groups (`list_groups` table, `groups_all`/`group_create`/`group_set_meta`/`group_delete`/`list_set_group`): a group is a named folder in the list panel - the panel shows the group tile (member lists with open counts, drill-in per column), a grouped list (`lists.group_id`) never renders as its own panel column; deleting a group releases its members (ON DELETE SET NULL, which also restamps them for sync); group names are unique among groups; the snapshot carries them in `list_groups.jsonl` (stamped merge like lists.jsonl; a restore drops a membership whose group is gone from a merged snapshot rather than failing the open).
- `tasks_mirror.rs` - Markdown mirror of tasks: a list's file header carries its group as an editable `<!-- group: Name -->` line (a group is otherwise invisible from the vault; editing the line moves the list and creates the group when the name is new, an empty name releases it, and a file with no such line at all - an older export, a hand-made file - leaves the membership alone; it merges against the base like any other field). One file per list + `scheduled.md` (manual tasks, full authority) + `agenda.md` (generated instances from today onward, gated by `config.tasks_mirror_agenda`: status/priority/time sync back, title/date edits do not, absence never deletes, an id-less line creates a manual task on that day - the phone-over-file-sync surface) + `today.md` (gated by `config.tasks_mirror_today`, covering `tasks_mirror_today_days` days: a read-only phone-readable day sheet - focus phrase, reminders, schedule blocks, Overdue, tasks grouped by category with no `^id` keys; its marker makes the import a no-op, the sweep removes it when the flag turns off, and it gets no mirror-base copy). The optional files ride `ExportOptions`; `export` takes the config dir for `dashboard_context`. Per-line `^<id>` sync keys (omitted with `config.tasks_mirror_ids` off, and a line is then matched to its task by title; in the agenda the date joins the match key); `[x]` done, `[z]` postponed, `[xz]` done but waiting, `[zz]` dropped (`[>]` from older versions still parses); marker first line; gated by `config.tasks_mirror`; folder watcher imports outside edits. Every export also snapshots the files into `state/mirror-base/`; an export from a command (`ExportOptions::preserve_pending`) leaves a file alone when its disk copy differs from that base - an outside edit the watcher has not imported yet - while the watcher's own export (having just imported the disk) rewrites it, and the watcher runs one pass right after it starts so an edit made while the app was closed gets imported instead of overwritten; the stale-file sweep never removes a file whose import just failed (a conflicted copy keeps its lines until the user deals with it); a stem of the export's own collision form `Name (id)` is not read as a rename; with ids off a trailing ` ^N` is title text, not a key. The import is a three-way merge against that base: a field applies only when the file changed it, absence deletes only tasks the base knew, a stale line of an app-side-deleted task is not resurrected, and a scheduled/agenda marker under a wrong file name (a sync "conflicted copy") is rejected instead of double-imported. Without a base the file wins wholesale.
- `journal.rs` - entry open/save/list/search, template at `config/templates/journal.md`.
- **Editor saves merge, never overwrite** (`text_merge.rs`): an editor saves the whole text it shows, read some time ago, so `journal_save` and `kb_write` take a `base` - the on-disk text the editor's text derives from - and `reconcile_save` three-way merges the save with whatever changed on disk since (a sync pass merging the other device's edit, another program). Same lines changed on both sides: the editor's text wins and the disk version is kept as `<name> (conflicted copy edited elsewhere <date>)`, logged under "to review" (`sync_conflicts::log_kept_aside`). Conflicted copies are resolved from the conflict list (`components/ConflictReview.tsx`): `sync_conflict_diff` shows the file against its copy line by line, `sync_conflict_resolve` keeps the file or puts the copy's text in it and moves the copy to the vault's `.trash/` (both refuse a pair that is not a file and its own conflicted copy beside it); the Notes tree marks conflicted copies with a badge. Both commands return the text now on disk; the editors (desktop Journal/Notes, phone Journal/Notes) settle onto it with `settleSave` (`sections/kb/util.ts`: adopt it when nothing was typed meanwhile, carry the typing over with `rebaseStamp`, else keep the typing and measure the next save against what was sent), and an editor with no unsaved typing rereads its file on `kb-updated` / `vault-updated`. `text_merge::merge3` (diffy, CRLF compared as LF, result in ours' line endings) is also the sync pass's line merge; both callers go through `merge_file`, which takes a Markdown note's Created / Last edited header (`kb::split_stamps`) off all three versions and merges it on its own (earliest Created, latest Last edited) - otherwise every save on both devices rewrites that line and no two-device edit of a note would ever merge. Saves and the sync pass's apply of a download hold `text_merge::user_file_lock` across their read-merge-write, so neither writes over a change the other made between its read and its write. All four editors share one autosave, `hooks/useAutosave.ts` (debounce `AUTOSAVE_DELAY_MS`: 800 ms desktop, 1200 ms phone; each editor keeps only its own save call and base handling): it runs saves one at a time (`serialSaves` in `sections/kb/util.ts` - two saves in flight with one base would meet each other on disk as a clash), numbers every keystroke so a landing save marks the editor saved only when nothing was typed after it, keeps a failed save for the next flush - and `flush()` then answers false, so opening another note, entry or day (desktop and phone) stays on the unsaved one instead of letting the next keystroke replace it (a delete of its file lets go) - leaves the editor dirty when a save refuses its edit (invalid YAML), drops the waiting edit of a file being renamed or deleted, and saves what is still waiting on unmount; `components/SaveIndicator.tsx` shows Saved / Saving... / Not saved · Retry.
- `starter.rs` - what every brand-new vault starts with in its database: Home and Work lists with a few tasks (one with a description and subtasks) and one task on today. `Vault::open` reports `fresh` (no `app.db` and no `state/tasks.jsonl` before the open: a vault nobody has used on any device), the opener (`watchers::open_vault`) seeds the starter lists then and requests an export; the config files' starter rules - a daily/weekly/monthly rule, a birthday, two focus phrases, a workday and a weekend reminder, two schedule blocks - are `vault::CONFIG_STARTERS`, written by `Vault::open` itself, `scheduled.yml` excepted (a made-up date would only go stale, so it stays a commented sample). `is_untouched_sample` knows starters and samples alike, so a device that joins a Drive vault from a fresh local one lets the other device's config win instead of keeping a conflicted copy. All of it goes through the same functions user edits use.
- `example.rs` - the welcome screen's example vault: `ensure_empty` (the target must be empty or missing, so the example never mixes into real notes) and `seed`, which adds to the starter content what a vault of one's own should not be given - two linked notes, today's journal entry, a scheduled event ten days out, two tasks that point at the notes and a `[[Ideas]]` link in the starter's outline task. `vault_create_example` opens the folder as a vault (the opener seeds the starter), seeds the example and remembers it; the desktop `VaultPicker` offers it as "Try it with an example" beside "Select vault folder".
- `kb.rs` - Notes FS layer. The root is the vault itself unless `config.kb_path` names a directory that exists **on this device**; a path from another machine falls back to the vault - `settings/` never syncs, but a vault copied wholesale from a desktop carries its app.yml along, and `D:\Projects\...` means nothing on a phone. The phone's fallback banner carries a "Use the vault" button that clears `kb_path` locally - settings never sync, so adopting the vault on the phone leaves the desktop's path alone. `kb_status` reports the effective root and whether it is a fallback, so a desktop whose external notes drive is unplugged is told rather than quietly writing into the vault. `write` stamps Markdown notes with the `Created:` / `Last edited:` header when `kb_write` asks it to (setting on, `.md`, not a `journal/` entry of a vault-rooted tree): `stamp_note` keeps the header at the top (inside a frontmatter block when there is one), finds it within the first lines so text typed above it never duplicates it, takes Created from the incoming text, then the disk copy, then the file's birth time, and moves Last edited only when the text under the header changed - a no-op save is not rewritten, and a hand-corrected Last edited wins like a hand-corrected Created does. A case-only rename (`note.md` -> `Note.md`) is allowed on a case-insensitive filesystem. `resolve()` blocks path traversal; `guard_work_dir` refuses to delete, move or rename `.hypomnema/` or anything in it outside `config/` (with the tree rooted at the vault, one Delete would otherwise trash the open database); `copy_into` refuses to paste a folder into itself; renaming a folder never appends the old "extension" (`proj.old` -> `proj`); `.hypomnemaignore` glob filter; trash + 30-day prune of the entries `delete` put there (the `YYYYMMDD-HHMMSS-` prefix; anything else in `.trash`, such as another app's trash in the same folder, is never touched) (the trash shows in the tree like any folder, hidden only by the ignore file). `kb_reveal` (Show in file manager) writes its Windows command line with `raw_arg`: explorer.exe does not parse arguments the way `CommandLineToArgvW` does, so Rust's own quoting made it open a default folder instead of the note whenever the path held a space.
- `reminders.rs` - `dashboard_context` (weekly focus, ISO-week pinned via `weekly_focus_state`; day-type reminders; schedule blocks) and `overview` behind the Reminders section.
- `views.rs` - read-only projections: upcoming, birthdays, recurring list, calendar outlook, daily streaks, cron weekday labels, habit rates. `calendar_outlook(from, to)` takes **`to` inclusive**, unlike `tasks_snapshot`'s exclusive `endDate` - a caller that hands both the same bound projects one day too many. `habit_rates` (command of the same name) gives each recurring rule item (`rule_key`) its completion rate over the newest `habit_rate_window` settled instances: done and waiting count as done, dropped as not done, a daily instance still open after its day as not done (dailies never carry over); an open instance of any other cadence is live overdue work and waits. Items under `habit_rate_min_instances` get no rate. The threshold is the rule's own `threshold:` else `habit_rate_threshold`, and `alert` = rate below it (the percent is rounded down, so a shown 80% never alerts at 80). The store keeps them in `habitRates` (reloaded by `refresh`, by a status change on a recurring task in `updateTask`, and by a change of the three computing settings); `TaskCard` shows `Rate: N%` after the overdue mark under `habit_rate_display` (`alert` - the default - shows it only while alerting, `always`, `off`), tinted with `habit_rate_alert_color` when alerting; the `[DOW]` marker in its default muted tone fades to `dow_label_opacity` % (a picked `dow_label_color` shows at full strength), and in a list of days (`MON,SAT`) the day the instance fired on (`origin_date`, else `scheduled_date`) is bold (`dowLabelParts` in `src/lib/tasks.ts`, drawn by `components/DowLabelText.tsx` on the card and the phone row alike); the Priority and Overdue badges are bold at the task text size, not the chip size; the Recurring section's add/edit forms set the per-rule threshold (empty = default).
- `state_export.rs` - makes app.db a disposable cache: every mirror-export trigger also writes a full JSONL snapshot of the database's authoritative state under `state/` (tasks with ids/provenance/tombstones, lists, list groups, `rule_runs`, `rule_seen`, `weekly_focus_state`; always on - sync ships it), and `Vault::open` restores from it whenever the database holds none of that state (`db_is_empty`) - a vault without app.db, but also one whose earlier restore failed or was cut short and left an empty app.db behind - before anything can export the empty database over it (a broken snapshot aborts the open for the same reason, and the next open tries again - every JSONL file that exists must parse, only a missing side file reads as empty). The export reads all six tables in one transaction (`snapshot`, written by `write`), so a list created between two reads cannot leave a task pointing at a list the files lack. Every row struct denies unknown fields, and `check_readable` (used by sync on a downloaded file before anything is applied) refuses a field, task status or list kind this build does not know with "written by a newer version ... update the app on this device": an older build reading past a newer field would drop it on its next export, and the record merge would take it from every device. An app.db SQLite cannot read (`NOTADB`/`CORRUPT`) is renamed to `app.db.unreadable-<ts>` (with its WAL/SHM) and rebuilt from the snapshot when one exists; without a snapshot the open fails and the file is left alone. The restore drops a dangling `list_id`/`parent_task_id`/`group_id` reference rather than failing on the FK: a record-wise merge legitimately keeps a row whose parent the other device hard-deleted. Deleting app.db is the supported way to force a rebuild; ids are preserved so the mirror's `^id` keys stay valid. Two active lists (or two groups) of one name in a snapshot - created on two devices under counted-up ids before either synced - restore as one: the smaller id stands and the other's members are remapped to it, rather than the restore failing on the unique active-name index.
- `backup.rs` - daily DB snapshot (`VACUUM INTO`) + pre-rewrite config backups, rotation by `backup_keep`, best effort; `overview`/`list_db_backups`/`list_config_backups` back the Data tab's restore list. The daily snapshot is taken at vault open and in `engine_run` (start and every day rollover), so a desktop that stays in the tray still gets one a day. `restore_db_backup` swaps app.db from a snapshot (copied to `app.db.restoring` and renamed over it, so a copy cut short never leaves a truncated database; caller must close the live connection first; the file being replaced is itself copied aside as `pre-restore-app-<ts>.db` - not `app-` prefixed, so the daily rotation by `backup_keep` never counts it - and its stale `-wal`/`-shm` siblings are dropped) and `restore_config_backup` puts one config/settings file back in place (also backing up the file it overwrites) - every restore backs up what it's about to replace first, so a restore is itself undoable.
- `vault_export.rs` - the vault as one zip archive (`vault_export` command): everything but `app.db` and its WAL/shm, `backups/`, `.trash/` and in-flight `.tmp` files, with the `state/` snapshot refreshed first so the database restores as of now. On Android the archive goes to `Download/Hypomnema/` through `MediaStore` (`android_storage::save_to_downloads`, no permission needed on Android 10+), the one place a file outlives an uninstall when the vault sits in the app-specific folder; elsewhere the command writes to the `target` path it is given (no desktop UI yet).
- `db.rs` - migrations (20), refuses a newer-than-known `user_version`; `pending_upgrade_from` tells `Vault::open` an existing database is about to be upgraded, and the open first snapshots it with `backup::backup_db_before_migration` to `backups/db/pre-upgrade-<ts>-v<from>.db` (rotated by `backup_keep` among its own kind, listed in the restore list as "before upgrade ..."; skipped only when `backup_keep` is 0) - unlike the daily snapshot this is not best effort: if the copy fails the open fails and the schema stays untouched; `mirror_settings`. Migration 020 recreates the six stamp triggers with millisecond `updated_at` (`%f`): whole seconds made two devices' edits of a row within one second a tie. Migration 019 rebuilds `tasks` to widen the status CHECK with `waiting`/`dropped` (self-reference named `tasks_new` during the copy so the DROP cascades into nothing; indexes and stamp triggers recreated, stamps preserved). Migration 017 adds `lists.kind` (`todo` | `checklist`); 018 adds `list_groups` (stamped by the same trigger pattern as migration 016) and `lists.group_id` (FK, ON DELETE SET NULL). Migration 016 adds `updated_at`/`updated_by` to `tasks` and `lists` and stamps them from **triggers**, not from the ~70 call sites that write those tables: a missed site would not fail a build, it would make a changed row look untouched and hand the next cross-device merge to the wrong side. Both triggers stand aside when a statement supplies its own values, which is what lets `state_export::restore` put a snapshot back with the stamps it was taken with instead of relabelling the vault as "changed here, now". `set_device_id` records the writing device per connection (`sync_device`), so the same vault opened on another machine stamps with that machine's id.
- `crypto.rs` / `secret_store.rs` - Argon2id + AES-256-GCM (pure Rust, so the Android cross-compile stays free of native deps) behind an optional device passphrase. It covers one file, `google.json`, and on the shipped platforms that file no longer exists: on Windows the Google refresh token - a standing grant to the app's Drive folder that outlives every access token - is a generic credential in Credential Manager (`google_link::token_vault`, `keyring-core` + `windows-native-keyring-store`, entry `<identifier>.Hypomnema` with local persistence; a `google.json` left by an older build is moved in on the first read and deleted), and the phone stores none (Play services holds its grant), so its Settings only offer to remove a passphrase left from an older build, and nothing in either UI sets one. Other desktops (not shipped) still keep the file through `secret_store.rs`; `cargo test` runs the credential-store path against keyring-core's mock store. Enabling seals what is already on disk, disabling requires the passphrase, and the unlocked passphrase lives in memory for the session and nowhere else. **Not** vault encryption - the vault is plain files each device reads directly and sync moves as-is (`docs/general/DECISIONS.md`).
- `device.rs` - this install's opaque device id (the `updated_by` half), kept in the app's private config dir and never in the vault: a vault synced to a second machine must not carry the first machine's identity, or two devices' edits become indistinguishable.
- Sync (Google Drive is the one backend): `sync_paths.rs` is the whitelist of what travels (only paths whose every segment is a portable plain name - no empty, `.`/`..`, trailing-dot or trailing-space segment, no `\`, `:` or control character, no Windows device name such as `CON` or `nul.md` - since remote listings are joined onto the vault folder and must never reach outside it; then everything outside `.hypomnema/` except `.trash/` at any depth, staging files and the user's `.hypomnemasyncignore` patterns - a folder rule covers everything below it, read at the start of every pass, push and pull and handed down explicitly rather than kept process-wide; inside `.hypomnema/` only `state/` minus `mirror-base/`, and `config/`); `sync_provider.rs` is the backend-agnostic trait (list changes since a cursor, read/write/delete a file guarded by an opaque change marker, `Error::SyncConflict` on a stale write or a guarded delete of a file that moved on); `sync_merge.rs` is the per-field last-writer-wins merge with a conflicts list plus the `rule_runs` set union; `sync_state.rs` applies that merge to the JSONL snapshot record by record, giving each file the merge its content deserves (`tasks`/`lists` by their `updated_at`/`updated_by` stamps - compared as instants, since migration 020 stamps milliseconds while older rows carry whole seconds, a true tie going to the larger device id so both devices pick the same side - `rule_runs` as a set union, `rule_seen` keeping the earliest first-seen so catch-up never re-runs a rule's history, `weekly_focus` keeping this device's pin and logging the other); `sync_cycle.rs` is the full pass - the manifest's revision says whether the remote moved, its hash says whether this device did, and only when both moved does a merge happen (record-wise for the snapshot; for mergeable text - `.md`/`.markdown`/`.txt`/`.yml`/`.yaml`, `.hypomnemaignore` and `.hypomnemasyncignore` - a git-style line-wise three-way merge (`text_merge::merge3`) against the agreed version kept in the sync space's base dir, which every download, upload and pull records for text as for the snapshot, and which a pass seeds for any text still matching its manifest hash; only when both sides changed the same lines, or there is no base or the bytes are not UTF-8, a `(conflicted copy <phone|desktop> <date>)` file beside the original (stepped to `<label> 2`, `3`... rather than overwrite an earlier copy of the day), because merging two people's edits of one line invents a version neither wrote - except a config file this device still holds as the seeded sample (`vault::is_untouched_sample`), which a vault started here before its first sync gives way to the other device's rules without a copy); `sync_conflicts.rs` keeps what those merges had to choose between in a device-local log - each entry that left a conflicted copy records it (`copy`), and `sync_conflicts_list` returns `for_display`: device ids named "this device" / "the other device", entries whose copy still exists marked `open` and sorted first (older entries have their copy parsed out of the text), shown by the shared `components/ConflictList.tsx` on both platforms as "to review"; `sync_bootstrap.rs` holds vault-root detection, the one-way first pull (`pull_vault`, resumable through the manifest; `google_pull_vault` uses it) and the sync spaces, `sync_push.rs` the guarded upload the pass ends with plus `adopt_local_baseline`; `oauth.rs` is the provider-neutral PKCE pair and the `OauthTransport` seam. When a pass changes the snapshot (a byte-identical download does not count) it drops app.db and reopens the vault so the merged JSONL rebuilds the cache through the existing restore path rather than a second write path into SQLite - the old app.db is kept aside until the reopen succeeds, and put back if it does not. Commands keep writing to app.db while the pass is on the network, so before the rebuild `run_pass` exports app.db again and `sync_cycle::fold_local_writes` merges every file that changed since the pass's own export into the merged one (base = the export at the start, record merge as in a pass), then closes the vault under the same lock; the folded file goes up with the next pass. If the rebuild fails, `forget_state_agreement` drops the snapshot files' manifest entries and merge bases: the old database's export will overwrite the merged files, and the next pass must merge it with the remote again (no base keeps every row either side has) instead of uploading it as the newer side. Before applying anything a pass also downloads the snapshot files with a new revision and runs `state_export::check_readable` on them (`prefetch_state_files`) - a snapshot from a newer build stops the pass with nothing changed; an extra Drive copy of a state file that fails the check is kept on the server. A file that cannot be applied is listed under `failed` rather than aborting the pass - including a local file that exists but cannot be read right now (locked by another app, a cloud placeholder offline): only `NotFound` counts as "not here", anything else is a failure, never a cue to write the other side over it. Deletions propagate both ways, distinguished from "never pulled" by the manifest and guarded by the revision this device last saw - an edit on the other end outranks a deletion here, and vice versa. A user file the other device deleted goes to the vault's `.trash/` (`kb::move_to_trash`, the same stamped name and 30-day prune as a Notes delete - the remote keeps no copy), only snapshot files are removed outright. The manifest and the merge base live in the active **sync space** (`sync_bootstrap::space_dir`): `.hypomnema/sync/` itself when no `sync/space` pointer names one, else `sync/spaces/<name>/` - so a different account starts from an empty manifest and its first pass joins (identical files adopted, the rest merged or uploaded) instead of reading another remote's revisions; `sync_reset_space` empties the active space for the same join on purpose. Before applying anything a pass runs the **mass-deletion guard**: with at least 10 synced files, more than `config.sync_mass_delete_guard_percent` (default 30, 100 = off) of them missing from the remote at once (counting only files still shared - a folder put under `.hypomnemasyncignore` after it synced is skipped, not missing) fails the pass with `Error::RemoteWiped` (`kind: "remote_wiped"`) with nothing touched - a wiped remote or another account looks exactly like the other device deleting everything - and both UIs offer "Upload this vault again" (reset the space, then sync). The command half of a pass (engine lock, export, `sync_vault`, `record_pass`, `rebuild_cache`) is `cmd_sync::run_pass`, generic over the provider. `sync_cycle::standing` (the pending count behind `sync_standing` and the scheduler's after-edit trigger) reads the vault's `.hypomnemasyncignore` itself, and a file ignored after it synced is not counted as a deletion waiting to go up; the pass, the push and `adopt_local_baseline` walk the vault through the one `sync_cycle::local_files`. Listings are always full, so a path in the manifest that is absent from one counts as deleted over there even without a tombstone. `SyncProvider::take_duplicates`/`discard_duplicate` cover a backend that allows two files under one path (Drive does): after the incoming phase each extra copy is folded into the local file with no base (state files as a union merge, differing prose as a `(conflicted copy duplicate <date>)` file), the merge goes up with the same pass, and only then is the copy discarded - one with nothing local to merge into is kept for the next pass. `sync_gdrive.rs` implements the trait over Drive v3 in the hidden `appDataFolder` (scope `drive.appdata`) behind a raw `GdriveTransport` seam (request in, any status out; retries 429/5xx/rate-limit 403 in the real `ureq` transport, honouring `Retry-After` up to 60 s; the agent `http_agent`, shared with the OAuth token calls, bounds every phase of a call - 30 s to connect, 120 s for the response headers, 15 min for a whole body - because a pass holds `engine_lock` throughout, and a connection that died silently would otherwise stall the engine, the export worker, the watchers and every later pass until restart): the vault-relative path is the file `name`, the marker is `headRevisionId`, duplicate names keep the earliest `createdTime` (then smallest id) as canonical, a guarded write reads the head revision first and afterwards checks `revisions.list` - another device's revision landed in that window is re-created as a duplicate for the next pass to merge - and a guarded delete is check-then-delete (appdata has no trash). **Google sign-in**: `google_auth.rs` is the desktop OAuth flow - PKCE + `state`, the redirect caught on a `127.0.0.1:<free port>` listener (`wait_for_redirect`, 5 min, cancellable via `google_sign_in_cancel`), the consent page opened with `tauri-plugin-opener`, code/refresh exchange and revoke at `oauth2.googleapis.com`; `CLIENT_ID` is a public constant (the project's own client, overridable at build time with `HYPOMNEMA_GOOGLE_DESKTOP_CLIENT_ID` for a self-build with its own OAuth client), the desktop client secret is compiled in from `HYPOMNEMA_GOOGLE_DESKTOP_CLIENT_SECRET` (`option_env!`, see `docs/windows/ARCHITECTURE.md`) and a build without it reports `available: false`. `google_link.rs` keeps the account (email, name, Drive `permissionId` from `about.get`) in plain `google-account.json` - readable on a locked device - and the tokens in `google.json` through `secret_store` (sealed by the passphrase when one is set; `cmd_sync::secret_files`), refreshing ahead of expiry. **Android sign-in** goes through `src-tauri/plugins/google-auth/` (crate `tauri-plugin-google-auth`, an Android-only dependency registered in `lib.rs`): its Kotlin half (`android/`, tracked in git rather than in the regenerated `gen/android` - Tauri's build scripts add the plugin's Gradle module to `gen/android` themselves) wraps Google Identity Services' `AuthorizationClient` for `drive.appdata` - `authorize` (interactive: account picker + consent through `startIntentSenderForResult`; silent with the stored email pinned via `setAccount`, rejecting with `CONSENT_REQUIRED` when a screen would be needed), `clearToken`, `revoke` - and its Rust half calls it with `run_mobile_plugin` (blocking, so only off the main thread). Play services keeps and refreshes the grant: the phone stores the account file only, no tokens, and `cmd_sync::drive_token` asks the plugin before every pass (desktop: `google_link::valid_access_token`). A token Drive refuses with 401 becomes `Error::SignInExpired` (`kind: "sign_in_expired"`, also the desktop's `invalid_grant`), and on Android it is cleared from Play services' cache so the next pass mints a new one; a pass (and the first pull) on Android also holds the plugin's `keepAlive` for its duration - `SyncKeepAliveService`, a `dataSync` foreground service with a "Syncing with Google Drive" notification - so putting the app away does not freeze it mid-pass (best effort: Android refuses the start for a pass begun from the background); the UI answers that kind with "Sign in again". Commands: `google_status`, `google_sign_in` (blocking work on `spawn_blocking`), `google_sign_in_cancel`, `google_sign_out` (revoke best effort, then forget; the sync space stays, so re-signing the same account resumes), `google_pull_vault` (first run on a device that has no vault yet: when Drive holds one, pull it into `local_vault_dir` under the account's space, open it and adopt the baseline - a pass would instead join the fresh vault's default config files against the real ones and keep both; `null` when Drive is empty, and the caller starts a local vault whose first pass uploads it), and `sync_now` - one Google pass (`SyncSummary`). Pass and pull progress go out as `sync-progress` `(done, total)`. `cmd_sync::google_pass` refuses to start while another runs (`SYNC_RUNNING`), switches the vault to the account's space `gdrive-<permissionId>`, syncs with `VaultRoot("")`, records failures that happen before the pass proper in the standing, and emits `sync-status` (`SyncActivity {running, error}`) at both ends. `sync_scheduler.rs` (started in setup on every platform; on the phone it runs only the after-edit trigger, the other moments being `MobileApp.tsx`'s) is a thread that ticks every 5 s and runs a pass, while a vault is open, the device is signed in and `sync_auto` is on, when one of these is due: start, then every `sync_interval_minutes`; `sync_debounce_seconds` after the last `poke()` (export worker, KB watcher, `journal_save`) *and* only if `standing` counts something pending - so the export after a pass does not start the next one; main-window focus (`sync_on_focus`, at most once a minute); and quit (`RunEvent::Exit`, `sync_on_leave`, only with something pending, waits up to 20 s).
- `watchers.rs` - `open_vault`, `rebuild_cache` (its file half `replace_db_files` keeps the old app.db aside and puts it back when the reopen's restore refuses the snapshot; it leaves the database untouched when the safety copy cannot be made, and when app.db survives the delete - another program holding it open - it reopens it and fails rather than open the old database with no restore), three debounced watchers: `config/`+settings (reload + engine + `vault-updated`), `tasks/` (mirror import), KB root (with the Notes rooted at the vault the recursive watch also sees `.hypomnema/`, so `is_work_dir_event` drops events whose every path runs through the work dir - the database, WAL, mirror and snapshot writes are not notes) - plus the export worker (`start_export_worker`): a mutating command holds the vault lock for its SQL alone and then calls `AppState::request_export`, and one thread turns those kicks, after a 200 ms debounce, into a state-snapshot + mirror rewrite on its own DB connection under `engine_lock` (`export_files` is the one export routine the worker, both watchers and the synchronous `mirror_export_now` share). Only `open_vault` still exports inline, because the first pull (`google_pull_vault`) adopts the exported files as its sync baseline right after. Everything that swaps or rewrites app.db or the JSONL under the workers (`backup_restore_db`, `google_pull_vault`, a sync pass and the `rebuild_cache` it calls) holds `engine_lock` for its whole run, and the worker skips a pass whose app.db is missing rather than create an empty one.
- `widget.rs` - the Android home-screen widgets' data and action queue, pure over a connection so the desktop builds and tests it: `payload` is the JSON the widgets draw from - `lists` (every active list, favorites first, with the tasks the phone's list screen shows as open in that screen's order, and a checklist's ticked items after them; `kind`, `color`, `favorite`, the group's name) and `day` (today's open top-level tasks in the Day screen's sections: the cadence groups in the config's `cadence_group_order`, inside one by category block then column order - `section_key` is `cadenceKeyOf` from `src/lib/tasks.ts`) - `apply_actions` applies the widget's queued taps (one `{"task","status"}` JSON object per line, `todo`/`done` only; a line that fails to parse or names a gone task is skipped - the widget drew from a snapshot). `widget::android` is the glue: the export worker calls `publish` after every export (the payload goes to the `tauri-plugin-widget` Kotlin side with the queue file's path, `<app config dir>/widget-actions.jsonl`), `start_queue_watcher` (from `setup`) drains that file into the vault on every change while the process lives, and `open_vault` drains it once more and requests an export, so taps made while the app was closed land at the next launch and the widget is redrawn from the vault that opened. The frontend's one command is `widget_launch_target` (`cmd_widget.rs`): what a widget tap launched or resumed the app for - the Day, or a list - handed over once.

The shell also asks `widget_launch_target` on launch and on every return to the foreground: a home-screen widget tap arrives as the launch intent, and the shell answers it through the navigation slice - `openDay(add)` (resets `gridOffset`, sets `dayOpen`) and the Day tab for the today widget, where `MobileDay` focuses its add field for the widget's +; `openList(id, add)` (sets `listOpen`) and the Lists tab for a list row tapped on the lists widget, where `MobileLists` opens that list (the add flag is there for the protocol; the lists widget never sets it). The first-run screen (`MobileVaultSetup`) offers a local vault, a chosen folder, or "Sign in with Google", which pulls the vault from Drive (`google_pull_vault`) or, with Drive empty, starts a local vault and uploads it. Android's hardware back button undoes one UI step before it closes the app: Tauri's app plugin hands the press to a JS `back-button` listener when one is registered and otherwise walks the WebView history and closes, so `mobile/back.ts` registers the listener (`onBackButtonPress`) exactly while some screen has a step to undo and drops it when the stack empties (registrations chained, they are async) - `useBackStep(active, onBack)` handlers stack in activation order (the task editor and search overlay register on mount, screens register their inner steps: list settings / open list / open group, the More screen, the journal browser, the Notes note / search hits / folder trail one level per press, the vault chooser, the Day and Journal screens' return to today from another day, and finally the non-Day tab back to Day); with nothing registered the press closes the app, so the last step before closing is always Day on today.

- Store invalidation: `vaultVersion` counter bumped by engine runs and `vault-updated`; that event's payload is the config files' current errors (the banner) from the emitters that read them (config and tasks watchers, `config_set`), and `null` from those that did not (`capture_task`, a sync pass), which leave the banner as it is; the YAML-backed sections (Upcoming, Reminders, Recurring, History) re-fetch on it. The task views with their own snapshot (Review, Calendar and their phone twins) re-fetch on the store's `tasks` reference alone - `refresh()` replaces the array on every run and `runEngine` calls `refresh()` itself, so one engine pass or one `vault-updated` event costs them exactly one refetch instead of two.
- `store.defaults` caches `config_default` once per session (settings disclosure and the per-group reset).
- `src/lib/`: date helpers, wiki-link codec, markdown lint/table, md color presets, updater flow (silent on failure, runs once on mount).
- Bundle: `MarkdownEditor` (CodeMirror and its language packs, the largest thing in the build) and `react-markdown` (the task dialog's preview) are `React.lazy` imports, so the entry chunk carries the task views and the editor's chunk loads on first use of the Journal, Notes or a description preview. Confirms and prompts everywhere, the phone included, go through `components/dialogs.tsx` (`ConfirmModal`/`PromptModal`); `window.confirm`/`window.prompt` are not used - the WebView's native dialogs are unstyled and unreliable on Android.
- `src/hooks/`: logic the desktop and the phone share without sharing markup - `useReviewData`/`useReviewStats`/`useNextByDay` (the Review's fetches and numbers, used by `sections/Review.tsx` and `mobile/MobileReview.tsx`), `useSearch` (the debounced three-way search behind `SearchPalette` and `MobileSearch`, newest-request-wins), `useDaySections`/`useListSections` (`useColumnSections.ts`: a day or list column's sections, rows, category stripes, block hairlines and chip block indexes - `DayColumn`/`ListColumn` and `MobileDay`/`MobileLists` render the same layout, the section frame, plate and category lead are `components/ColumnSection.tsx`), `useTaskTextDraft` (title/description drafts that commit on blur, close and unmount exactly once, with `discard` for a delete, behind `TaskModal` and `MobileTaskEditor`), `useAutosave` (the Notes and Journal editors' save queue, desktop and phone). A behavior fix belongs there, not in one of the two twins.
- Global keys: Ctrl/Cmd+K search, Ctrl/Cmd+1..9 sections, Ctrl+= / Ctrl+- / Ctrl+0 step `ui_font_size` (clamped 10-28, 0 = the default) the way zoom keys would, but persisted; `src/lib/shortcuts.ts` is the list About shows and README's Keyboard table repeats. 60s rollover engine re-run; the 30s due-task notification timer lives in `src/components/DueToasts.tsx` (rendered by both the desktop layout and the phone shell) - Snooze hides the toast and forgets the notified id after `notify_snooze_minutes`, so the 30s check raises it again while the task stays open. The check runs on mount too, fires `notify_lead_minutes` ahead ("Coming up"), folds the tasks whose time had already passed at a fresh start (app open, new day) into one summary toast instead of a burst (a single one keeps its own toast), hides a toast after `notify_toast_seconds`, and drops a toast whose task is no longer `todo`. A task's toast opens the task on click (the desktop `App` holds a `TaskModal` for it, the phone opens `MobileTaskEditor`); ✕ dismisses, Snooze re-arms.
- Undo toast (bottom center on the desktop in `App.tsx`, above the tab bar on the phone in `MobileApp.tsx`): deleting a task or archiving a list offers Undo for `undo_toast_seconds`; one pending entry at a time (`store.undoEntry`), task undo calls `task_restore` with the snapshot, list undo calls `list_unarchive`.

Crash handling: `main.tsx` wraps both windows in `components/ErrorBoundary.tsx` (a render crash shows a "Something went wrong" screen with Reload instead of a blank window, and is logged) and installs `installGlobalErrorLogging` from `lib/log.ts`. `components/ProblemReport.tsx` - Copy diagnostics / Show log file (desktop) / Report a problem (opens the GitHub bug-report form prefilled with the version) - sits on that screen and in About; the app never sends the log itself.

## Accessibility

- Every screen is checked by axe-core (WCAG 2.0/2.1 A and AA) in `e2e/tests/a11y.spec.ts` - each section in both themes, the task dialog and the phone - and `eslint-plugin-jsx-a11y` (recommended, `eslint.config.js`; `no-autofocus` off: focus only ever lands in a dialog or inline editor the user just opened) runs with the lint. A finding is fixed, not silenced; the one scoped exception is the Notes tree container, a focusable composite whose rows are buttons of their own.
- Keyboard: a task card is one tab stop (`taskCardKeyboard` in `components/taskDnd.ts`, also on the list column's sortable wrapper) announced as a "task" group named by its title - Enter opens it, Space picks it up, the arrow keys carry it to another day or list, Space/Enter drops and Escape cancels (`KeyboardSensor` with `KEYBOARD_CODES`, shared with the Calendar; `DND_ACCESSIBILITY` gives every `DndContext` instructions that say so). A card cannot be a button: it holds buttons. Rows that open an editor on click and hold buttons of their own (Upcoming, Recurring, Reminders) keep the click on the row for the mouse (`role="presentation"`) and put the keyboard stop on the row's main text with `pressable(fn, { click: false })` (`lib/a11y.ts`); a stretch of text with nothing inside it takes `pressable(fn)` whole. `[role=button]` gets the same focus ring as a button.
- Dialogs: the backdrop is `role="presentation"` (a click outside closes, Escape is the keyboard's way out), the panel `role="dialog"`, `aria-modal`, named, and carries `useDialogFocus` (`hooks/useDialogFocus.ts`): focus moves into the panel on open (onto the panel itself unless a field took it), Tab/Shift+Tab cycle inside it (a key a control already handled, like the editor's Tab, is left alone, so dialogs nest), and closing returns focus to the opener. Every dialog uses it; a new one must too. When the focused control disappears with what it acted on (Delete on a card), `useFocusIfLost` puts focus on the Undo the action offered. Icon-only buttons carry an `aria-label` equal to their tooltip; the rail and the phone tab bar are named `nav`s with `aria-current` on the open section, page tabs (Upcoming, Settings) mark theirs with `aria-current`. CodeMirror's text area is named through `MarkdownEditor`'s `label`; Tab indents in it, and Escape-then-Tab or Ctrl+M (CodeMirror's tab-focus mode) leave it.
- Announcements: the error banner sits in an always-mounted `role="alert"`, the config-error banner, the Undo toast and the due toasts in always-mounted `role="status"` regions (desktop and phone) - a region that arrives with its text is not read. Drag-and-drop speaks names, not ids: `DND_ACCESSIBILITY.announcements` (`dndAnnouncements` in `components/taskDnd.ts`) turns `task:42` / `day:2026-10-15` / `list:3` into the task title, the weekday and date, the list name.
- Structure: every page has one `h1` (visually hidden; the section or phone tab name, set in `App.tsx` / `MobileApp.tsx`), day, list and group column headers are `h2`. axe runs with `best-practice` on top of WCAG A/AA, so a missing heading or landmark fails the test.
- Size: the rail is the one fixed-px piece of chrome (`TabBar.tsx`); every other text size is rem (no `text-[Npx]`), so `ui_font_size` scales all of it. The rail drops its labels (kept as accessible names, tooltips still show them) when the window is shorter than the labelled rail (`useCompactRail`), and scrolls below even that - the default 1280x800 window and the 900x600 minimum both reach Settings (`e2e/tests/layout.spec.ts`). A task card's hover actions (priority star, drop, delete) are out of the layout until the card is hovered or holds focus (`HOVER_ACTION` in `TaskCard.tsx`), except in a card at least 17rem wide, where they stay `invisible` and keep their room; they close the row, after the time and the Priority/Overdue/Rate badges, so nothing shifts on hover there (a narrower card, such as the default 200px day column, cannot spare the room from the title) (a day column's Priority label is the badge itself; the star toggle shows only where it is not).
- Contrast: the theme defaults meet 4.5:1 for text on the panels and on their own `/15` tints (light danger/warn/info, light muted text and the dark accent and danger were moved to get there), and filled accent buttons use `bg-accent-fill`, the accent mixed toward black on the dark theme (`--accent-fill-mix`) so white text keeps 4.5:1 for any accent Settings picks. Object colors go through `readable()` with a small margin over `color_min_contrast` (the browser's 8-bit compositing of a tint can land a hair under the computed value); category block headers do too.

## Icons

One mark on every platform: a paper-white tile with a faint rim and a black H cut out of two interlocking brackets on a 5x5 grid (every line one cell thick), the empty bottom-right corner holding a folded page corner ("dog-ear"). `src-tauri/icons/icon.svg` is the tile; `android-bg.svg`/`android-fg.svg` are the Android adaptive layers (the H alone, shrunk into the launcher's safe zone). `npx tauri icon src-tauri/icons/icon-manifest.json` regenerates everything: the desktop/iOS PNGs, `.ico` and `.icns` land in `src-tauri/icons/`, but the Android mipmaps are written straight into the uncommitted `src-tauri/gen/android` - copy its `res/mipmap-*` folders into `src-tauri/icons/android/`, which `scripts/android/build-android.sh` (`sync_launcher_icons`) copies back into the generated project on every build. `app-icon.png` at the repo root (the CLI's default input) is a 1024px render of the same tile, and the About dialog draws the mark inline from the same geometry (`src/components/AppLogo.tsx`) over the serif "Hypomnema" wordmark and the YOUR MIND. ORGANIZED. motto (the website's hero repeats both). Under the text the About content (`AboutContent`, shared by the desktop dialog and the phone's Settings > About) carries the legal notice: the copyright line and the GPL licence URL from `src/lib/legal.ts`, the donation link from the same file when `DONATE_URL` is set, and a Third-party licenses link that loads `third_party_licenses` - `THIRD_PARTY_LICENSES.txt` at the repo root, compiled into the core with `include_str!` so every platform ships it, regenerated by `scripts/general/third-party-licenses.mjs` (crates reachable through normal dependency edges from `cargo metadata`, non-dev packages from `package-lock.json`, the Android Gradle libraries listed by hand in the script) whenever dependencies change. `site/` is the static website - home page and privacy policy - that Google's OAuth verification asks for; it describes what the app sends where, so a change to sync scopes or network endpoints updates it too. The icon is compiled into the exe, so Windows shortcuts pick it up only from a rebuilt install - and Explorer may keep showing its cached copy until `ie4uinit.exe -show` (or a sign-out).

## Versioning

`VERSION` at the repo root is the single version source, synced into `package.json`/`src-tauri/tauri.conf.json`/`src-tauri/Cargo.toml` by `scripts/general/bump.sh` (never edit those manifests by hand). Bumping and cutting an actual release are separate concerns per build target - see `docs/windows/ARCHITECTURE.md` for the Windows release flow (`scripts/windows/release.sh`/`release.ps1`, `release.yml`) and `docs/android/ARCHITECTURE.md` for the Android build.

CI (`ci.yml`, pushes to main and development + PRs + weekly + manual, read-only token; a new push to a PR cancels its older run): frontend lint/typecheck/test/build; rust fmt/clippy(-D warnings)/test on Linux and clippy/test again on Windows (the shipped target, where the `cfg(windows)` desktop code compiles); after the Linux tests, the job fails if `src/bindings` differs from what ts-rs just exported or `THIRD_PARTY_LICENSES.txt` from what the script regenerates (a Dependabot PR has to regenerate it too); an `audit` job - `cargo-deny` (RustSec advisories, the license allow-list and crate sources, policy in `src-tauri/deny.toml`), `npm audit --omit=dev` (what ships in the frontend bundle) and `gitleaks` (pinned through `GITLEAKS_VERSION`, which Dependabot does not see). Actions are pinned to commit SHAs and the Rust toolchain to an exact version (`dtolnay/rust-toolchain`'s version branch), so a new clippy lint arrives as a deliberate bump; Dependabot (`.github/dependabot.yml`, grouped, at most 5 open PRs per ecosystem, targeting `development`, with a 7-day cooldown after a version's publication) proposes the updates; it reads that file from the default branch, so a change there takes effect once `main` has it. Locally, `.githooks/pre-commit` (opt-in: `git config core.hooksPath .githooks`) runs the fast part - `cargo fmt --check` and ESLint on staged files.

## Tests

Rust `#[test]`s per module - inline as `mod tests`, or for a module past ~1000 lines in its own `<module>/tests.rs` (`#[cfg(test)] mod tests;`: engine, tasks, tasks_mirror, sync_cycle, sync_gdrive, config, config_files, kb, views) so the logic reads without scrolling past the tests (engine's are the biggest, including `invariants_hold_over_a_long_irregular_run` - 200 runs at irregular hours, each repeated, with completions and `task_delete`s in between, asserting no duplicate (rule, period), no-op reruns, kept statuses and no return of a superseded deleted instance; `sync_paths` pins the path guard; `views.rs` and `reminders.rs` cover every projection and the focus rotation's edge cases, `error.rs` pins the wire shape); frontend Vitest: pure-logic tests (`src/lib/*.test.ts`, `dateFields.test.ts`), store tests (`src/store.test.ts`: optimistic patch and per-task rollback, out-of-order `task_update` replies, delete + Undo round trip and expiry, reorder), `src/lib/ipc.test.ts` (the `Commands` map against `generate_handler!`, and each command's argument names against its Rust parameters - Tauri passes them by name, so a rename only one side makes would otherwise fail in the running app alone), plus component smoke tests with a mocked Tauri IPC (`src/App.smoke.test.tsx`, `QuickAddModal.test.tsx`, `Review.smoke.test.tsx`, `MobileCalendar.test.tsx` - a late month outlook is dropped, `DueToasts.test.tsx` - a reminder toast's text opens its task, its cross only closes it; per-file `@vitest-environment jsdom`, fixtures in `src/test/fixtures.ts` - `defaultConfig` there mirrors `AppConfig::default()` and the typecheck forces it to track new fields, dispatch in `src/test/tauriMocks.ts`). `npm run coverage` adds a v8 coverage report (`vitest.config.ts`, which also keeps Vitest out of `e2e/`). End-to-end: Playwright (`playwright.config.ts`, `npm run e2e`) builds the bundle behind `e2e/app/index.html` - which loads `e2e/app/backend.ts`, an in-memory fake of the core answering every command through `mockIPC` (tasks, lists, notes, journal as state; an unknown command throws; its handlers are typed against `Commands`, so a wrong answer shape fails the typecheck; `?fail=<command>:<kind>` makes a command's first call reject the way the core does, `?configerror` reports a broken config file, `?signedin` a Google sign-in) and logging the calls on `window.__e2eCalls` - serves it with `vite preview` and drives it at a fixed clock (`e2e/tests/fixtures.ts`, which also fails a test on any page or console error): `navigation`, `tasks`, `screens`, `editors`, `keyboard`, `a11y`, `motion` (reduced motion stops animations; in forced colors a task's status keeps its outline and mark) and `failures` (what the user is told when the core refuses: config error banner, rolled-back status change, the mass-deletion guard's re-upload, a Notes or Journal save that keeps failing holds the editor) specs. `npm run e2e:visual` (project `visual`) takes pixel baselines of every section and Settings tab in both themes, the task dialog, the vault picker and the phone tabs; baselines are per machine and gitignored - made on the base commit with `--update-snapshots`, compared after a change. CI runs the functional project on Linux and uploads coverage for the frontend and (`cargo llvm-cov`) the Rust core. Type checking covers the Node side through `tsconfig.node.json`. See `docs/general/DECISIONS.md` for why there is no driver-based suite.
