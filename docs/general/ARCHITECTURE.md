# Architecture Reference (shared core)

Maintained map of the codebase shared across every build target (Windows desktop, Android), kept accurate so a new session can build context from this file instead of re-reading the sources. Update the affected section in the same commit whenever a change touches vault layout, config schemas, engine invariants, or module responsibilities. Platform-only concerns live in `docs/windows/ARCHITECTURE.md` and `docs/android/`; product-level decisions live in `docs/general/DECISIONS.md`. Kept in step with the code commit by commit (the version in `VERSION` is the one this file describes).

## Layers

- Rust core (`src-tauri/src/`) owns all data and business logic: SQLite, YAML parsing, the generation engine, watchers, filesystem access for Journal/Notes. Exposed as ~100 `#[tauri::command]`s plus the `vault-updated` event. `lib.rs` is the Tauri builder only (plugins, windows, the handler list); the commands live in `cmd_vault.rs` (vault selection, settings, profiles, backups), `cmd_tasks.rs` (lists, groups, tasks, `engine_run`), `cmd_views.rs` (read-only projections), `cmd_rules.rs` (the rule/reminder YAML splice commands and the editable config files), `cmd_journal.rs`, `cmd_kb.rs` (Notes and `open_external`), `cmd_sync.rs` (Google sign-in and sync, passphrase lock, conflict log); `state.rs` holds `AppState`, `with_conn`/`with_vault_root` and the `LockOrRecover` trait (every mutex is taken through `lock_or_recover`, which hands back a poisoned guard instead of panicking - with `panic = "abort"` in release a second panic would be a dead process); `watchers.rs` holds `open_vault`, the three watchers and the export worker; `desktop.rs` the windows/tray/shortcut code with its mobile stubs. This layer is shared as-is across build targets (`#[cfg(desktop)]`/`#[cfg(mobile)]` gate only the small integration bits in `lib.rs` that differ - see `docs/windows/ARCHITECTURE.md`).
- React frontend (`src/`) is presentation only: one Zustand store (`src/store.ts`) wrapping `invoke` calls, ts-rs generated types in `src/bindings/` (regenerated by `cargo test`), Tailwind tokens, CodeMirror 6 editor. Every IPC call goes through `src/lib/ipc.ts`: its `Commands` interface names each `#[tauri::command]` with its camelCased argument object and its result type, and the typed `invoke` there is the only import of `@tauri-apps/api/core`'s invoke outside the tests, so a wrong command name or argument shape fails `tsc`. Adding a command = the Rust fn + `generate_handler!` + a `Commands` entry; `src/lib/ipc.test.ts` fails when the two lists drift. A rejected command carries `error.rs`'s `Error` serialized as `{kind, message, path?}` (`kind` in io/db/config/state/no_vault/sync_conflict; `NoVault` is its own variant so "nothing selected yet" is distinguishable from a failure), and the frontend turns rejections into banner text only through `errorMessage` in `ipc.ts` (`String(e)` on the object would read "[object Object]"), branching on `errorKind` where it matters. Rejections the UI deliberately keeps out of the banner (cosmetic theme calls, the offline update check, an automatic sync pass, a missing habit rate) still go through `warn` in `src/lib/log.ts`, so a swallowed failure leaves a trace in the WebView console. Same frontend codebase for every target; the phone has its own UI under `src/mobile/` (Frontend notes below).
- Desktop-only chrome - a second always-on-top `capture` window, the system tray, and the global capture shortcut - lives outside this shared core; see `docs/windows/ARCHITECTURE.md` for how it's wired.

## Vault layout (`vault.rs`)

All working files live under `<vault>/.hypomnema/` (like a repo's `.git`). Never join layout paths by hand - use the helpers in `vault.rs` (`work_dir`, `config_dir`, `settings_file`, `colors_file`, `db_path`, `tasks_dir`).

```
<vault>/
  journal/<YYYY>/<YYYY-MM-DD>.md   # journal entries
  .trash/                          # Notes deletes, pruned after 30 days; never synced
  .hypomnemaignore                 # gitignore-like filter for the Notes tree
  .hypomnemasyncignore             # same syntax: paths sync leaves on this device (itself synced)
  <user notes>                     # KB root = vault root unless config.kb_path names a folder that exists here
  .hypomnema/
    app.db (+wal/shm)              # WAL mode, migrations in db.rs (20 entries)
    settings/app.yml               # AppConfig minus the colors, per device; SQLite `settings` is a mirror
    settings/profiles/*.yml        # saved settings profiles (profiles.rs): visual-subset snapshots
    config/                        # user YAML configs, seeded with commented samples
      recurring.yml scheduled.yml birthdays.yml
      weekly-focus.yml day-reminders.yml day-schedule.yml
      colors.yml                   # the color scheme (config::COLOR_KEYS), synced so every device matches; absent = defaults
      templates/journal.md
      <subfolder>/*.yml            # "packs": merged into recurring/scheduled/birthdays by top-level key
    tasks/                         # two-way Markdown task mirror + agenda.md + read-only today.md (tasks_mirror.rs)
    state/                         # app-written text state (state_export.rs): *.jsonl DB snapshot
      mirror-base/                 # last-exported mirror copies: the import's merge base
    backups/db/ backups/config/    # daily VACUUM INTO + pre-rewrite config copies (backup.rs)
```

The only state outside the vault is `vault-path.txt` in the OS app-config dir. `migrate_layout` moves pre-0.32 flat vaults into `.hypomnema/` (resumable, step-by-step). All file writes go through `write_atomic` / `write_atomic_bytes` (tmp, `sync_all`, rename) - sync's downloads and merges included; a crash leaves at most a `.<name>.<pid>-<seq>.tmp` staging file (`vault::is_staging_file`), which the Notes tree hides and sync never ships.

## UI sections

Order configurable via `config.section_order`; Settings always last. The list panels (dashboard list zone and the Lists page) render `orderPanel` items, in one of two shapes chosen by `config.lists_group_display`: **folded** (the default) puts ungrouped lists on the panel as columns plus one tile per group (`GroupColumn`), and **flat** gives every list its own column whatever group it is in, with the group's name as a clickable chip on the column header (the chip drills into the group view) and no group tiles at all. A group tile is a member-list index with open counts over its own + List / + Existing pair (create a list straight into the group, or move an existing one in); ⋯ - and a double-click on the tile's free space - opens `GroupModal` (rename, color, membership checkboxes sorted by name, delete-with-release), and the tile is a drop target. Groups are created via the rail's + New group; the All-lists index lists groups with a ▸ marker (`indexRows` in `src/lib/tasks.ts` builds it, `components/IndexRowLabel.tsx` draws a row on both panels: a top-level list starts at the left edge where a group's ▸ stands, members hang one step past the group's name): the index keeps the folded shape whatever the panel does, so under **flat** a group still gets its row with its member lists indented beneath it - the panel has spread them out, and the index is then the only place left that says who belongs together. A group row jumps to its tile when there is one, and to its first member (listed right under it) when there is not (flat) - the index only ever scrolls or pages, it never opens a group view; that is the group chip's and the tile's job. Clicking a group tile (header or any row) switches the whole panel into that group's view - its lists as full columns under a `GroupBackBar` (per-view ephemeral state; the bar carries the group's own ⋯ and doubles as the "take this list out" drop target); a click on a member row also pages/scrolls to that list and flashes it with the same accent ring the index jump uses, and the mouse's back button (button 3) leaves the view. Inside the view the rail's index shows the group's lists ("Group lists"), + New list creates the list directly in the group, + Existing list moves one in, and + New group hides - groups do not nest. Membership is also a drag: a list column's header grip drags `listmove:<id>`, and `components/taskDnd.ts` turns a drop on a group tile (`group:<id>`) or on the back bar (`group:none`) into a `list_set_group` call - the same DndContext as the task cards, told apart by the id prefix. Besides the combined Dashboard there are two focused variants: **Lists** (every list in a wrapping grid, `lists_page_columns`, rows optionally height-aligned via `lists_page_align_rows`, a Lists column count and the Groups folded/flat switch in the header, in the dashboard's order - the same `lists_group_display` the dashboard header also carries, put where the panel it reshapes is; it hides inside a group view, where the shape does not apply, and a sticky right rail like the dashboard list zone's: the New list button over the All-lists index, which scrolls a column into view - `scroll-mt-4` keeps it a page-padding below the top edge so the ring is not cut off - and flashes it with an accent ring) and **Days** (the day grid at full height, no list zone; its own `days_today_only` toggle and `days_page_columns` count). Every day and list column, on all three pages, renders its tasks as one look - flush rows split by hairlines: a `TaskCard` row is transparent - no frame, fill, rounding or shadow; only the drag overlay keeps a framed card - and the column itself takes the card fill `bg-surface-alt`, so rows and gaps share one work surface the theme contrasts against the page; the section plates grow to `list_view_plate_scale` % of their size (default 100, the plain plate) - label font and padding together (`listViewPlateStyle` in `src/lib/tasks.ts`), so the text stays in proportion to the plate - and the first row of every block also takes the hairline above it (`lineAbove`) so a block opened by a gap is framed on both sides. Every break is whole separator stripes (`components/GapFill.tsx`, also used between {Category} blocks in the list dialog): one stripe is `list_gap_stripe` % of a single-line row's height (`listGapStripe`, follows `ui_font_size`), 1 stripe between category blocks, 2 between sections (cadence groups; the priority block and the backlog), 3 into the closed blocks (Postponed / Done, waiting / Done / Dropped - before the first one shown) and 2 between those blocks (`LIST_GAP_STRIPES`; `layout` in `hooks/useColumnSections.ts` turns a closed block that follows another one into a section break). Each stripe carries a soft band of color as thick as a single stripe's band, with the empty space spread evenly (`justify-evenly`) so row-to-band and band-to-band distances match instead of two slots' paddings adding up between bands. The band's look is one shared set (Settings > Columns > Column layout): `gap_fill_color` (empty = the border color), `gap_fill_inset` (% of a stripe left empty above and below, so the band floats clear of the rows' hairlines), `gap_fill_opacity` (% alpha of the band), `gap_fill_max_thickness` (px cap on the band) and `gap_fill_fade` (% of each half of the band that ramps to transparent - vertically in the background gradient, horizontally through a mask, the same ramp length both ways so the corners soften evenly). On top of the stripes sit a few toggles in the same group, all on by default (`components/ColumnSection.tsx`, shared by `DayColumn`, `ListColumn` and the phone's `Sections`) - this flat look is the only one, there is no framed-panel mode: `row_hairlines` draws the line under every row; `category_headers` names a category block once over its first row (`ColumnRow.header`, in the block's chip hue) and the rows drop that chip - the {Category} one, else the list one (`labelInHeader`); `category_header_bold` sets it bold at the task text size; `section_plate_count` adds `· N` to the plate (`done/total` when closed tasks stay inline); `section_plate_sticky` pins the plate to the top of its scrolling column; any plate is a fold toggle (the store's session-only `sectionFolds`, by section key, so a fold applies to every column) and `fold_postponed` / `fold_waiting` / `fold_done` / `fold_dropped` start each closed section folded, one switch each; `closed_row_opacity` fades a closed row's text, chips and badges - not its status box (`.closed-dim` in `src/styles.css`). The plate label is bold, uppercase, 12px at 100% scale. All three views end their header with the same + Task quick-add button at the far right, and share the store snapshot - whose window spans the widest of the day grids, so widening one page never leaves it empty - and the drag-and-drop wiring (`components/taskDnd.ts`). The Dashboard and Days headers carry a date picker that jumps the grid to any date; the Dashboard header also holds the list zone's Lists count (`list_columns`), the Groups Folded/Flat switch and its Days count - Days last, so it stands where the Days page has it. Every page header's view controls go through `components/HeaderControls.tsx` (`HeaderControls` + `HeaderSelect`): one gap between controls and before + Task, one label-to-dropdown gap, and the same names on every page (the Lists page's column count is "Lists", like the dashboard's). Every ‹ / › that steps a view by a period (day grid, Journal day, Calendar and History month, Review week) is `components/NavArrow.tsx`, one look for one function. The app's `<main>` scroller reserves its scrollbar lane (`scrollbar-gutter: stable`), so a page that grows a scrollbar keeps its header controls where a page without one has them. Rail also has Search (Ctrl/Cmd+K), Sync (runs the engine and, while a Google account is signed in, a Drive pass right after; under it the last pass's day and time from `sync_standing` - refreshed on every `sync-status` end, so scheduler passes move it too - red with the error in the tooltip when that pass failed), About. The theme lives in Settings > Appearance only. `config.section_hidden` takes sections off the rail entirely (Settings > Pages > Left bar, next to the order arrows): Settings itself never hides, Ctrl/Cmd+1..9 follow what the rail actually shows, and standing in a section that is being hidden steps the window to the first one still shown.

- **Dashboard** - day grid (`grid_columns`, paged; the count is set by the header's Days dropdown, like the Days page, and has no Settings control) over list-zone backlog columns (paged, split draggable); the list dialog (⋯ on a column, or double-click on the column's free space) manages name/color/description/type (todo queue vs persistent checklist, with Check all / Uncheck all for checklists; the phone's inline list settings carry the same controls) plus the list's group, and the backlog itself (add, check off, star, delete, open a task with its subtasks); dnd-kit drag between days/lists; a dated manual list task stays in its list column always (any date, with a date chip - `tasks_snapshot` includes manual list tasks unconditionally), shows on its day column under Exact date wearing the scheduled-style date label and the exact-date color (isListExact in src/lib/tasks.ts; inside the list the stripe stays list-colored unless `list_exact_stripe` and the chip color follows `list_date_chip_color`), and is listed read-only in Upcoming > Scheduled - one row everywhere; weekly focus + day reminders from `dashboard_context`.
- **Upcoming** - sub-tabs Scheduled / Birthdays / Recurring; CRUD writes back into the YAML files (comment-preserving splice in `config_files.rs`). A materialized scheduled event stays listed until its task is done or deleted.
- **Reminders** - the three ambient config files that feed the day columns, in sub-tabs Weekly focus / Day reminders / Day schedule, over a "Right now" summary (this week's phrase, today's reminders, the current and next block). Same index-based splice CRUD as Upcoming (`reminders_overview` + `focus_phrase_*`, `day_reminder_*`, `schedule_block_*`); these files have no packs, so file order is a stable key.
- **Calendar** - month grid: real tasks + read-only projections from `views::calendar_outlook`, per-cadence horizons. The day list groups a day's tasks by category ({X} title prefix, else the list name) and wears the same chips as the cards. Real tasks are interactive: a day-list row drags onto any month cell to reschedule (its own local DndContext, ids `caltask:`/`calday:`; selection follows the drop), a row click opens the task dialog, and the QuickAdd under the list adds a task on the selected day. Projections stay read-only.
- **History** - month completion stats, per-rule daily streaks (each with a strip of its newest `streak_strip_days` instances as done / waiting / not-done marks, `DailyStreak::recent`), completed tasks by day; bounded by retention pruning.
- **Review** (section id `review`) - weekly review over an ISO week (offset navigation, 0 = current): the week's focus phrase, stat tiles (done/past with rate, per-origin, still-open, dropped), Completed grouped by day with a Dropped, not done group under it next to Still open (rows open the task dialog; Still-open rows carry a hover action strip - manual tasks: Next wk (`nextWeekTarget` in `src/lib/tasks.ts`: Monday of the following week, clamped to tomorrow for past weeks), Backlog (clear date, keep list, Inbox via `inbox_list` when listless), Done, Drop, Delete with Undo; generated tasks get only Done/Drop/Delete since their date and list are rule-owned), and a Next week panel (next week's focus, real tasks + `calendar_outlook` projections by day). Composes existing commands only (`tasks_snapshot`, `calendar_outlook`, `dashboard_context` - which pins the asked week's focus phrase, deterministic cycle so harmless); "Weekly note" jumps to the Journal on the week's last day.
- **Journal** - one Markdown entry per date, template-seeded (`{{date}}`), file created on first save. The header carries the same day stepper as the Dashboard and Days headers - ‹ › (`NavArrow`, also Alt+←/→), the date picker (`DatePick` from `components/DateJump.tsx`) and Back to today when away from it - then names the weekday; the sidebar has no Today button or date field of its own; under it `journal/DayTasks.tsx` lists the day's tasks from `tasks_snapshot` (gated by `journal_day_tasks`, rows open the task dialog); the sidebar index (`journal/EntryList.tsx`) folds by year with month headings and lists the entries written on this calendar day in earlier years ("On this day").
- **Notes** (section id `kb`) - file tree over the KB root (multi-select with Ctrl/Shift, F2 rename, Delete, Ctrl+C/X/V copy-cut-paste via `kb_copy`/`kb_rename`, drag-and-drop onto a folder row or the root area, right-click menu with the same actions plus new note/folder, "Show in file manager" (`kb_reveal`) and "Copy absolute path" (`kb_abs_path`); folders are created with `kb_mkdir` from the header button, a folder row's button, or the menu), editor (YAML colored per the VS Code Dark+/Light+ spec via --yaml-* vars, Markdown headings bold and colored but at the text size so no line jumps in height, markdown/YAML linting with a lint gutter, Alt+Z toggling word wrap for the session across documents - off, a wide table keeps its Tab-aligned rows and scrolls sideways), content search, wiki `[[links]]` and web/mail URLs (both on Ctrl/Cmd+click; URLs go to the system browser via `open_external`, which only accepts http/https/mailto and never touches a shell), `.trash`, plus a Config group editing the six YAMLs, colors.yml (opens on the scheme in use while the file does not exist yet; only color keys pass validation) + journal template with save-time validation. A collapsible Backlinks strip under the editor lists notes whose `[[wiki links]]` point at the open note plus unlinked plain-text mentions, journal entries (links and mentions via `journal::backlinks`, newest first, the note's own-date entry skipped) and tasks (`tasks::backlinks`, `[[links]]` in title/description only - mentions in short titles are noise); `kb_backlinks` returns the aggregate `BacklinksResult`, and with the KB rooted at the vault the note scan drops `journal/` hits so the journal scan stays authoritative. Link beats mention per file, mention floor 3 chars, same caps as `kb_search`. A note/journal hit navigates there; a task hit opens the task dialog in place. The section's frontend is split across `src/sections/kb/` (NoteRow tree row, EditorPane, TreeMenu, CreateNoteModal, util) with state staying in `KnowledgeBase.tsx`. New-note dialog completes the .md extension explicitly (Tab); the + on a folder row pre-fills that folder's path. Markdown notes carry a `Created:` / `Last edited:` header the app keeps (`config.notes_timestamps`, `kb.rs`): `kb_write` returns the stamped text, and the editor adopts it through `rebaseStamp` (`kb/util.ts`) - only the head that changed is carried onto whatever was typed while the save ran - while `MarkdownEditor` applies an outside value as a minimal diff kept out of the undo history and not echoed back as an edit; a note opens with the cursor under the header (`noteBodyOffset`).
- **Settings** - filed by the thing being configured rather than by kind of setting, so a card's geometry and behavior sit in one group instead of across a look tab and a behavior tab. Nine tabs (`src/sections/settings/`): Profiles (named snapshots of the visual settings: built-in Default resets the visual surface, Save/Apply/Delete with confirms, app.yml backed up before an apply, plus the list of groups a profile actually covers, folded by tab - a tab absent from it is one a profile never touches) / Appearance (the global chrome only: theme, fonts and sizes) / Pages (tab id `views`: Left bar = `section_order` + `section_hidden`, Dashboard = the split, Lists page = row alignment, History = `streak_strip_days`; column counts, the Folded/Flat group shape and the two `*_today_only` view modes have no control here - they are switched on the page headers that own them) / Task cards (Chips & categories = chip size plus the category block headers; Weekday markers = the cron markers; Completion rate = the habit-rate chip; Card behavior = undo toast, subtask order, priority overdue) / Columns (Column layout: sections and separators - the knobs-only look shared by every day and list column: panels, plates, hairlines, separator stripes and the gap fill; Postponed and done tasks - `done_display`, with `closed_sections_sort_alpha` (ordered by category then title via `sortClosedAlpha`, in day columns, list columns and the phone's day alike) and `done_hold_seconds` under Separate, the fold defaults and closed-row opacity; then Day columns (header centering, daily-today-only, section order) and List columns, each owning its own habits) / Recurring & calendar (cadence buckets, generation, projection horizons) / Capture & alerts (quick capture, tray, due-task notifications) / Data (vault paths; Journal & notes = editor line numbers, note stamps, the Journal's day tasks, the journal template; snapshots & mirror; backup retention *with* the restore lists; Done tasks cleanup = `retention_days`, `clear_done_list_tasks`, delete-done and archived-list restore - `backups_list`/`backup_restore_db`/`backup_restore_config`) / Sync (`SyncTab.tsx`: Google sign-in and sign-out, standing + Sync now + the mass-deletion guard's "Upload this vault again", the conflict log, a warning when the vault path sits inside a Dropbox / OneDrive / Google Drive client folder, and the When to sync group). The map itself is `src/lib/settingsCatalog.ts`: tabs, groups (title, tab, always-open, no-reset, knobs-only) and one entry per `AppConfig` field with its search label; `SettingsGroup` reads title and field list from it by group id, so a tab never repeats a key list, and `settingsCatalog.test.ts` pins the catalog against `AppConfig` - a new field must land in a group or be named in `EXCLUDED_KEYS` with a reason (today: `grid_columns`, `list_columns`, `days_page_columns`, `lists_page_columns`, `lists_group_display` and the two `*_today_only` toggles, all set on the page headers they reshape; the two mobile-only inset fields; and every color - each `*_color`, `color_min_contrast`, `cadence_colors`, the category chip coloring mode and its avoid-cadence switch, `dow_label_opacity` (tunes the default marker tone only) and `list_exact_stripe` - which live in the synced `config/colors.yml`, edited by hand or set by a profile, so Settings stays short). A search box over the whole catalog (label, config key, group title, extra terms; every term must match) jumps to the tab and rings the group - with 100+ fields, finding the tab is the real cost of the page. The page's column is exactly as wide as its tab strip on one line (`w-fit` over a nowrap strip, the search and the tab body sized `w-0 min-w-full` so they follow rather than set the width), capped at the window - there is no width setting. Every group is a `SettingsGroup`: a group whose fields all sit at their factory defaults (compared against `config_default` via `src/lib/settingsGroups.ts`) renders collapsed behind a "Customize" affordance (manual expand state is ephemeral), a changed one offers "reset" back to those defaults, and a group inside the profile scope says so in its header - the scope comes from the Rust `PROFILE_KEYS` through the `profile_scope` command, never from a second copy in the frontend. A group that is *nothing but* knobs is flagged `knobs` in the catalog (Column layout, Cadence buckets, Calendar projections) and wears a customization checkbox on its own header instead of the collapse link: it is ticked exactly while one of its fields differs from its default, so unticking it is the reset - a checkbox left unticked over changed values would be a lie. Ticking only reveals the fields; it writes nothing. Search still reaches a hidden field: the focus context (`{group}`) opens the group a hit landed in.

## Config files (`config_files.rs`, `config.rs`)

| File | Schema |
| --- | --- |
| `recurring.yml` | `tasks: [{schedule: cron, description, items: ["{List} text"], threshold?: 0-100}]` (`threshold` = the rule's own rate-chip alert, not part of the rule key) |
| `scheduled.yml` | `events: [{date: YYYY-MM-DD, title, time?}]` |
| `birthdays.yml` | `birthdays: [{name, date: MM-DD, year?}]` |
| `weekly-focus.yml` | `rotation: cycle`, `phrases: [..]` (no packs) |
| `day-reminders.yml` | `reminders: [{day_type: workday\|weekend\|mon..sun, text}]` (no packs) |
| `day-schedule.yml` | `blocks: [{from, to, label}]` (no packs); `from`/`to` are zero-padded `HH:MM` on both the read and the write path (`reminders::normalized_blocks`, `config_files::validate_block`) - the whole block model compares clock strings lexicographically, so a hand-written `9:00` would sort after `23:00` and never read as the current block |

Packs: subfolders of `config/` are walked recursively; a `*.yml` file contributes to whichever of the three task sections its top-level keys name. Errors carry the path relative to `config/`. Broken files never wipe state - last valid config stays active, error shows as a banner.

`AppConfig` (128 fields, every one of them filed in `src/lib/settingsCatalog.ts` or excluded there with a reason): dark/light `theme` over a single chrome palette - VS Code Dark+/Light+, baked into the `:root`/`.dark` tokens of `src/styles.css` - with individual accent/surface/panel/border overrides, typography, dashboard layout, task display (cadence colors, closed-section plate colors, done display/hold, `undo_toast_seconds` for the delete/archive Undo toast, `list_task_lines`/`list_dialog_task_lines` title clamps), engine (`retention_days`, `catchup_days`, `cron_ignore_time`), calendar outlook horizons, quick capture (`capture_list` is used on every target; `capture_shortcut`, `tray_icon`, `close_to_tray` are desktop-only - see `docs/windows/ARCHITECTURE.md`), chip look (`chip_font_scale` sizes every category/list/date chip against the text beside it, `category_color_mode` (default `single`) picks how a category chip is colored via `categoryChipColor`: `single` = one shared `category_color`, `varied` = the list's own color else a `CATEGORY_PALETTE` hue hashed from the name - with `category_avoid_cadence_colors` (default on) the palette first drops every hue within 20 degrees of a saturated cadence color, so a chip never wears the color of the Weekly/Monthly plate above it, `alternate` = `category_color_a`/`category_color_b` taking turns by the card's `categoryBlockIndex` - a counter the column runs over its cards in render order, so the turn carries straight through the cadence sections and on into Postponed/Done instead of restarting), `section_order` + `section_hidden`, `lists_group_display` (folded/flat list panels), files (`kb_path`, `notes_timestamps`, `tasks_mirror` + `tasks_mirror_ids`, `backup_keep`), `notify_system` + `notify_lead_minutes` + `notify_toast_seconds`, `journal_day_tasks`, `streak_strip_days`, sync (`sync_auto`, `sync_interval_minutes`, `sync_on_leave` - leave on the phone, quit on the desktop - plus desktop-only `sync_debounce_seconds` and `sync_on_focus`, and `sync_mass_delete_guard_percent`), markdown editor: no color presets - Markdown and YAML always follow the VS Code Dark+/Light+ `--md-*`/`--yaml-*` tokens in `src/styles.css`. Adding a setting = field + default + `sanitized()` clamp + `settings_pairs()` in `config.rs`, deciding whether it joins `PROFILE_KEYS` (visual customization) or stays out (behavior, paths, timings), ts-rs regen via `cargo test`, then a control in the matching Settings group plus its entry in `src/lib/settingsCatalog.ts` (the test fails until the field is filed or excluded).

Object colors (cadence stripes and plates, closed-section plates, status marks, chips, list/group dots, the day header, reminder, weekly focus and weekday marker tones) are one hex for both themes and adapt per theme at render (`src/lib/color.ts`): `readable(hex, kind)` keeps the hue and moves only the OKLCH lightness - lighter on dark surfaces, darker on light ones, judged by the actual surface colors so chrome overrides count - just far enough to reach `color_min_contrast` (tenths of a ratio, default 45 = 4.5:1, 0 = off) against both surfaces. `tint` measures text on its own 15% tint (`tintStyle`: plates and chips), `text` plain text, `mark` non-text and stops at 3:1; a color that already reads comes back untouched. `applyTheme` in the store refreshes the context (`setColorContext`) before the render that follows a config change. The default hexes (`AppConfig::default()`, `CATEGORY_PALETTE`) sit at the OKLCH lightness that balances contrast on the dark and light panels, so the adaptation rarely has to move them; neighbouring plates get distinct hues. The text-tone and chrome overrides default to empty, following the theme (the Dark+ secondary text token is lightened to #bfbfbf). None of these colors has a Settings control, on the desktop or the phone. They are `config::COLOR_KEYS` and live in `config/colors.yml`, not app.yml: app.yml is per device (sync leaves `settings/` alone), the scheme is the user's, so it sits with the synced user configs. `AppConfig::read` lays colors.yml over app.yml (color keys still in an old app.yml are ignored, a missing colors.yml means the defaults, a broken one costs only the colors); `save` writes app.yml without them, and `Vault::save_config` writes colors.yml only when a color actually changed (backing it up first) - rewriting it on every setting would push this device's copy over a newer synced one. The config watcher reloads it like any config file.

Settings profiles (`profiles.rs`): flat YAML mappings of the `PROFILE_KEYS` subset (77 visual fields, pinned by `profile_keys_are_real_fields`) under `settings/profiles/<name>.yml`. Apply = reset every scope key to its default, overlay the file's whitelisted keys, `sanitized()`, `vault.save_config`; missing keys mean defaults, unknown/out-of-scope keys (a smuggled `kb_path`) are ignored, "Default" is the reserved empty overlay. Commands: `config_default` (the frontend's defaults source), `profile_scope` (the key list itself, so the Settings page can mark each group with what a profile does to it), `profiles_list`, `profile_save`, `profile_apply` (backs up app.yml via `backup_config_file` first), `profile_delete`.

## Engine (`engine.rs`)

Three generators per pass: recurring (cron), scheduled events, birthdays. No separate dailies/priority generator: "daily" is a cadence bucket derived from firing frequency (`cadence_of`); priority is instance-local user state on ANY task (generated included) and survives engine passes.

- **Dedup**: `rule_runs(rule_key, period_key)` ledger, keys via stable FNV-1a 64. Period keys: recurring `YYYY-MM-DDTHH:MM`, scheduled `YYYY-MM-DD`, birthday `<year>`. Card deletes are hard (`task_delete` drops the row and its `rule_runs` entry), so a deleted instance of a live rule regenerates on the next pass; only the delete-done sweep leaves archived tombstones, and `repair_orphaned_period` unblocks today/future periods whose task vanished without one. A generated task's row id is derived from its `(rule_key, period_key)` (`ids.rs`), so two devices generating the same instance mint the same row and the snapshot merge folds them; it is inserted with the untouched stamp (`ids::UNTOUCHED_AT`/`UNTOUCHED_BY`, the epoch and `engine`), so a real edit on the other device - checking it off - always outranks a copy generated later. Carry-over's `dedupe_instances` collapses any remaining twins of one `(rule, period)` (older builds, rows merged in under counted-up ids): the copy someone acted on is kept (done/dropped, then waiting, then postponed, then untouched), then the smallest id - deterministic, so both devices keep the same one - and the loser's subtasks move to it.
- **Catch-up**: window `[now - catchup_days, today + config.horizon_days() - 1]`, where the horizon is the widest day grid any view shows (`max(grid_columns, days_page_columns)`) - the calendar projection starts right after it; missed firings collapse into the single latest one (one overdue copy, not N); `MAX_FIRINGS = 2000` runaway guard (a daily-cadence rule enumerates from today only, since it discards every pre-today firing anyway); fresh rules start from today (`rule_seen`). Birthdays are checked for every year the window touches (`window_start.year()..=horizon.year()`), so a birthday missed over New Year still catches up. Scheduled events store their `date`/`time` zero-padded whatever the YAML says (chrono accepts `2026-9-8`; the model compares strings), and a changed `time:` reaches the already-generated instance the way a changed birthday year reaches its title.
- **Reconcile**: removing a rule/item removes ALL its instances - future, today's open, and pre-today done history (nothing lingers in the Calendar); only a copy already acted on today (done, dropped or waiting) survives, so editing a rule (key change) never hides a just-finished task. Missing/comment-only `recurring.yml` is treated as transient (generation may run, reconcile must not).
- **Statuses**: `todo`, `postponed`, `waiting` (done on the user's side, waiting on someone else) are open; `done` and `dropped` (not done, taken off the plan) are closed - SQL spells that as `status IN ('done', 'dropped')` (`tasks::STATUSES`/`is_closed`). Closed tasks are what the list sweep, retention and delete-done remove and what carry-over skips; only `done` is a completion (History, Review rate, streaks), so a recurring instance dropped at review time reads as not done. The checkbox cycles todo -> done -> postponed -> waiting -> todo; dropped is only ever chosen on purpose (the card's ⊘, the task dialog, Review's Drop) and a click brings it back to todo. In the separate done display waiting gets its own "Done, waiting" section between Postponed and Done, and dropped gets "Not done, dropped" after Done (`dropped_plate_color`, neutral gray by default: dropped is a quiet outcome, not an error). The waiting mark takes `config.waiting_color` through the `--color-waiting` var, exposed to Tailwind as the `waiting` color; the dropped mark likewise takes `config.dropped_color` through `--color-dropped` / `dropped`. `done_display` defaults to `separate`.
- **Carry-over**: open pre-today tasks (postponed and waiting included) move to today with the overdue mark (priority included unless `priority_overdue` is off); dailies are exempt and get rehomed to their firing day; at most one open overdue copy per rule - a waiting copy is never the one collapsed away.
- **Done ahead of time**: a task checked off on a future day column keeps that day. Both the list sweep (`clear_done_list_tasks`) and retention pruning skip a done task whose `scheduled_date` is today or later, so it disappears only on the rollover after its own day.
- **Pass phases** (one IMMEDIATE transaction): generate x3 -> carry-over -> retention prune -> clear done list-backlog tasks (`clear_done_list_tasks`; checklist-kind lists are exempt from both this sweep and retention - their checked items are kept state) -> purge archived rows (>24h, except pending delete-done tombstones) -> trim old `rule_runs` -> dedupe errors. Returns `EngineOutcome{generated, carried_over, removed, pruned, errors}`.

## Core modules

- `ids.rs` - row ids for `tasks`, `lists` and `list_groups` that two devices mint without colliding (the snapshot merge is keyed by `id`, and SQLite's `MAX(id) + 1` hands the same next id to different rows on each device). Every production insert names its id: an engine-generated task gets one derived from `(rule_key, period_key)`, a list or group one derived from its name (two devices creating "Work" get one list), anything else - or a name whose derived id is taken - a random one. Random ids live in `[2^40, 2^51)`, derived in `[2^51, 2^52)`: above any counted-up id of an older vault, below JS's 2^53. Ids carry no order, so "newest" queries sort by `created_at`.
- `tasks.rs` - lists/tasks CRUD; `ensure_inbox` returns the quick-capture list (case-insensitive match over active lists, promotes an auto namesake, else creates manual+favorite); list names are unique among **active** lists only (partial index `idx_lists_active_name`, migration 015): an archived namesake never blocks a create/rename, an auto list of that name is absorbed into the user list instead (its tasks move over, the auto row goes), a live manual namesake reports "a list named X already exists", and `list_unarchive` refuses a restore whose name is taken. `list_ensure` prefers the active list over an archived namesake. `task_delete` is a hard delete (cascades to subtasks, drops the `rule_runs` row) and returns a `DeletedTasks` snapshot (rows + ledger entry) that `task_restore` puts back - the Undo toast round-trips it through the frontend; original ids are kept while free, and a restore is skipped when the engine already regenerated the same (rule, period) instance. `archived_at` remains only for the delete-done sweep tombstones; lists carry a `favorite` flag (sorts ahead in the list zone) and a `kind` (`todo` | `checklist`, set in the list dialog via `list_set_meta`): a checklist keeps its checked items - the overnight list sweep, retention pruning and the delete-done maintenance sweep all skip its tasks (subtasks included) - its tasks have no postponed state in the UI (the checkbox is a plain todo <-> done toggle; a leftover postponed row still renders and can be reset), and `list_set_all_statuses` checks/unchecks the whole list at once (top-level tasks plus their subtasks - the Check all / Uncheck all bulk actions). The `overdue` flag survives the status cycle (done does not clear it; the UI just hides it on done cards). List groups (`list_groups` table, `groups_all`/`group_create`/`group_set_meta`/`group_delete`/`list_set_group`): a group is a named folder in the list panel - the panel shows the group tile (member lists with open counts, drill-in per column), a grouped list (`lists.group_id`) never renders as its own panel column; deleting a group releases its members (ON DELETE SET NULL, which also restamps them for sync); group names are unique among groups; the snapshot carries them in `list_groups.jsonl` (stamped merge like lists.jsonl; a restore drops a membership whose group is gone from a merged snapshot rather than failing the open).
- `tasks_mirror.rs` - Markdown mirror of tasks: a list's file header carries its group as an editable `<!-- group: Name -->` line (a group is otherwise invisible from the vault; editing the line moves the list and creates the group when the name is new, an empty name releases it, and a file with no such line at all - an older export, a hand-made file - leaves the membership alone; it merges against the base like any other field). One file per list + `scheduled.md` (manual tasks, full authority) + `agenda.md` (generated instances from today onward, gated by `config.tasks_mirror_agenda`: status/priority/time sync back, title/date edits do not, absence never deletes, an id-less line creates a manual task on that day - the phone-over-file-sync surface) + `today.md` (gated by `config.tasks_mirror_today`, covering `tasks_mirror_today_days` days: a read-only phone-readable day sheet - focus phrase, reminders, schedule blocks, Overdue, tasks grouped by category with no `^id` keys; its marker makes the import a no-op, the sweep removes it when the flag turns off, and it gets no mirror-base copy). The optional files ride `ExportOptions`; `export` takes the config dir for `dashboard_context`. Per-line `^<id>` sync keys (omitted with `config.tasks_mirror_ids` off, and a line is then matched to its task by title; in the agenda the date joins the match key); `[x]` done, `[z]` postponed, `[xz]` done but waiting, `[zz]` dropped (`[>]` from older versions still parses); marker first line; gated by `config.tasks_mirror`; folder watcher imports outside edits. Every export also snapshots the files into `state/mirror-base/`; an export from a command (`ExportOptions::preserve_pending`) leaves a file alone when its disk copy differs from that base - an outside edit the watcher has not imported yet - while the watcher's own export (having just imported the disk) rewrites it, and the watcher runs one pass right after it starts so an edit made while the app was closed gets imported instead of overwritten; the stale-file sweep never removes a file whose import just failed (a conflicted copy keeps its lines until the user deals with it); a stem of the export's own collision form `Name (id)` is not read as a rename; with ids off a trailing ` ^N` is title text, not a key. The import is a three-way merge against that base: a field applies only when the file changed it, absence deletes only tasks the base knew, a stale line of an app-side-deleted task is not resurrected, and a scheduled/agenda marker under a wrong file name (a sync "conflicted copy") is rejected instead of double-imported. Without a base the file wins wholesale.
- `journal.rs` - entry open/save/list/search, template at `config/templates/journal.md`.
- **Editor saves merge, never overwrite** (`text_merge.rs`): an editor saves the whole text it shows, read some time ago, so `journal_save` and `kb_write` take a `base` - the on-disk text the editor's text derives from - and `reconcile_save` three-way merges the save with whatever changed on disk since (a sync pass merging the other device's edit, another program). Same lines changed on both sides: the editor's text wins and the disk version is kept as `<name> (conflicted copy edited elsewhere <date>)`, logged under "to review" (`sync_conflicts::log_kept_aside`). Conflicted copies are resolved from the conflict list (`components/ConflictReview.tsx`): `sync_conflict_diff` shows the file against its copy line by line, `sync_conflict_resolve` keeps the file or puts the copy's text in it and moves the copy to the vault's `.trash/` (both refuse a pair that is not a file and its own conflicted copy beside it); the Notes tree marks conflicted copies with a badge. Both commands return the text now on disk; the editors (desktop Journal/Notes, phone Journal/Notes) settle onto it with `settleSave` (`sections/kb/util.ts`: adopt it when nothing was typed meanwhile, carry the typing over with `rebaseStamp`, else keep the typing and measure the next save against what was sent), and an editor with no unsaved typing rereads its file on `kb-updated` / `vault-updated`. `text_merge::merge3` (diffy, CRLF compared as LF, result in ours' line endings) is also the sync pass's line merge; both callers go through `merge_file`, which takes a Markdown note's Created / Last edited header (`kb::split_stamps`) off all three versions and merges it on its own (earliest Created, latest Last edited) - otherwise every save on both devices rewrites that line and no two-device edit of a note would ever merge. Saves and the sync pass's apply of a download hold `text_merge::user_file_lock` across their read-merge-write, so neither writes over a change the other made between its read and its write. Each editor runs its saves one at a time (`serialSaves` in `sections/kb/util.ts` - two saves in flight with one base would meet each other on disk as a clash), numbers every keystroke so a landing save marks the editor saved only when nothing was typed after it, and keeps a failed save for the next flush; `components/SaveIndicator.tsx` shows Saved / Saving... / Not saved · Retry.
- `kb.rs` - Notes FS layer. The root is the vault itself unless `config.kb_path` names a directory that exists **on this device**; a path from another machine falls back to the vault - `settings/` never syncs, but a vault copied wholesale from a desktop carries its app.yml along, and `D:\Projects\...` means nothing on a phone. The phone's fallback banner carries a "Use the vault" button that clears `kb_path` locally - settings never sync, so adopting the vault on the phone leaves the desktop's path alone. `kb_status` reports the effective root and whether it is a fallback, so a desktop whose external notes drive is unplugged is told rather than quietly writing into the vault. `write` stamps Markdown notes with the `Created:` / `Last edited:` header when `kb_write` asks it to (setting on, `.md`, not a `journal/` entry of a vault-rooted tree): `stamp_note` keeps the header at the top (inside a frontmatter block when there is one), finds it within the first lines so text typed above it never duplicates it, takes Created from the incoming text, then the disk copy, then the file's birth time, and moves Last edited only when the text under the header changed - a no-op save is not rewritten, and a hand-corrected Last edited wins like a hand-corrected Created does. A case-only rename (`note.md` -> `Note.md`) is allowed on a case-insensitive filesystem. `resolve()` blocks path traversal; `guard_work_dir` refuses to delete, move or rename `.hypomnema/` or anything in it outside `config/` (with the tree rooted at the vault, one Delete would otherwise trash the open database); `copy_into` refuses to paste a folder into itself; renaming a folder never appends the old "extension" (`proj.old` -> `proj`); `.hypomnemaignore` glob filter; trash + 30-day prune (the trash shows in the tree like any folder, hidden only by the ignore file). `kb_reveal` (Show in file manager) writes its Windows command line with `raw_arg`: explorer.exe does not parse arguments the way `CommandLineToArgvW` does, so Rust's own quoting made it open a default folder instead of the note whenever the path held a space.
- `reminders.rs` - `dashboard_context` (weekly focus, ISO-week pinned via `weekly_focus_state`; day-type reminders; schedule blocks) and `overview` behind the Reminders section.
- `views.rs` - read-only projections: upcoming, birthdays, recurring list, calendar outlook, daily streaks, cron weekday labels, habit rates. `calendar_outlook(from, to)` takes **`to` inclusive**, unlike `tasks_snapshot`'s exclusive `endDate` - a caller that hands both the same bound projects one day too many. `habit_rates` (command of the same name) gives each recurring rule item (`rule_key`) its completion rate over the newest `habit_rate_window` settled instances: done and waiting count as done, dropped as not done, a daily instance still open after its day as not done (dailies never carry over); an open instance of any other cadence is live overdue work and waits. Items under `habit_rate_min_instances` get no rate. The threshold is the rule's own `threshold:` else `habit_rate_threshold`, and `alert` = rate below it (the percent is rounded down, so a shown 80% never alerts at 80). The store keeps them in `habitRates` (reloaded by `refresh`, by a status change on a recurring task in `updateTask`, and by a change of the three computing settings); `TaskCard` shows `Rate: N%` after the overdue mark behind `habit_rate_chip`, tinted with `habit_rate_alert_color` when alerting, and only while alerting under `habit_rate_alert_only` (default on); the `[DOW]` marker in its default muted tone fades to `dow_label_opacity` % (a picked `dow_label_color` shows at full strength); the Recurring section's add/edit forms set the per-rule threshold (empty = default).
- `state_export.rs` - makes app.db a disposable cache: every mirror-export trigger also writes a full JSONL snapshot of the database's authoritative state under `state/` (tasks with ids/provenance/tombstones, lists, list groups, `rule_runs`, `rule_seen`, `weekly_focus_state`; gated by `config.state_snapshot`, on by default), and `Vault::open` on a vault without app.db restores from it before anything can export the empty database over it (a broken snapshot aborts the open for the same reason - every JSONL file that exists must parse, only a missing side file reads as empty). The restore drops a dangling `list_id`/`parent_task_id`/`group_id` reference rather than failing on the FK: a record-wise merge legitimately keeps a row whose parent the other device hard-deleted. Deleting app.db is the supported way to force a rebuild; ids are preserved so the mirror's `^id` keys stay valid. Two active lists (or two groups) of one name in a snapshot - created on two devices under counted-up ids before either synced - restore as one: the smaller id stands and the other's members are remapped to it, rather than the restore failing on the unique active-name index.
- `backup.rs` - daily DB snapshot (`VACUUM INTO`) + pre-rewrite config backups, rotation by `backup_keep`, best effort; `overview`/`list_db_backups`/`list_config_backups` back the Data tab's restore list. `restore_db_backup` swaps app.db from a snapshot (caller must close the live connection first; the file being replaced is itself copied aside as `pre-restore-app-<ts>.db` - not `app-` prefixed, so the daily rotation by `backup_keep` never counts it - and its stale `-wal`/`-shm` siblings are dropped) and `restore_config_backup` puts one config/settings file back in place (also backing up the file it overwrites) - every restore backs up what it's about to replace first, so a restore is itself undoable.
- `db.rs` - migrations (20), refuses a newer-than-known `user_version`; `mirror_settings`. Migration 020 recreates the six stamp triggers with millisecond `updated_at` (`%f`): whole seconds made two devices' edits of a row within one second a tie. Migration 019 rebuilds `tasks` to widen the status CHECK with `waiting`/`dropped` (self-reference named `tasks_new` during the copy so the DROP cascades into nothing; indexes and stamp triggers recreated, stamps preserved). Migration 017 adds `lists.kind` (`todo` | `checklist`); 018 adds `list_groups` (stamped by the same trigger pattern as migration 016) and `lists.group_id` (FK, ON DELETE SET NULL). Migration 016 adds `updated_at`/`updated_by` to `tasks` and `lists` and stamps them from **triggers**, not from the ~70 call sites that write those tables: a missed site would not fail a build, it would make a changed row look untouched and hand the next cross-device merge to the wrong side. Both triggers stand aside when a statement supplies its own values, which is what lets `state_export::restore` put a snapshot back with the stamps it was taken with instead of relabelling the vault as "changed here, now". `set_device_id` records the writing device per connection (`sync_device`), so the same vault opened on another machine stamps with that machine's id.
- `crypto.rs` / `secret_store.rs` - Argon2id + AES-256-GCM (pure Rust, so the Android cross-compile stays free of native deps) behind an optional device passphrase. One secret is covered: the desktop's Google refresh token (`google.json`), a standing grant to the app's Drive folder that outlives every access token; the phone stores none (Play services holds its grant), so its Settings only offer to remove a passphrase left from an older build, and nothing in either UI sets one. Enabling seals what is already on disk, disabling requires the passphrase, and the unlocked passphrase lives in memory for the session and nowhere else. **Not** vault encryption - the vault is plain files each device reads directly and sync moves as-is (`docs/general/DECISIONS.md`).
- `device.rs` - this install's opaque device id (the `updated_by` half), kept in the app's private config dir and never in the vault: a vault synced to a second machine must not carry the first machine's identity, or two devices' edits become indistinguishable.
- Sync (Google Drive is the one backend): `sync_paths.rs` is the whitelist of what travels (everything outside `.hypomnema/` except `.trash/` at any depth, staging files and the user's `.hypomnemasyncignore` patterns - a folder rule covers everything below it, reloaded at the start of every pass, push and pull; inside `.hypomnema/` only `state/` minus `mirror-base/`, and `config/`); `sync_provider.rs` is the backend-agnostic trait (list changes since a cursor, read/write/delete a file guarded by an opaque change marker, `Error::SyncConflict` on a stale write or a guarded delete of a file that moved on); `sync_merge.rs` is the per-field last-writer-wins merge with a conflicts list plus the `rule_runs` set union; `sync_state.rs` applies that merge to the JSONL snapshot record by record, giving each file the merge its content deserves (`tasks`/`lists` by their `updated_at`/`updated_by` stamps - compared as instants, since migration 020 stamps milliseconds while older rows carry whole seconds, a true tie going to the larger device id so both devices pick the same side - `rule_runs` as a set union, `rule_seen` keeping the earliest first-seen so catch-up never re-runs a rule's history, `weekly_focus` keeping this device's pin and logging the other); `sync_cycle.rs` is the full pass - the manifest's revision says whether the remote moved, its hash says whether this device did, and only when both moved does a merge happen (record-wise for the snapshot; for mergeable text - `.md`/`.markdown`/`.txt`/`.yml`/`.yaml`, `.hypomnemaignore` and `.hypomnemasyncignore` - a git-style line-wise three-way merge (`text_merge::merge3`) against the agreed version kept in the sync space's base dir, which every download, upload and pull records for text as for the snapshot, and which a pass seeds for any text still matching its manifest hash; only when both sides changed the same lines, or there is no base or the bytes are not UTF-8, a `(conflicted copy <phone|desktop> <date>)` file beside the original (stepped to `<label> 2`, `3`... rather than overwrite an earlier copy of the day), because merging two people's edits of one line invents a version neither wrote - except a config file this device still holds as the seeded sample (`vault::is_untouched_sample`), which a vault started here before its first sync gives way to the other device's rules without a copy); `sync_conflicts.rs` keeps what those merges had to choose between in a device-local log - each entry that left a conflicted copy records it (`copy`), and `sync_conflicts_list` returns `for_display`: device ids named "this device" / "the other device", entries whose copy still exists marked `open` and sorted first (older entries have their copy parsed out of the text), shown by the shared `components/ConflictList.tsx` on both platforms as "to review"; `sync_bootstrap.rs` holds vault-root detection, the one-way first pull (`pull_vault`, resumable through the manifest; `google_pull_vault` uses it) and the sync spaces, `sync_push.rs` the guarded upload the pass ends with plus `adopt_local_baseline`; `oauth.rs` is the provider-neutral PKCE pair and the `OauthTransport` seam. When a pass changes the snapshot (a byte-identical download does not count) it drops app.db and reopens the vault so the merged JSONL rebuilds the cache through the existing restore path rather than a second write path into SQLite - the old app.db is kept aside until the reopen succeeds, and put back if it does not. A file that cannot be applied is listed under `failed` rather than aborting the pass. Deletions propagate both ways, distinguished from "never pulled" by the manifest and guarded by the revision this device last saw - an edit on the other end outranks a deletion here, and vice versa. The manifest and the merge base live in the active **sync space** (`sync_bootstrap::space_dir`): `.hypomnema/sync/` itself when no `sync/space` pointer names one, else `sync/spaces/<name>/` - so a different account starts from an empty manifest and its first pass joins (identical files adopted, the rest merged or uploaded) instead of reading another remote's revisions; `sync_reset_space` empties the active space for the same join on purpose. Before applying anything a pass runs the **mass-deletion guard**: with at least 10 synced files, more than `config.sync_mass_delete_guard_percent` (default 30, 100 = off) of them missing from the remote at once fails the pass with `Error::RemoteWiped` (`kind: "remote_wiped"`) with nothing touched - a wiped remote or another account looks exactly like the other device deleting everything - and both UIs offer "Upload this vault again" (reset the space, then sync). The command half of a pass (engine lock, export, `sync_vault`, `record_pass`, `rebuild_cache`) is `cmd_sync::run_pass`, generic over the provider. Listings are always full, so a path in the manifest that is absent from one counts as deleted over there even without a tombstone. `SyncProvider::take_duplicates`/`discard_duplicate` cover a backend that allows two files under one path (Drive does): after the incoming phase each extra copy is folded into the local file with no base (state files as a union merge, differing prose as a `(conflicted copy duplicate <date>)` file), the merge goes up with the same pass, and only then is the copy discarded - one with nothing local to merge into is kept for the next pass. `sync_gdrive.rs` implements the trait over Drive v3 in the hidden `appDataFolder` (scope `drive.appdata`) behind a raw `GdriveTransport` seam (request in, any status out; retries 429/5xx/rate-limit 403 in the real `ureq` transport): the vault-relative path is the file `name`, the marker is `headRevisionId`, duplicate names keep the earliest `createdTime` (then smallest id) as canonical, a guarded write reads the head revision first and afterwards checks `revisions.list` - another device's revision landed in that window is re-created as a duplicate for the next pass to merge - and a guarded delete is check-then-delete (appdata has no trash). **Google sign-in**: `google_auth.rs` is the desktop OAuth flow - PKCE + `state`, the redirect caught on a `127.0.0.1:<free port>` listener (`wait_for_redirect`, 5 min, cancellable via `google_sign_in_cancel`), the consent page opened with `tauri-plugin-opener`, code/refresh exchange and revoke at `oauth2.googleapis.com`; `CLIENT_ID` is a public constant, the desktop client secret is compiled in from `HYPOMNEMA_GOOGLE_DESKTOP_CLIENT_SECRET` (`option_env!`, see `docs/windows/ARCHITECTURE.md`) and a build without it reports `available: false`. `google_link.rs` keeps the account (email, name, Drive `permissionId` from `about.get`) in plain `google-account.json` - readable on a locked device - and the tokens in `google.json` through `secret_store` (sealed by the passphrase when one is set; `cmd_sync::secret_files`), refreshing ahead of expiry. **Android sign-in** goes through `src-tauri/plugins/google-auth/` (crate `tauri-plugin-google-auth`, an Android-only dependency registered in `lib.rs`): its Kotlin half (`android/`, tracked in git rather than in the regenerated `gen/android` - Tauri's build scripts add the plugin's Gradle module to `gen/android` themselves) wraps Google Identity Services' `AuthorizationClient` for `drive.appdata` - `authorize` (interactive: account picker + consent through `startIntentSenderForResult`; silent with the stored email pinned via `setAccount`, rejecting with `CONSENT_REQUIRED` when a screen would be needed), `clearToken`, `revoke` - and its Rust half calls it with `run_mobile_plugin` (blocking, so only off the main thread). Play services keeps and refreshes the grant: the phone stores the account file only, no tokens, and `cmd_sync::drive_token` asks the plugin before every pass (desktop: `google_link::valid_access_token`). A token Drive refuses with 401 becomes `Error::SignInExpired` (`kind: "sign_in_expired"`, also the desktop's `invalid_grant`), and on Android it is cleared from Play services' cache so the next pass mints a new one; a pass (and the first pull) on Android also holds the plugin's `keepAlive` for its duration - `SyncKeepAliveService`, a `dataSync` foreground service with a "Syncing with Google Drive" notification - so putting the app away does not freeze it mid-pass (best effort: Android refuses the start for a pass begun from the background); the UI answers that kind with "Sign in again". Commands: `google_status`, `google_sign_in` (blocking work on `spawn_blocking`), `google_sign_in_cancel`, `google_sign_out` (revoke best effort, then forget; the sync space stays, so re-signing the same account resumes), `google_pull_vault` (first run on a device that has no vault yet: when Drive holds one, pull it into `local_vault_dir` under the account's space, open it and adopt the baseline - a pass would instead join the fresh vault's default config files against the real ones and keep both; `null` when Drive is empty, and the caller starts a local vault whose first pass uploads it), and `sync_now` - one Google pass (`SyncSummary`). Pass and pull progress go out as `sync-progress` `(done, total)`. `cmd_sync::google_pass` refuses to start while another runs (`SYNC_RUNNING`), switches the vault to the account's space `gdrive-<permissionId>`, syncs with `VaultRoot("")`, records failures that happen before the pass proper in the standing, and emits `sync-status` (`SyncActivity {running, error}`) at both ends. `sync_scheduler.rs` (started in setup on every platform; on the phone it runs only the after-edit trigger, the other moments being `MobileApp.tsx`'s) is a thread that ticks every 5 s and runs a pass, while a vault is open, the device is signed in and `sync_auto` is on, when one of these is due: start, then every `sync_interval_minutes`; `sync_debounce_seconds` after the last `poke()` (export worker, KB watcher, `journal_save`) *and* only if `standing` counts something pending - so the export after a pass does not start the next one; main-window focus (`sync_on_focus`, at most once a minute); and quit (`RunEvent::Exit`, `sync_on_leave`, only with something pending, waits up to 20 s).
- `watchers.rs` - `open_vault`, `rebuild_cache`, three debounced watchers: `config/`+settings (reload + engine + `vault-updated`), `tasks/` (mirror import), KB root (with the Notes rooted at the vault the recursive watch also sees `.hypomnema/`, so `is_work_dir_event` drops events whose every path runs through the work dir - the database, WAL, mirror and snapshot writes are not notes) - plus the export worker (`start_export_worker`): a mutating command holds the vault lock for its SQL alone and then calls `AppState::request_export`, and one thread turns those kicks, after a 200 ms debounce, into a state-snapshot + mirror rewrite on its own DB connection under `engine_lock` (`export_files` is the one export routine the worker, both watchers and the synchronous `mirror_export_now` share). Only `open_vault` still exports inline, because the first pull (`google_pull_vault`) adopts the exported files as its sync baseline right after. Everything that swaps or rewrites app.db or the JSONL under the workers (`backup_restore_db`, `google_pull_vault`, a sync pass and the `rebuild_cache` it calls) holds `engine_lock` for its whole run, and the worker skips a pass whose app.db is missing rather than create an empty one.

## Frontend notes

Written against the desktop's keyboard/mouse interaction model. The phone gets its own UI under `src/mobile/` rather than a responsive squeeze of it (build specifics: `docs/android/ARCHITECTURE.md`). Five tabs: Day (`MobileDay`, one day at a time: it drives the store's `gridOffset` - the desktop date-jump mechanism - so the snapshot window follows wherever the day goes, past days included; the header (`mobile/DayHeader.tsx`, shared with Journal so both read alike: a left action - search here, the entry list there - the day's name over its date between drawn ‹ › chevrons, the label doubling as a hidden date-input picker, and Today on the right only away from today), the desktop column's ambient context (weekly focus, the day's reminders, today's Now/Next schedule blocks from `dashboard_context`), and the desktop column's own task layout through `useDaySections` - cadence sections, plates, separator stripes, Postponed/Done blocks under `done_display`, `daily_tasks_today_only` - rendered by `mobile/Sections.tsx`; a persistent input row at the bottom adds a task to the shown day), Lists (`MobileLists`, one list at a time - the desktop list column's layout through `useListSections`: Priority plate, backlog (the only block Up/Down reorders, as drag does on the desktop), closed sections - with inline list settings incl. a Group selector; the index shows groups open in place over the ungrouped lists - each group row a ▾/▸ fold toggle with its member lists indented under it (folds remembered per phone in localStorage) and a ⋯ that opens the group's own screen - and its bottom field creates either a list or a group - without that a phone could only ever see groups a desktop had made - and a tapped group gets a member-list screen of its own with its own inline settings (rename, colour, delete-with-release) and its own two ways to fill it: a new list straight into the group, or an existing one moved in. Both screens apply the desktop panel's `orderLists` rule - favorites first, auto lists only while something unscheduled or priority lives in them), Journal (`MobileJournal`, a textarea - the system keyboard is the editor on a phone; the Day screen's `DayHeader` with the entry list on its left slot and "· Saving..." after the date while a save is pending (a failed save gets a Retry line under the header), plus a `journal_list` entries screen, and it consumes `journalOpenDate` so search hits and the Review's Weekly note land here), Notes (`MobileNotes`, folder-at-a-time browse plus edit, search, tappable `[[wiki links]]`, backlinks, trash, creation and rename/move via inline forms (the WebView's prompt is unreliable on Android), the desktop's Config group - the six YAMLs + journal template through `config_file_get`/`config_file_set` with save-time validation shown inline - and it consumes `kbOpenNote` for search hits), and More (`MobileMore`) holding the sections a five-slot bar cannot seat: Upcoming (`MobileUpcoming`, the three rule files through the desktop's own comment-preserving splice commands, add/edit/delete for root-file rows), Reminders (`MobileReminders`), Calendar (`MobileCalendar`, month browse over its own month-wide `tasks_snapshot` - the store's window follows the day view - plus a QuickAdd on the selected day), Review (`MobileReview`, the desktop Review stacked for one column: done-rate over past days, per-origin tiles, Completed grouped by day, a Next week panel from `tasks_snapshot` + `calendar_outlook`, Weekly note jump, and leftover actions - Next week / Backlog - carried by each row's own "..." via TaskRow's `reviewWeekStart` prop) and Settings (`MobileSettings`: an index of panels rather than one scroll, each row carrying its live state - Sync (signed out the panel *is* "Sign in with Google", followed by a first pass that joins this vault with Drive; signed in it holds the account, the standing, Sync now, "Upload this vault again" after the mass-deletion guard, "Sign in again" after `sign_in_expired`, the automatic-sync switches, the guard limit, Sign out, and the conflict log), Appearance (theme, palette, text size, cadence colours, screen edges), Tasks & engine (engine run, notifications, done-display, snooze, capture list, retention, catch-up, cron time), Maintenance mirroring the desktop tab - delete-done sweep, archived-list restore, DB/config backup restore - Vault (path, move to another folder), Passphrase (only while one is left set from an older build; it offers nothing but removing it), and About last (the desktop dialog's own `AboutContent` from `components/AboutModal.tsx`, the version on its index row); boolean settings are switches and number settings commit on blur, both from `mobile/controls.tsx`). `MobileSearch` is the phone's Ctrl+K: a whole-screen palette over `tasks_search`/`kb_search`/`journal_search`, reached from the Day header; a task hit opens the editor (moving the day window there first when the task sits outside it), note and journal hits jump tabs through the same store fields the desktop palette uses (`MobileNavContext` in `mobile/nav.ts` carries the tab switch). The shell renders the store's Undo toast above the tab bar (delete/archive on a phone is one tap with no confirm) and the shared `DueToasts` component (`src/components/DueToasts.tsx`) - the 30s due-check, in-app toast stack and Snooze, extracted from the desktop layout so both targets run the same code. The document itself never scrolls (`html, body { overflow: hidden; overscroll-behavior: none }`): every view owns an inner scroll container, because the Android WebView scrolls the *page* to lift a focused input above the soft keyboard, which slides the whole layout up under the status bar and behind the navigation buttons. For the same reason a scroll container must never be the element carrying the inset - padding on a scrollport scrolls away with the content, and `position: sticky; top: 0` inside one sticks to the padding box, i.e. under the status bar; `MobileTaskEditor` keeps a still wrapper and scrolls its body. Every screen that owns the whole viewport wears `.safe-area` (`src/styles.css`): Android has drawn apps under the status and navigation bars since API 35 and this build targets 36, so each edge takes the larger of `env(safe-area-inset-*)` and a floor set by hand in app.yml (`mobile_safe_area_top`/`_bottom`, no Settings control) for the devices where the WebView reports no inset. `MobileVaultFolder` is the phone's answer to "pick a folder" - Android has no directory picker to call (Tauri's dialog plugin picks files; SAF returns a `content://` tree the Rust core cannot open), so the app browses the filesystem itself: `vault_browse` lists a directory with shortcuts, `vault_browse_mkdir` makes one, `vault_use_path` takes the result. Each listing reports two things a plain `read_dir` does not, because on Android both are invisible from the path and both change what the button should say: whether the app can *write* there (probed by writing a file and deleting it) and whether a vault is already there. The default vault location on Android is the app's folder on shared storage rather than its private one - both need no permission, only that one is reachable from a computer over USB. The chooser is a full screen, not a panel. `build-android.sh` declares `MANAGE_EXTERNAL_STORAGE` so the browser can leave those folders, and `android_storage.rs` asks for it from Rust - `PlatformWebview::jni_handle().exec()` hands over the JNI environment, so `Environment.isExternalStorageManager()` and the settings `Intent` need no Kotlin and no edit to the regenerated `gen/android`. Anything needing an activity *result* (a SAF picker) still would. Until the grant happens a directory reports itself unreadable instead of looking empty. `TaskRow` follows `TaskCard` (the reference - a change to the card lands in the row too): the card's stripe rule (list-exact included), chip order (list-exact date, list, `{Category}` on the alternating block palette, exact date, then `[DOW]` inside the title), PRIORITY/OVERDUE/Rate badges (stacked in a fixed-width column reserved on the row's right, so a badge never wraps under one title and not another), the `StatusMark` box and `nextStatus` cycle on a row tap, a subtask count that folds the subtasks open, and Drop beside Postpone in its actions; only the geometry (thumb-sized rows, full-height stripe) is the phone's own: a phone shows fewer tasks at once than a desktop, not less distinguishable ones. `MobileTaskEditor` is a whole screen rather than a dialog, reached from any task row through the `EditingTaskContext` in `mobile/editing.ts`; reordering is Up/Down rather than drag. Automatic sync lives in the shell and calls `sync_now` on resume, on leaving the app, on reconnect, and on a `sync_interval_minutes` heartbeat. The first-run screen (`MobileVaultSetup`) offers a local vault, a chosen folder, or "Sign in with Google", which pulls the vault from Drive (`google_pull_vault`) or, with Drive empty, starts a local vault and uploads it. Android's hardware back button undoes one UI step before it closes the app: Tauri's app plugin hands the press to a JS `back-button` listener when one is registered and otherwise walks the WebView history and closes, so `mobile/back.ts` registers the listener (`onBackButtonPress`) exactly while some screen has a step to undo and drops it when the stack empties (registrations chained, they are async) - `useBackStep(active, onBack)` handlers stack in activation order (the task editor and search overlay register on mount, screens register their inner steps: list settings / open list / open group, the More screen, the journal browser, the Notes note / search hits / folder trail one level per press, the vault chooser, the Day and Journal screens' return to today from another day, and finally the non-Day tab back to Day); with nothing registered the press closes the app, so the last step before closing is always Day on today.

- Store invalidation: `vaultVersion` counter bumped by engine runs and `vault-updated`; the YAML-backed sections (Upcoming, Reminders, Recurring, History) re-fetch on it. The task views with their own snapshot (Review, Calendar and their phone twins) re-fetch on the store's `tasks` reference alone - `refresh()` replaces the array on every run and `runEngine` calls `refresh()` itself, so one engine pass or one `vault-updated` event costs them exactly one refetch instead of two.
- `store.defaults` caches `config_default` once per session (settings disclosure and the Profiles tab); `store.profiles` + load/save/delete/applyProfile wrap the profile commands, applyProfile re-running the engine when a `WINDOW_KEYS` field changed, same contract as `updateConfig`.
- `src/lib/`: date helpers, wiki-link codec, markdown lint/table, md color presets, updater flow (silent on failure, runs once on mount).
- Bundle: `MarkdownEditor` (CodeMirror and its language packs, the largest thing in the build) and `react-markdown` (the task dialog's preview) are `React.lazy` imports, so the entry chunk carries the task views and the editor's chunk loads on first use of the Journal, Notes or a description preview. Confirms and prompts everywhere, the phone included, go through `components/dialogs.tsx` (`ConfirmModal`/`PromptModal`); `window.confirm`/`window.prompt` are not used - the WebView's native dialogs are unstyled and unreliable on Android.
- `src/hooks/`: logic the desktop and the phone share without sharing markup - `useReviewData`/`useReviewStats`/`useNextByDay` (the Review's fetches and numbers, used by `sections/Review.tsx` and `mobile/MobileReview.tsx`), `useSearch` (the debounced three-way search behind `SearchPalette` and `MobileSearch`, newest-request-wins), `useDaySections`/`useListSections` (`useColumnSections.ts`: a day or list column's sections, rows, category stripes, block hairlines and chip block indexes - `DayColumn`/`ListColumn` and `MobileDay`/`MobileLists` render the same layout, the section frame, plate and category lead are `components/ColumnSection.tsx`), `useTaskTextDraft` (title/description drafts that commit on blur, close and unmount exactly once, with `discard` for a delete, behind `TaskModal` and `MobileTaskEditor`). A behavior fix belongs there, not in one of the two twins.
- Global keys: Ctrl/Cmd+K search, Ctrl/Cmd+1..9 sections. 60s rollover engine re-run; the 30s due-task notification timer lives in `src/components/DueToasts.tsx` (rendered by both the desktop layout and the phone shell) - Snooze hides the toast and forgets the notified id after `notify_snooze_minutes`, so the 30s check raises it again while the task stays open. The check runs on mount too, fires `notify_lead_minutes` ahead ("Coming up"), folds every task whose time had already passed at a fresh start (app open, new day) into one summary toast instead of a burst, hides a toast after `notify_toast_seconds`, and drops a toast whose task is no longer `todo`.
- Undo toast (bottom center on the desktop in `App.tsx`, above the tab bar on the phone in `MobileApp.tsx`): deleting a task or archiving a list offers Undo for `undo_toast_seconds`; one pending entry at a time (`store.undoEntry`), task undo calls `task_restore` with the snapshot, list undo calls `list_unarchive`.

## Icons

One mark on every platform: a deep slate tile with a bright rim and a pure-white H traced as three nested contour lines per stem - bold enough to read at 32px on a dark taskbar ("The Meander Habit"). `src-tauri/icons/icon.svg` is the tile; `android-bg.svg`/`android-fg.svg` are the Android adaptive layers (the H alone, shrunk into the launcher's safe zone). `npx tauri icon src-tauri/icons/icon-manifest.json` regenerates everything: the desktop/iOS PNGs, `.ico` and `.icns` land in `src-tauri/icons/`, but the Android mipmaps are written straight into the uncommitted `src-tauri/gen/android` - copy its `res/mipmap-*` folders into `src-tauri/icons/android/`, which `scripts/android/build-android.sh` (`sync_launcher_icons`) copies back into the generated project on every build. `app-icon.png` at the repo root (the CLI's default input) is a 1024px render of the same tile, and the About dialog draws the mark inline from the same geometry (`src/components/AppLogo.tsx`) over the HYPOMNEMA / The Meander Habit label. Under the text the About content (`AboutContent`, shared by the desktop dialog and the phone's Settings > About) carries the legal notice: the copyright line and the GPL licence URL from `src/lib/legal.ts` (the holder is still a placeholder) and a Third-party licenses link that loads `third_party_licenses` - `THIRD_PARTY_LICENSES.txt` at the repo root, compiled into the core with `include_str!` so every platform ships it, regenerated by `scripts/general/third-party-licenses.mjs` (crates reachable through normal dependency edges from `cargo metadata`, non-dev packages from `package-lock.json`, the Android Gradle libraries listed by hand in the script) whenever dependencies change. `site/` is the static website - home page and privacy policy - that Google's OAuth verification asks for; it describes what the app sends where, so a change to sync scopes or network endpoints updates it too. The icon is compiled into the exe, so Windows shortcuts pick it up only from a rebuilt install - and Explorer may keep showing its cached copy until `ie4uinit.exe -show` (or a sign-out).

## Versioning

`VERSION` at the repo root is the single version source, synced into `package.json`/`src-tauri/tauri.conf.json`/`src-tauri/Cargo.toml` by `scripts/general/bump.sh` (never edit those manifests by hand). Bumping and cutting an actual release are separate concerns per build target - see `docs/windows/ARCHITECTURE.md` for the Windows release flow (`scripts/windows/release.sh`/`release.ps1`, `release.yml`) and `docs/android/ARCHITECTURE.md` for the Android build.

CI (`ci.yml`, push to main + PRs): frontend lint/typecheck/test/build; rust fmt/clippy(-D warnings)/test - this gate runs regardless of target, since it's exercising the shared frontend and Rust core.

No e2e on any target (`docs/general/DECISIONS.md`).
