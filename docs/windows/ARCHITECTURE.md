# Windows Desktop Notes

Supplement to `docs/general/ARCHITECTURE.md` (the shared Rust core + React frontend map). This file covers only what's specific to the Windows desktop build: the desktop-only chrome in `lib.rs`, and the Windows build/release flow. Android's equivalents live under `docs/android/`.

## Desktop-only chrome (`lib.rs`)

Single instance: `tauri-plugin-single-instance` (desktop-only dependency, registered first in `run`) turns a second launch - typically a shortcut clicked while the app sits in the tray under `tray_icon` - into `show_main` on the running instance and an immediate exit, so two copies never fight over the capture shortcut (the loser's banner read "HotKey already registered") or write the same vault.

Two windows: `main` (the app) and `capture`, a small hidden always-on-top window pre-created in `.setup()` that `src/main.tsx` routes to `CaptureWindow.tsx` via the `#/capture` hash - one input calling `capture_task` (task into the `capture_list` list, created manual+favorite on first use via `tasks::ensure_inbox`; the command emits `vault-updated` so the main window refreshes). Shown by the OS-global shortcut `capture_shortcut` and the tray menu; hidden on Esc, focus loss or close, never destroyed. The tray (`tray_icon`, Settings' "Keep running in the tray": the icon with menu Show / Quick capture / Quit, left click shows main, and a main-window close that hides instead of quitting) is synced from the config in setup, on vault open, on `config_set` and on the watcher reload; a shortcut that fails to parse/register surfaces in the error banner and never blocks saving.

Google sign-in (`google_auth.rs`) is desktop-only too: the consent page opens in the default browser and returns to a one-shot listener on `127.0.0.1:<free port>`, which answers with a "you can close this tab" page; the main window is brought back to the front afterwards. The desktop sync scheduler (`sync_scheduler.rs`) starts in setup, hears main-window focus from `on_window_event`, and gets one last pass from the `RunEvent::Exit` handler (`run` now builds the app and runs it with an event callback).

None of this exists on mobile: the tray, global-shortcut and updater plugins, and the pre-created capture window are `#[cfg(desktop)]`-only in `lib.rs`; mobile gets no-op `#[cfg(mobile)]` stubs with the same signatures so shared call sites need no branching.

## Build

- `scripts/windows/build.sh` (Linux/WSL) / `scripts/windows/build.ps1` (Windows) run `npm ci && tauri build`; `build.ps1` then copies the NSIS installer into `releases/windows/` (below), `build.sh` only lists what was built. They sign updater artifacts only with `TAURI_SIGNING_PRIVATE_KEY` set, or with the key at `~/.tauri/hypomnema.key` plus `TAURI_SIGNING_PRIVATE_KEY_PASSWORD`; otherwise they build with `createUpdaterArtifacts` off. `build.sh` on macOS or Linux only smoke-checks the pipeline (it produces that platform's bundle, not a shippable Windows installer).
- Google sign-in needs the desktop OAuth client secret compiled in (`google_auth.rs`, `option_env!("HYPOMNEMA_GOOGLE_DESKTOP_CLIENT_SECRET")`): Google treats a desktop client's secret as non-confidential, but secret scanners flag it in a public repo, so it lives in the Windows user environment, never in git. `build.ps1` (`Import-GoogleClientSecret`) copies the user-level value into the process when the shell lacks it (a shell opened before it was set, or one launched from WSL) and warns when it is missing - such a build works, with sign-in reported unavailable. `release.yml` passes the repository secret of the same name to `tauri-action`, plus the optional repository variable `HYPOMNEMA_GOOGLE_DESKTOP_CLIENT_ID` (a self-build's own client; unset keeps the project's id).
- Development: `npm run app:dev` = `tauri dev --config src-tauri/tauri.dev.conf.json`, which merges in identifier `com.hypomnema.app.dev` and productName "Hypomnema Dev". The identifier names the per-device folder (`app_config_dir`: vault path, `google.json`, device id, log), the WebView2 data folder and the single-instance lock, so a dev build runs beside the installed app without touching its vault, sign-in or device id; only the global capture shortcut is shared (the second to start reports it cannot register it). Plain `tauri dev` keeps the installed identity.
- Before building, both scripts run `scripts/general/prune-target.mjs`, which deletes stale Cargo output: Cargo never removes a unit compiled under an old hash (each version bump makes new ones), so the target dir otherwise grows by gigabytes a week. A unit (its `.fingerprint`, `deps/` and `build/` entries) or an incremental cache goes when nothing in it changed for `PRUNE_DAYS` days (default 7) and a newer one of the same name exists; files under `bundle/` go by age alone. It walks every profile dir, `target/debug` from the WSL checks included, and honors `CARGO_TARGET_DIR`; `--dry-run` reports without deleting, `--days N` overrides the limit, and any other argument prints the usage and exits 1 without touching anything (`--help` prints it and exits 0). The dev profile carries line tables only (none for dependencies), and the lib builds no `staticlib` (iOS only), which keeps the debug tree small to begin with.
- Artifacts land in `src-tauri/target/release/bundle/`; `scripts/windows/build.ps1` additionally copies the `.exe` into `releases/windows/<name>-<version>.exe`. It copies exactly `<productName>_<version>_x64-setup.exe`, and only if this run wrote it: `bundle/nsis` keeps the installers of earlier versions, and a failed build once had the newest of those copied under the new version's name. Native steps (`npm ci`, `tauri build`) go through `Invoke-Native`, which stops the script on a nonzero exit - Windows PowerShell's `$ErrorActionPreference = 'Stop'` does not cover native programs.

## Release

- `scripts/windows/release.sh [--check]` / `release.ps1 [-Check]` release the version `scripts/general/bump.sh` already set: no bump, no commit - they check a clean tree, every manifest version equal to `VERSION`, a non-empty `## <version> - ` entry in `CHANGELOG.md` (`scripts/general/changelog-entry.mjs`), the branch not behind `origin/<branch>` and no `v<version>` tag locally or on `origin`, then tag and push branch + tag - which triggers `release.yml`. `--check` stops after the checks. (They used to bump again, so every release was a version with no CHANGELOG entry.)
- `release.yml` (tag `v*`): job `verify` (a minute, before the gates) fails if the tag doesn't match `VERSION` or `CHANGELOG.md` has no entry for it, and hands the entry on as `releaseBody` (the draft's notes and `latest.json`'s `notes`); then it runs the whole `ci.yml` (called as a reusable workflow, job `checks`) on the tagged commit. `checks` grants exactly `contents: read` + `pull-requests: read`: a called workflow can only narrow the caller's token, so a `ci.yml` job asking for more than the caller grants makes the whole run fail before it starts. Then it builds a Windows-only NSIS installer via `tauri-action` and attaches it to a draft GitHub Release. The workflow token is read-only except in `build-windows` (`contents: write`, for the draft release), and its actions are pinned to commit SHAs like `ci.yml`'s. No secret is in reach of third-party build code: every checkout in both workflows sets `persist-credentials: false` (no token left in `.git/config`), `npm ci` and `npm run build` run as their own steps with no secrets in their env, and the `tauri-action` step - the only one holding `TAURI_SIGNING_PRIVATE_KEY` and the Google client secret - is passed `--config src-tauri/tauri.release.conf.json`, which removes `beforeBuildCommand` so no npm script runs beside the key. Cargo build scripts still run in that step (the remaining exposure). `build-windows` runs in the `release` environment: the signing secrets belong there, behind a required reviewer. Besides `verify` and `checks`, one job (`build-windows`, `needs: [verify, checks]`) exists today; an Android release job would be a separate addition, not a change to this flow.
- Updater endpoint = `releases/latest/download/latest.json` (a GitHub Release asset path, unrelated to the local `releases/windows/` folder); secrets `TAURI_SIGNING_PRIVATE_KEY(_PASSWORD)`. The draft release must be published for `latest.json` to be servable. The check runs once per start from `App.tsx` (`lib/updater.ts`), once the config is loaded, and only while `update_check` (Settings > General > Updates, default on) is set.
